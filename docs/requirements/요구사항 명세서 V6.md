## 1. 프로젝트 개요

### 1.1 프로젝트 배경 및 목적

본 프로젝트는 카메라로 사용자의 실제 손 자세를 인식하고, 텐던 방식으로 구동되는 3D 프린팅 로봇 손이 해당 동작을 실시간으로 따라 움직이도록 구현하는 것을 목적으로 한다.

기존의 정교한 로봇 손은 손가락 관절마다 별도의 모터와 센서를 사용하기 때문에 가격, 무게, 제작 난도가 높다. 본 프로젝트에서는 각 손가락의 여러 관절을 하나의 모터로 함께 구동하는 언더액추에이티드(underactuated) 구조를 적용하여 제한된 기간과 자원 안에서 사람 손의 주요 동작을 재현한다.

장기적으로 수집한 손동작 데이터를 학습 데이터로 활용하고, B2B 데이터·모델 제공 가능성을 검토한다. 해당 사업 확장은 현재 MVP 범위에 포함하지 않는다.

최종적으로 다음 기능을 시연하는 것을 목표로 한다.

- 실제 손의 펴기·쥐기와 엄지 대립·벌림 동작 모방
- 원통형 물체 파지
- ROS 2 기반 무선 제어
- MediaPipe landmark, 7논리축 목표 명령 및 모터 상태 기록
- 내부망 관제·제어 웹을 통한 모방 모드와 조작 모드 시연
- 추가 손동작은 시험 결과에 따라 확정한다.
- 엄지와 검지를 이용한 집기
- 통신 단절 시 안전 동작
- EC2에 배포된 데이터 포털을 통해 저장된 로봇 데이터를 조회할 수 있다.
- 사용자는 세션별 모터 위치, 모터축 각도, 속도, 전류, 온도 및 동작 결과를 확인할 수 있다.
- 사용자는 공개된 실험 데이터를 CSV 또는 JSON 파일로 다운로드할 수 있다.
- EC2 데이터 포털은 완료된 세션의 조회·다운로드 전용이며 외부 인터넷에서 로봇 제어 명령을 전달하지 않는다.

프로젝트 개발 기간은 총 3주이며, vision을 통한 손가락 동작 모방과 반복 가능한 파지 성능 확보를 우선한다.

### 1.2 MVP

1. **로봇 손 구동**
    - 제작 범위
        - 3D 모델링
        - 관절 연결
        - 텐던 연결
        - 모터 연결
    - 검증 동작
        - 손 펴기와 쥐기
        - 원통형 물체 파지
        - 엄지–검지 집기
        - 가벼운 물체 2종을 각각 10회 시험하여 7회 이상 파지
2. **실제 손동작 모방**
    - MediaPipe 기반 손 landmark 검출
    - 손가락 굽힘과 엄지 대립 및 벌림 정도 계산
    - 모터에 전달
    - 7논리축을 7개 물리 모터에 1:1로 연결한다
3. **ROS 2 패키지**
    - ROS 2 토픽·노드·서비스·액션 인터페이스 정의 및 구현
    - ROS 2를 통한 무선 명령 전달
    - ROS 2를 이용한 모터 동작
4. **완성형 웹 사용자 인터페이스**
    - 모방 모드에서 실시간 카메라 영상과 손 인식 결과 모니터링
    - 조작 모드에서 웹 버튼으로 로봇 손 제어
    - 모방 모드와 조작 모드는 별도 화면 또는 탭으로 구성
5. **EC2 기반 로봇 데이터 포털**
    - 기존 내부망 관제·제어 웹과 별도의 웹사이트로 구성한다.
    - 완료된 실험 세션 목록을 조회할 수 있다.
    - 세션별 로봇 상태와 모터 데이터를 확인할 수 있다.
    - 저장된 데이터를 CSV 또는 JSON 파일로 다운로드할 수 있다.
    - 원본 rosbag2 압축 파일 다운로드는 Could 우선순위의 선택 기능으로 분류한다.
    - EC2 웹에서는 로봇 제어, 녹화 시작·종료 및 모드 변경 기능을 제공하지 않는다.

#### MVP 제외 범위 - 향후 확장 기능

- 관절 각 선형 회귀 AI 모델 - Could
- VLA 기반 자율 조작
- Imitation Learning 모델 학습
- Isaac Sim 및 Isaac Lab 연동
- 손가락 관절별 독립 다축 제어
- 모든 관절의 실제 각도 측정
- 손가락 전체 촉각 센서
- 물체 종류 자동 인식
- 물체 위치 자동 탐색
- 클라우드 또는 외부 인터넷을 통한 로봇 원격 제어
- 산업용 수준의 방수·방진·내구성 확보
- 축–모터 결합·공유 구동은 MVP에서 사용하지 않는다

EC2 기반 데이터 조회 및 다운로드 기능은 MVP에 포함한다. 단, 외부 인터넷에서 로봇으로 명령을 전달하는 기능은 MVP 및 EC2 배포 범위에서 제외한다.

향후 학습 데이터 활용을 위해 MediaPipe landmark, 목표 명령, 모터 엔코더값 및 파지 성공 여부는 MVP에서도 저장한다.

### 1.3 제품 및 시스템 기능 요약

시스템은 크게 손동작 인식부, 명령 생성부, 로봇 손 제어부, 기구 구동부로 구성된다.

웹 시스템은 역할에 따라 두 종류로 구분한다.

1. **내부망 관제·제어 웹**
    - 프로젝트 내부 네트워크에서 실행한다.
    - MIMIC 및 MANUAL 모드를 제공한다.
    - 영상, landmark, 7논리축 목표값, 모터 상태 및 안전 상태를 실시간으로 표시한다.
    - 검증된 ROS 2 인터페이스를 통해 로봇 명령을 전달한다.
    - 녹화 시작·종료와 성공·실패 판정을 제공한다.
2. **EC2 데이터 포털**
    - 외부 사용자가 인터넷을 통해 접속한다.
    - 완료된 실험 세션과 저장된 로봇 데이터를 조회한다.
    - 세션별 데이터를 CSV 또는 JSON 파일로 다운로드한다.
    - 원본 rosbag2 압축 파일 다운로드는 Could 범위로 제공한다.
    - 로봇 제어, ROS 2 명령 전달, 모드 변경 및 녹화 제어 기능은 제공하지 않는다.
    - EC2 서버는 ROS 2 DDS 네트워크에 참여하지 않는다.

단일 로봇의 데이터 업로더는 완료된 세션의 rosbag2 및 SQLite 데이터를 공개용 CSV·JSON 형식으로 변환하고, 장치별 Bearer Token으로 인증된 HTTPS 요청을 통해 EC2 서버에 전송한다. EC2는 세션 메타데이터를 SQLite에 저장하고 파일을 영속 디렉터리에 보관한다. EC2 서버 장애나 업로드 실패는 로봇 제어 및 로컬 데이터 기록에 영향을 주지 않아야 한다.

권장 구조:

```
로봇/Jetson 또는 Logger 실행 장치
├─ ROS 2 제어
├─ rosbag2 및 SQLite 세션 데이터 저장
└─ 데이터 변환기·업로더
          │ 장치별 Bearer Token으로 인증된 HTTPS
          ▼
EC2 데이터 포털
├─ Nginx
├─ Gunicorn
├─ Django 조회·다운로드 API
├─ SQLite DB 및 EC2 영속 파일 디렉터리
└─ React 사용자 웹사이트
```

#### 내부망 웹 기반 운용 흐름

카메라와 Vision Node는 시스템 실행 중 항상 동작한다. 내부망 관제·제어 웹의 기록 버튼은 카메라 실행 여부를 제어하지 않고 rosbag2 데이터 기록만 시작하거나 종료한다.

- MIMIC 모드와 MANUAL 모드 모두에서 영상, landmark, 7논리축 목표값, 모터 상태 및 안전 상태를 확인할 수 있어야 한다.
- MIMIC 모드에서는 사용자의 손동작을 실시간으로 모방한다.
- MANUAL 모드에서는 웹 버튼으로 사전 정의 자세 또는 연속 동작을 실행한다.
- 데이터 기록은 MIMIC 모드에서만 허용하며 기록 중에는 제어 모드를 변경할 수 없다.
1. 사용자가 내부망 관제·제어 웹에 접속한다.
2. MIMIC 모드에서는 RGB 카메라 영상을 입력받아 Jetson의 MediaPipe로 손 landmark를 검출한다.
3. 시스템이 5개 손가락 굽힘값과 엄지 대립·벌림값을 계산하고 7논리축 목표값을 ROS 2 토픽으로 발행한다.
4. MANUAL 모드에서는 사용자가 사전 정의 자세 또는 연속 동작 버튼을 선택하고, 시스템이 해당 7논리축 목표값을 ROS 2 토픽으로 발행한다.
5. Raspberry Pi가 명령의 범위와 유효성을 검사한 뒤 목표값을 보간하고 모터 속도와 위치를 제한한다.
6. 서보가 스풀과 텐던을 당겨 로봇 손가락을 움직인다.
7. 시스템이 모터 상태와 시스템 상태를 ROS 2 토픽으로 발행하고 기록한다.

#### ROS 2 통합 실행 및 수동 시험

1. 개발자 또는 운영자가 bringup launch로 로봇 손 통합 제어를 시작한다.
2. 필요하면 `teleop_keyboard` 노드로 로봇 손의 각 축을 수동 제어한다.
3. 정의된 서비스와 액션으로 가위바위보 또는 5부터 0까지의 카운트다운 동작을 실행한다.

## 2. 주요 사용 시나리오

### UC-01-01. 실시간 손동작 모방(MIMIC 모드)

1. 사용자가 카메라 앞에 손을 위치시킨다.
2. 시스템이 손 landmark를 검출한다.
3. 시스템이 손가락별 굽힘값과 엄지 대립 및 벌림값을 계산한다.
4. 7논리축 목표값이 Raspberry Pi로 전달된다.
5. 로봇 손이 사용자의 손 자세를 따라 움직인다.

### UC-01-02. 웹 명령 기반 로봇 손 조작(MANUAL 모드)

1. 사용자가 내부망 관제·제어 웹에서 명령을 선택한다.
2. 7논리축 목표값이 Raspberry Pi로 전달된다.
3. 로봇 손이 전달된 목표값에 따라 움직인다.

### UC-02-01. 원통형 물체 파지(MIMIC 모드)

1. 원통형 물체를 로봇 손의 파지 영역에 배치한다.
2. 사용자가 손을 오므린다.
3. 로봇 손가락이 물체와 접촉한다.
4. 직렬 스프링이 추가 모터 이동을 흡수하며 물체를 누른다.
5. 로봇 손이 물체를 최소 3초 이상 유지한다.

### UC-02-02. 원통형 물체 파지(MANUAL 모드)

1. 사용자가 MANUAL 모드에서 원통형 물체 파지 명령을 선택한다.
2. 시스템이 사전에 정의된 7논리축 목표값을 생성한다.
3. Raspberry Pi가 명령의 유효성과 안전 상태를 검사한다.
4. 로봇 손가락이 원통형 물체를 감싸도록 움직인다.
5. 로봇 손이 물체를 최소 3초 이상 유지한다.

### UC-03. 엄지–검지 집기

1. 가벼운 소형 물체를 엄지와 검지의 집기 영역에 배치한다.
2. 사용자가 MIMIC 모드에서 집기 동작을 수행하거나 MANUAL 모드에서 집기 명령을 선택한다.
3. 시스템이 엄지 굽힘·대립축과 검지 굽힘축의 목표값을 생성한다.
4. 엄지 끝과 검지 끝 또는 검지 측면이 물체에 접촉한다.
5. 로봇 손이 물체를 최소 3초 이상 유지한다.

### UC-05. 실험 데이터 기록·업로드·조회 및 다운로드

#### A. 로컬 데이터 기록

1. 카메라와 손동작 인식 기능은 시스템 실행 중 계속 동작한다.
2. 사용자가 내부망 관제·제어 웹의 MIMIC 모드에서 기록 시작을 요청한다.
3. Logger가 고유한 Session ID를 생성하고 rosbag2 기록과 로컬 SQLite 세션 기록을 시작한다.
4. Logger는 MediaPipe landmark, 7논리축 HandCommand, 7개 모터 MotorStatus 및 필수 상태 토픽을 기록한다.
5. 사용자가 기록 종료를 요청하면 Logger가 rosbag2를 종료하고 세션 종료 시각을 저장한다.
6. 사용자가 해당 세션의 모방 성공 또는 실패를 판정한다.
7. 판정이 완료되기 전에는 다음 기록을 시작할 수 없다.
8. 카메라 원본 영상은 저장하지 않고 MJPEG 내부망 관제에만 사용한다.

#### B. EC2 데이터 변환 및 업로드

1. 데이터 업로더가 판정까지 완료된 세션을 확인한다.
2. 업로더가 로컬 rosbag2와 SQLite 데이터를 UTC 기준 JSON·CSV 파일로 변환한다.
3. 업로더가 장치별 Bearer Token을 사용한 HTTPS 요청으로 데이터를 EC2에 전송한다.
4. EC2 서버는 인증 정보, Session ID, 데이터 형식, 필수 필드 및 파일 크기를 검증한다.
5. EC2 서버는 세션 메타데이터를 SQLite에 저장하고 JSON·CSV 파일을 `EC2_DATA_DIR` 영속 디렉터리에 저장한다.
6. 동일한 Session ID와 데이터 버전을 다시 전송해도 서버에는 하나의 세션만 유지해야 한다.
7. 업로드 실패 시 로컬 원본을 보존하고 재시도할 수 있어야 하며, 로봇 제어와 로컬 기록은 계속 동작해야 한다.

#### C. 공개 데이터 조회 및 다운로드

1. 외부 사용자가 별도 로그인 없이 EC2 데이터 포털에 접속한다.
2. 사용자가 날짜, Session ID 및 성공·실패 결과로 완료 세션을 검색한다.
3. 사용자가 세션 상세 화면에서 7논리축과 모터 위치·모터축 각도·속도·전류·온도 데이터를 확인한다.
4. 사용자가 세션 메타데이터 JSON과 시계열 CSV 파일을 다운로드한다.
5. 원본 rosbag2 압축 파일 다운로드는 Could 기능이 구현된 경우에만 제공한다.

표시되는 각도는 DYNAMIXEL 모터 엔코더 기반 모터축 각도이며 실제 손가락 관절별 측정 각도를 의미하지 않는다.

EC2 데이터 포털에서는 로봇 제어, 모드 변경, 비상정지 해제 및 데이터 기록 시작·종료 기능을 제공하지 않는다.

---

### UC-06. ROS 2 시스템 실행

1. 사용자가 장치별 bringup launch를 실행한다.
2. Jetson은 카메라, MediaPipe, 손 목표 생성, MJPEG 및 Web Bridge 노드를 실행한다.
3. Raspberry Pi는 command manager, command guard, safety manager 및 DYNAMIXEL 제어 노드를 실행한다.
4. 사용자가 내부망 관제·제어 웹 또는 로컬 프로그램에서 제어 모드를 선택한다.
5. command manager가 현재 제어 모드와 제어권에 맞는 입력원 하나를 선택한다.
6. command guard가 선택된 명령의 timestamp, 범위, 속도 및 안전 상태를 검사한다.
7. 검증된 목표만 DYNAMIXEL 제어 노드에 전달한다.
8. 모터 상태, 제어 모드, 안전 상태 및 진단 정보를 ROS 2 토픽으로 발행한다.

제어 모드는 다음과 같이 구분한다.

- `DISABLED`: 일반 명령 비활성화
- `MIMIC`: MediaPipe 기반 실시간 손동작 모방
- `MANUAL`: 내부망 웹에서 Gesture 서비스와 Sequence 액션 실행
- `TELEOP`: 로컬 키보드 기반 개별축 조작

내부망 관제·제어 웹은 MIMIC과 MANUAL 모드 모두를 관제할 수 있다. 데이터 기록은 MIMIC 모드에서만 허용하며 기록 중에는 제어 모드를 변경할 수 없다.

## 3. 기능 요구사항

우선순위는 다음과 같이 구분한다.

- **Must:** MVP 완료를 위해 반드시 필요한 기능
- **Should:** 가능하면 구현해야 하지만 단순화할 수 있는 기능
- **Could:** 시간이 남을 경우 구현하는 기능

### 3.1 손 자세 인식

#### FR-01. 손 landmark 검출

**우선순위: Must**

시스템은 RGB 카메라 영상에서 한 사용자의 오른손을 검출하고 MediaPipe 기반 21개 landmark 좌표를 생성해야 한다.

인수 조건:

- MVP에서는 한 번에 한 사용자의 오른손만 검출해야 한다.
- landmark를 카메라 영상 위에 표시할 수 있어야 한다.
- 손이 검출되지 않은 상태를 구분할 수 있어야 한다.
- 손 검출 여부와 모델 신뢰도 정보를 제공해야 한다.

#### FR-02. 손가락 굽힘값 계산

**우선순위: Must**

시스템은 검지, 중지, 약지, 소지 및 엄지의 landmark를 사용하여 각 손가락의 굽힘 정도를 계산해야 한다.

인수 조건:

- 각 손가락의 굽힘값을 `0.0~1.0` 범위로 표현해야 한다.
- `0.0`은 편 상태, `1.0`은 최대 굽힘 상태로 정의한다.
- 손 크기와 카메라 거리에 따른 영향을 최소화해야 한다.
- 비정상적인 계산 결과는 허용 범위 안으로 제한해야 한다.

#### FR-03. 엄지 대립 및 벌림값 계산

**우선순위: Must**

시스템은 엄지 끝과 검지, 중지 및 손바닥 landmark의 상대 관계를 이용하여 엄지 대립 및 벌림 정도를 계산해야 한다.

인수 조건:

- 엄지 대립 및 벌림값을 `0.0~1.0`으로 표현해야 한다.
- 엄지가 검지 방향으로 접근하는 움직임을 구분할 수 있어야 한다.
- 손의 크기를 기준으로 거리를 정규화해야 한다.

#### FR-04. 사용자 캘리브레이션

**우선순위: Should**

시스템은 사용자마다 다른 손가락 가동범위를 보정할 수 있어야 한다.

인수 조건:

- 사용자의 편 손 자세를 최소값으로 저장할 수 있어야 한다.
- 사용자의 주먹 자세를 최대값으로 저장할 수 있어야 한다.
- 저장된 값은 손가락별 정규화에 적용되어야 한다.
- 캘리브레이션은 내부망 관제·제어 웹에서 편 손과 주먹 자세를 수집·확인한 후 적용해야 한다.

---

### 3.2 명령 생성 및 전달

#### FR-05. 명령값 필터링

**우선순위: Must**

시스템은 손 떨림과 landmark 오차가 모터의 급격한 움직임으로 전달되지 않도록 목표값을 필터링해야 한다.

인수 조건:

- 작은 변화는 deadband를 통해 무시할 수 있어야 한다.
- 이동 평균 또는 저역 통과 필터를 적용해야 한다.
- 한 프레임에서 목표값이 급격하게 변경되지 않도록 제한해야 한다.

#### FR-06. ROS 2 손 명령 발행

**우선순위: Must**

Jetson은 계산된 7논리축 목표값을 ROS 2 토픽으로 발행해야 한다.

권장 토픽:

```
/thing/command/mimic → command_manager → /thing/command
```

명령 데이터에는 다음 정보가 포함되어야 한다.

- 메시지 생성 시간
- 메시지 순서 번호
- 손가락별 목표값 7개
- 제어 활성화 여부
- 제어 모드
- 최대 속도 또는 속도 제한값

인수 조건:

- 명령을 초당 20회 이상 발행해야 한다.
- 오래된 명령과 최신 명령을 구분할 수 있어야 한다.
- 목표값은 사전에 정의된 범위를 벗어나지 않아야 한다.
- 제어 모드 상태는 `ControlState.msg`로 분리해 관리해야 한다.

---

### 3.3 모터 제어

#### FR-07. 7채널 서보 제어

**우선순위: Must**

Raspberry Pi는 7개의 서보에 개별 목표 위치를 전달해야 한다.

인수 조건:

- 각 모터는 서로 다른 ID를 사용해야 한다.
- 손가락마다 최소 및 최대 모터 위치를 설정할 수 있어야 한다.
- 7개 모터에 서로 다른 목표값을 전달할 수 있어야 한다.
- 잘못된 목표값은 모터에 전달되기 전에 제한되어야 한다.

#### FR-08. 명령 보간 및 속도 제한

**우선순위: Must**

Raspberry Pi는 Jetson에서 전달된 목표값을 모터 제어 주기에 맞춰 부드럽게 보간해야 한다.

인수 조건:

- 목표 위치가 갑자기 변경되어도 모터가 즉시 최대 속도로 이동하지 않아야 한다.
- 손가락별 최대 속도를 설정할 수 있어야 한다.
- 엄지 대립 및 벌림축은 일반 손가락과 별도의 속도 제한값을 사용할 수 있어야 한다.

#### FR-09. 모터 상태 수집

**우선순위: Must**

시스템은 서보에서 제공하는 상태값을 수집해야 한다.

수집 대상:

- 실제 위치
- 목표 위치
- 속도
- 전류 또는 부하 추정값
- 온도
- 통신 상태

권장 토픽:

```
/joint_states, /thing/motor_status, /thing/diagnostics
```

#### FR-10. 초기 자세 설정

**우선순위: Must**

시스템 시작 시 로봇 손이 안전하게 정의된 초기 자세로 이동해야 한다.

인수 조건:

- 시스템 시작 직후 급격한 모터 움직임이 발생하지 않아야 한다.
- 초기 자세는 편 손 또는 중립 자세로 설정할 수 있어야 한다.
- 초기 자세 이동 시 낮은 속도 제한을 적용해야 한다.

### 3.4 안전 기능

#### FR-11. 통신 timeout 감지

**우선순위: Must**

Raspberry Pi는 마지막 정상 명령을 수신한 이후 경과 시간을 지속적으로 확인해야 한다.

인수 조건:

- 200~500ms 범위에서 timeout 기준값을 설정할 수 있어야 한다.
- timeout이 발생하면 새로운 일반 명령 실행을 중단해야 한다.
- timeout 발생 여부를 시스템 상태로 발행해야 한다.

#### FR-12. 안전 상태 전환

**우선순위: Must**

통신 단절 또는 시스템 오류 발생 시 시스템은 사전에 정의된 안전 상태로 전환해야 한다.

상태는 다음과 같이 구분한다.

```
INIT
→ READY
→ RUN
→ HOLD
→ SAFE 또는 FAULT
```

- `INIT`: 시스템과 모터 초기화
- `READY`: 제어 명령 대기
- `RUN`: 정상 손동작 추종
- `HOLD`: 짧은 통신 단절 시 현재 자세 유지
- `SAFE`: 장시간 통신 단절 시 안전 자세 수행
- `FAULT`: 과전류, 과온 또는 모터 통신 오류 상태

#### FR-13. 물리적 비상정지

**우선순위: Must**

ROS 2 및 소프트웨어 상태와 관계없이 모터 전원을 차단할 수 있는 물리적 비상정지 기능을 제공해야 한다.

인수 조건:

- 비상정지 작동 시 모터 구동 전원이 차단되어야 한다.
- Jetson 또는 Raspberry Pi가 멈춘 상태에서도 작동해야 한다.
- 비상정지 해제 후 자동으로 모터가 재동작하지 않아야 한다.

#### FR-14. 과전류 및 과온 보호

**우선순위: Should**

모터가 설정된 전류 또는 온도 기준값을 초과하면 시스템은 해당 모터의 동작을 제한하거나 중단해야 한다.

---

### 3.5 파지 기능

#### FR-15. 편 손과 주먹 동작

**우선순위: Must**

로봇 손은 사용자의 손동작 또는 사전 정의된 명령을 통해 편 손과 주먹 자세를 수행해야 한다.

인수 조건:

- 모든 손가락이 시각적으로 구분 가능한 편 손 자세를 만든다.
- 모든 손가락이 주먹 방향으로 굽혀진다.
- 편 손에서 주먹, 주먹에서 편 손으로 반복 전환할 수 있다.

#### FR-16. 원통형 물체 파지

**우선순위: Must**

로봇 손은 손바닥과 여러 손가락을 이용해 가벼운 원통형 물체를 파지해야 한다.

인수 조건:

- 지정된 위치에 놓인 원통형 물체를 감쌀 수 있어야 한다.
- 물체를 최소 3초 이상 유지해야 한다.
- 동일 물체를 10회 시험하여 7회 이상 성공해야 한다.

#### FR-17. 집기

**우선순위: Must**

로봇 손은 엄지 굽힘 및 대립축과 검지를 이용해 가벼운 소형 물체를 집어야 한다.

인수 조건:

- 엄지 끝과 검지 끝 또는 검지 측면이 접촉해야 한다.
- 물체를 최소 3초 이상 유지해야 한다.
- 지정된 물체를 10회 시험하여 7회 이상 성공해야 한다.

### 3.6 데이터 저장

#### FR-18. 실험 데이터 기록 및 세션 수명주기

**우선순위: Must**

시스템은 분석·학습 및 EC2 공개 데이터 생성의 원본이 되는 실험 세션을 rosbag2와 로컬 SQLite에 일관되게 기록해야 한다.

필수 기록 데이터:

- MediaPipe landmark
- 메시지 timestamp
- 녹화 Session ID
- 녹화 시작 및 종료 시각
- 사용자 성공·실패 판정
- 7논리축 HandCommand
- 7개 모터 MotorStatus
- ControlState 및 SafetyState

책임 구분:

- Logger는 Session ID 생성, rosbag2 기록, SQLite 세션 상태 및 성공·실패 판정을 전담한다.
- 내부망 관제·제어 웹은 기록 시작·종료와 판정 요청만 전송하며 SQLite를 직접 수정하지 않는다.
- EC2 변환기·업로더는 판정까지 완료된 로컬 세션만 읽으며 원본을 수정하거나 삭제하지 않는다.

인수 조건:

- 기록은 MIMIC 모드에서만 시작할 수 있어야 한다.
- 동시에 하나의 기록 세션만 허용해야 한다.
- 기록 중에는 제어 모드를 변경할 수 없어야 한다.
- 기록 시작 시 Logger가 고유한 Session ID를 생성해야 한다.
- rosbag2에는 MediaPipe landmark, HandCommand 및 MotorStatus가 반드시 포함되어야 한다.
- 기록 종료 후 사용자가 성공 또는 실패를 판정할 수 있어야 한다.
- 성공·실패 판정이 완료되기 전에는 다음 기록을 시작할 수 없어야 한다.
- 기록된 데이터를 다시 재생하거나 JSON·CSV로 변환할 수 있어야 한다.
- 카메라와 Vision Node는 기록 여부와 관계없이 계속 동작해야 한다.
- 카메라 원본 영상은 파일이나 rosbag2에 저장하지 않고 MJPEG 내부망 관제에만 사용해야 한다.

### 3.7 내부망 관제·제어 웹 기능

#### FR-19. 웹 모드 선택

**우선순위: Must**

시스템은 사용자가 내부망 관제·제어 웹에서 로봇 손의 제어 방식을 선택할 수 있도록 해야 한다.

제공 모드:

- MIMIC: 실제 손동작 모방 모드
- MANUAL: 웹 버튼 기반 조작 모드

인수 조건:

- 사용자가 현재 선택된 제어 모드를 확인할 수 있어야 한다.
- 모방 모드와 조작 모드가 동시에 활성화되지 않아야 한다.
- 현재 제어 모드가 ROS 2 명령 메시지에 포함되어야 한다.
- 로봇 손이 동작 중이거나 초기 자세가 아닌 경우 모드 변경 요청을 거부해야 한다.
- 사용자가 정지 명령으로 로봇 손을 초기 자세로 이동한 후에만 모드를 변경할 수 있어야 한다.
- 두 모드 모두 웹에서 영상, landmark, 7논리축 목표값, 모터 상태 및 안전 상태를 확인할 수 있어야 한다.
- 데이터 기록 중에는 모든 일반 모드 변경 요청을 거부하고 MIMIC 모드를 유지해야 한다.

#### FR-20. 모방 모드 영상 표시

**우선순위: Must**

내부망 관제·제어 웹은 모방 모드에서 사용자의 손을 촬영하는 카메라 영상을 실시간으로 표시해야 한다.

인수 조건:

- RGB 카메라 영상을 내부망 관제·제어 웹 화면에서 확인할 수 있어야 한다.
- 영상 위에 MediaPipe 손 landmark를 표시해야 한다.
- 손 검출 성공 여부를 표시해야 한다.
- 손이 검출되지 않으면 사용자에게 안내 메시지를 출력해야 한다.
- 카메라 연결이 끊어진 상태를 구분할 수 있어야 한다.
- 카메라와 Vision Node는 시스템 실행 중 항상 동작해야 한다.
- MJPEG 영상 스트리밍은 데이터 녹화 여부와 독립적으로 동작해야 한다.
- MJPEG 영상은 웹 관제 목적으로만 사용하며 파일로 저장하지 않아야 한다.

#### FR-21. 모방 모드 손동작 정보 표시

**우선순위: Must**

내부망 관제·제어 웹은 MediaPipe를 통해 계산된 손동작 정보를 실시간으로 표시해야 한다.

표시 대상:

- 5개 손가락 굽힘값
- 엄지 대립 및 벌림값
- 총 7논리축 목표값
- 손 검출 신뢰도
- 현재 명령 발행 상태

인수 조건:

- 각 채널의 값을 `0.0~1.0` 범위로 표시해야 한다.
- 값의 변화를 숫자 또는 게이지 형태로 확인할 수 있어야 한다.
- 비정상적인 값은 화면에 표시하지 않고 오류 상태를 안내해야 한다.
- 기본 화면에는 손 검출 여부와 7논리축 목표값을 우선 표시하고, 원시 landmark 좌표는 별도 상세 영역에서 확인할 수 있어야 한다.
- 현재 통신 상태를 확인할 수 있어야 한다.

#### FR-22. 조작 모드 명령 입력

**우선순위: Must**

내부망 관제·제어 웹은 조작 모드에서 버튼 입력을 통해 로봇 손에 명령을 전달할 수 있어야 한다.

기본 명령:

- 손 펴기
- 주먹 쥐기
- 원통형 물체 파지 자세
- 집기 자세
- 동작 정지
- 초기 자세 이동

추가 명령:

- 가위바위보
- 카운트다운

인수 조건:

- 사용자가 버튼을 통해 각 동작을 실행할 수 있어야 한다.
- 사용자 입력을 사전에 정의된 7논리축 목표값으로 변환해야 한다.
- 현재 일반 동작이 실행 중이면 다음 일반 동작을 큐에 쌓지 않고 요청을 거부한다.
- 모방 모드에서는 조작 모드 명령이 실행되지 않아야 한다.
- 각 버튼에는 사용자가 동작을 구분할 수 있는 텍스트 또는 아이콘을 제공해야 한다.

#### FR-23. 웹 명령 범위 제한

**우선순위: Must**

내부망 관제·제어 웹에서 생성하는 명령은 사전에 정의된 안전 범위를 벗어나지 않아야 한다.

인수 조건:

- 7논리축 목표값은 각각 허용된 범위 안에서 생성되어야 한다.
- `NaN`, 무한대, 문자열 등 잘못된 값은 전달하지 않아야 한다.
- 한 번의 입력으로 목표값이 급격하게 변경되지 않아야 한다.
- 동작 정지 명령은 다른 일반 명령보다 우선하여 처리되어야 한다.
- 내부망 관제·제어 웹은 모터에 직접 명령하지 않고 ROS 2 명령 인터페이스를 통해 전달해야 한다.

#### FR-24. 로봇 및 시스템 상태 모니터링

**우선순위: Must**

내부망 관제·제어 웹은 로봇 손과 제어 시스템의 현재 상태를 표시해야 한다.

표시 대상:

- Jetson 연결 상태
- Raspberry Pi 연결 상태
- ROS 2 통신 상태
- 카메라 연결 상태
- 모터 연결 상태
- 현재 제어 모드
- watchdog 상태
- 안전 상태

인수 조건:

- 정상, 대기, 연결 끊김 및 오류 상태를 시각적으로 구분해야 한다.
- 모터 통신 오류가 발생한 경우 해당 모터를 식별할 수 있어야 한다.
- 통신이 끊기면 사용자에게 즉시 상태를 안내해야 한다.
- 상태 정보는 주기적으로 갱신되어야 한다.

#### FR-25. 모터 상태 표시

**우선순위: Should**

내부망 관제·제어 웹은 Raspberry Pi가 발행한 모터 상태를 확인할 수 있도록 해야 한다.

표시 대상:

- 모터별 목표 위치
- 모터별 실제 위치
- 모터별 속도
- 모터별 전류
- 모터별 온도
- 모터 통신 상태

인수 조건:

- 7개 모터의 상태를 구분하여 표시해야 한다.
- 전류 또는 온도가 기준값을 초과하면 경고를 표시해야 한다.
- 상태값을 수신하지 못한 경우 마지막 값과 연결 끊김 상태를 구분해야 한다.
- 내부망 관제·제어 웹 화면의 상태 표시가 실제 모터 안전 제어를 대신해서는 안 된다.

#### FR-26. 데이터 기록 UI 및 상태 표시

**우선순위: Must**

내부망 관제·제어 웹은 FR-18의 기록 수명주기를 사용자가 안전하게 요청하고 확인할 수 있는 UI를 제공해야 한다. 실제 기록, Session ID 생성 및 SQLite 변경은 Logger가 담당한다.

인수 조건:

- 기록 시작 버튼은 MIMIC 모드이고 활성 세션과 판정 대기 세션이 없을 때만 활성화되어야 한다.
- 웹은 기록 시작·종료 및 성공·실패 판정 요청을 정해진 ROS 2 서비스로 전달해야 한다.
- 현재 기록 상태, 활성 Session ID, 최근 종료 Session ID 및 판정 대기 여부를 표시해야 한다.
- 기록 중에는 모드 변경 UI를 비활성화하고 서버가 모드 변경 요청도 거부해야 한다.
- 중복 시작·종료 요청을 비활성화하거나 명확하게 거부해야 한다.
- 기록 또는 판정 요청이 실패하면 원인을 사용자에게 표시해야 한다.
- 웹은 SQLite와 rosbag2 파일을 직접 생성·수정·삭제하지 않아야 한다.
- WebSocket 요청과 응답은 동일한 `request_id`로 연결할 수 있어야 한다.

#### FR-27. 웹 오류 및 안전 안내

**우선순위: Must**

내부망 관제·제어 웹은 시스템 오류와 안전 상태를 사용자가 이해할 수 있도록 안내해야 한다.

안내 대상:

- 손 검출 실패
- 카메라 연결 실패
- ROS 2 통신 단절
- Raspberry Pi 연결 실패
- 모터 통신 오류
- timeout 발생
- 과전류 및 과온
- 비상정지 작동

인수 조건:

- 오류 발생 위치와 원인을 화면에 표시해야 한다.
- 위험 상태에서는 새로운 일반 조작 명령을 비활성화해야 한다.
- 비상정지가 작동한 경우 해제 전까지 조작 기능을 사용할 수 없어야 한다.
- 통신이 복구되더라도 사용자의 명시적인 제어 재개 입력 없이 자동으로 로봇 손을 움직이지 않아야 한다.

#### FR-28. 내부망 관제·제어 웹 실행 환경 제한

**우선순위: Must**

내부망 관제·제어 웹은 프로젝트 전용 내부 네트워크에서만 접근·사용하도록 구성해야 한다.

인수 조건:

- 본 요구사항은 MIMIC 및 MANUAL 제어 기능을 제공하는 내부망 관제·제어 웹에 적용한다.
- 외부 인터넷에서 직접 로봇 손을 제어할 수 없어야 한다.
- 웹 명령은 지정된 ROS 2 시스템에만 전달되어야 한다.
- 내부망 웹 서버가 중단되어도 Raspberry Pi의 모터 제한과 안전 기능은 독립적으로 동작해야 한다.
- EC2 데이터 포털은 별도 외부 웹으로 운영할 수 있으나 로봇 제어 기능을 제공하지 않아야 한다.

### 3.8 ROS 2 시스템 및 인터페이스

#### FR-29. ROS 2 패키지 모듈화

**우선순위: Must**

시스템은 기능별 책임을 분리한 ROS 2 패키지로 구성해야 한다.

권장 패키지:

| 패키지 | 주요 역할 | 실행 장치 |
| --- | --- | --- |
| `thing_interfaces` | 메시지·서비스·액션 정의 | 공통 |
| `thing_description` | URDF·mesh·RViz 설정 | 공통 |
| `thing_vision` | 카메라·MediaPipe·7논리축 목표·영상 overlay | Jetson |
| `thing_control` | 명령 중재·검증·안전·Gesture·Sequence | Raspberry Pi |
| `thing_hardware` | DYNAMIXEL 통신과 상태 수집 | Raspberry Pi |
| `thing_teleop` | 키보드 기반 개별축 제어 | Laptop 또는 Jetson |
| `thing_logger` | rosbag2와 SQLite 세션 관리 | Jetson 또는 Laptop |
| `thing_web_bridge` | WebSocket JSON과 ROS 2 연결 | Jetson |
| `thing_bringup` | Launch와 YAML 설정 | 공통 |

인수 조건:

- 각 패키지는 하나의 명확한 책임을 가져야 한다.
- `command_manager`와 `command_guard`는 독립 노드로 실행해야 한다.
- 공통 인터페이스는 `thing_interfaces`에서 관리해야 한다.
- 모든 패키지는 동일한 workspace에서 빌드할 수 있어야 한다.
- EC2 데이터 업로더는 `thing_logger`와 분리된 일반 Python 애플리케이션 또는 독립 모듈로 구현할 수 있으며 EC2 서버를 ROS 2 DDS 네트워크에 참여시키지 않아야 한다.

- `0.0`은 펼침, `1.0`은 최대 굽힘 또는 대립으로 정의한다.

- 일부 모터 읽기에 실패해도 성공한 모터의 상태는 함께 발행해야 한다.
- `bus_communication_ok`는 설정된 전체 모터와 정상 통신했을 때만 `true`여야 한다.
- `failed_read_count`는 모터 노드 시작 이후의 누적 읽기 실패 횟수여야 한다.

- `/thing/recording_state`는 `Reliable`, `Keep Last 1`, `Transient Local` QoS를 사용해야 한다.

#### FR-32. 명령 검증 및 안전 목표 생성

**우선순위: Must**

```

	↓

	↓
/thing/safe_target
```

검증 항목:

- 현재 SafetyState

인수 조건:

- 검증을 통과한 명령만 `/thing/safe_target`으로 발행해야 한다.
- 입력원 선택과 제어권 중재는 수행하지 않아야 한다.
- 안전 상태에서 허용되지 않는 일반 명령을 차단해야 한다.
- `command_guard`가 중단되면 마지막 일반 명령을 계속 실행하지 않아야 한다.

#### FR-33. 최신 목표 추종형 모터 제어

**우선순위: Must**

인수 조건:

- 명령 콜백은 `latest_target`만 갱신하고 즉시 반환해야 한다.
- 별도 제어 타이머가 최신 목표를 향해 보간해야 한다.
- 이전 목표에 도달하기 전에 새로운 목표를 처리할 수 있어야 한다.
- hardware-side timeout 시 마지막 일반 목표를 계속 실행하지 않아야 한다.
- 상태를 `/joint_states`와 `/thing/motor_status`로 발행해야 한다.

#### FR-35. 안전 상태 관리

**우선순위: Must**

안전 상태:

```

```

| 현재 상태 | 조건 | 다음 상태 | 동작 |
| --- | --- | --- | --- |
| 시작 전 | Bringup 실행 | `INIT` | 설정·모터 통신 검사 |
| `INIT` | 초기화 성공 | `READY` | 명령 대기 |
| `INIT` | 초기화 실패 | `FAULT` | 모터 구동 금지 |
| `READY` | 유효한 명령 | `RUN` | 최신 목표 추종 |

| `RUN/HOLD` | timeout 장기화 | `SAFE` | 안전 동작 수행 |

인수 조건:

- `SAFE`, `FAULT`, `ESTOP`은 일반 명령보다 우선해야 한다.
- HOLD 진입 후 자동으로 RUN에 복귀하지 않아야 한다.
- 통신 복구 후 사용자의 재활성화를 요구해야 한다.
- 실제 timeout·전류·온도 제한값은 하드웨어 시험 후 확정한다.

#### FR-42. Bringup Launch

**우선순위: Must**

필수 launch:

```
vision.launch.py
thing_bringup.launch.py
```

역할:

- `vision.launch.py`
    - Jetson의 카메라 입력, MediaPipe landmark 검출, 7논리축 목표 생성, 영상 overlay·MJPEG 및 Web Bridge를 실행한다.
- `thing_bringup.launch.py`
    - Raspberry Pi의 `command_manager`, `command_guard`, `safety_manager`, Gesture·Sequence executor와 DYNAMIXEL hardware node를 실행한다.

인수 조건:

- Jetson 비전 스택은 Docker 컨테이너 내부에서 `vision.launch.py` 한 번으로 실행할 수 있어야 한다.
- Raspberry Pi 제어 스택은 Docker 컨테이너 내부에서 `thing_bringup.launch.py` 한 번으로 실행할 수 있어야 한다.
- 각 장치의 컨테이너는 문서화된 단일 실행 명령 또는 실행 스크립트로 시작할 수 있어야 한다.
- 컨테이너 실행 시 필요한 장치, 네트워크, 볼륨 및 환경 변수 설정을 함께 적용해야 한다.
- Teleop은 `thing_teleop` 패키지의 노드를 `ros2 run`으로 직접 실행해야 한다.
- Logger는 `thing_logger` 패키지의 노드를 `ros2 run`으로 직접 실행해야 한다.
- Teleop과 Logger 전용 launch 파일을 만들지 않는다.
- 단일 컴퓨터용 `full_system.launch.py`와 dry-run launch를 만들지 않는다.

### 3.9 EC2 기반 데이터 포털

#### 확정된 MVP 데이터 계약

- 조회 접근: 별도 로그인 없는 공개 읽기 전용 GET
- 업로드 인증: 단일 로봇에 발급한 장치별 Bearer Token
- EC2 메타데이터 DB: SQLite
- EC2 파일 저장소: `EC2_DATA_DIR`로 지정한 영속 디렉터리(기본값 `/var/lib/thing-data`)
- 필수 다운로드: 세션 메타데이터 JSON, HandCommand CSV, MotorStatus CSV
- 선택 다운로드: 원본 rosbag2 압축 파일(Could)
- 시간 기준: UTC
- 대상 장치: 단일 로봇

#### FR-46. 실험 데이터 EC2 전송

**우선순위: Must**

시스템은 판정까지 완료된 단일 로봇의 실험 세션을 장치별 Bearer Token으로 인증된 HTTPS 요청을 통해 EC2 서버에 전송할 수 있어야 한다.

전송 대상:

- Session ID
- 녹화 시작 및 종료 시각
- 사용자 성공·실패 판정
- MediaPipe landmark
- 7논리축 HandCommand 목표값
- 모터별 목표 위치
- 모터별 실제 엔코더 위치 및 모터축 각도
- 모터별 속도, 전류 및 온도
- 모터 통신 상태와 안전 상태
- UTC timestamp
- 데이터 스키마 및 변환 버전

업로드 상태:

```
PENDING
UPLOADING
COMPLETED
FAILED
```

인수 조건:

- 업로더는 `Authorization: Bearer <device-token>` 헤더를 사용해야 한다.
- 서버는 등록된 단일 로봇의 유효한 토큰만 허용해야 한다.
- 완료되지 않았거나 성공·실패 판정이 남은 세션은 업로드하지 않아야 한다.
- 업로드 전에 rosbag2와 로컬 SQLite 세션 정보를 UTC 기준 JSON·CSV 형식으로 변환해야 한다.
- JSON과 CSV의 시간값은 UTC임을 스키마에 명시해야 한다.
- 동일한 Session ID와 데이터 버전을 다시 전송해도 중복 세션을 생성하지 않아야 한다.
- 업로드 성공 여부, 마지막 시도 시각 및 실패 사유를 로컬에서 확인할 수 있어야 한다.
- 업로드 실패 시 로컬 rosbag2, SQLite 및 변환 파일을 삭제하지 않아야 한다.
- 업로드 실패가 로봇 제어, 내부망 관제 및 로컬 데이터 기록에 영향을 주지 않아야 한다.
- 카메라 원본 영상은 업로드하지 않아야 한다.

#### FR-47. 공개 세션 목록 및 상세 조회

**우선순위: Must**

EC2 데이터 포털은 별도 로그인 없이 완료된 실험 세션을 읽기 전용으로 조회할 수 있어야 한다.

표시 대상:

- Session ID
- UTC 기준 실험 시작 및 종료 시각
- 실험 시간
- 성공·실패 결과
- 데이터 업로드 시각
- 시계열 샘플 수 또는 CSV 행 수
- 데이터 스키마 버전
- 사용 가능한 다운로드 형식과 파일 크기

인수 조건:

- 조회 API는 인증 없는 GET 요청을 허용해야 한다.
- 공개 사용자는 POST, PUT, PATCH 및 DELETE 요청으로 데이터를 변경할 수 없어야 한다.
- 최신 세션을 먼저 표시해야 한다.
- 날짜, Session ID 및 성공·실패 결과로 검색하거나 필터링할 수 있어야 한다.
- 세션 목록은 페이지 단위로 조회할 수 있어야 한다.
- 존재하지 않는 세션을 요청하면 명확한 오류를 반환해야 한다.
- 업로드가 완료되지 않은 세션은 공개 목록에 표시하지 않아야 한다.

#### FR-48. 로봇 데이터 시각화

**우선순위: Must**

EC2 데이터 포털은 세션별 저장 로봇 데이터를 숫자, 표 또는 그래프로 표시해야 한다.

표시 대상:

- 7논리축 목표값
- MediaPipe landmark 데이터 또는 요약 정보
- 모터별 목표 위치
- 모터별 실제 엔코더 위치 및 모터축 각도
- 모터별 속도
- 모터별 전류
- 모터별 온도
- 모터 통신 상태
- ControlState 및 SafetyState 변경 이력
- 실험 성공·실패 결과

인수 조건:

- 화면에 표시하는 시간은 UTC 기준임을 명시해야 한다.
- 위치, 각도, 속도, 전류 및 온도의 단위를 표시해야 한다.
- 7개 논리축과 7개 활성 모터를 구분하여 조회할 수 있어야 한다.
- 결측값, `NaN` 및 통신 실패 값을 정상값과 구분해야 한다.
- 많은 데이터에는 화면 표시용 샘플링 또는 다운샘플링을 적용할 수 있어야 한다.
- 표시되는 각도는 모터 엔코더 기반 모터축 각도이며 실제 손가락 관절별 측정 각도가 아님을 표시해야 한다.
- 카메라 원본 영상은 표시하지 않아야 한다.

#### FR-49. 데이터 다운로드

**우선순위: Must**

EC2 데이터 포털은 사용자가 선택한 완료 세션의 공개 데이터를 다운로드할 수 있도록 해야 한다.

필수 다운로드 형식:

- 세션 메타데이터: JSON
- 7논리축 HandCommand 시계열: CSV
- 모터 상태 시계열: CSV

선택 다운로드 형식:

- 원본 rosbag2 압축 파일: Could

인수 조건:

- JSON과 CSV 다운로드는 별도 로그인 없이 읽기 전용 GET으로 제공해야 한다.
- 다운로드 파일명에 Session ID와 데이터 버전 또는 생성 시각이 포함되어야 한다.
- 각 CSV 행에는 UTC timestamp가 포함되어야 한다.
- 각 필드의 단위, 데이터 타입 및 결측값 처리 기준을 설명하는 스키마 문서를 함께 제공해야 한다.
- 선택하지 않은 다른 세션의 데이터가 포함되지 않아야 한다.
- 손상되었거나 존재하지 않는 파일을 정상 파일로 제공하지 않아야 한다.
- 다운로드 전에 파일 형식과 크기를 확인할 수 있어야 한다.
- 카메라 원본 영상은 저장하거나 다운로드 대상으로 제공하지 않아야 한다.
- 다운로드 실패 시 사용자에게 오류 원인을 안내해야 한다.

#### FR-50. EC2 웹의 조회 전용 제한

**우선순위: Must**

EC2 데이터 포털의 일반 사용자용 웹 UI와 공개 GET API는 완료된 로봇 데이터의 조회·다운로드 전용이어야 한다. 쓰기 기능은 장치별 Bearer Token이 필요한 업로드 API로 한정해야 한다.

인수 조건:

- EC2 웹에 로봇 동작 명령 기능을 제공하지 않아야 한다.
- EC2 웹에 MIMIC, MANUAL 또는 TELEOP 모드 변경 기능을 제공하지 않아야 한다.
- EC2 웹에서 데이터 기록을 시작하거나 종료할 수 없어야 한다.
- EC2 웹에서 비상정지를 해제하거나 안전 상태를 변경할 수 없어야 한다.
- EC2 서버는 ROS 2 DDS 네트워크에 참여하지 않아야 한다.
- 외부 인터넷에 모터 제어 API, ROS 2 Web Bridge, ROS 2 토픽·서비스·액션을 노출하지 않아야 한다.
- 내부 로봇에서 EC2로 향하는 인증된 업로드 경로만 허용하고 EC2에서 로봇으로 향하는 제어 경로를 만들지 않아야 한다.
- EC2 서버가 중단되거나 침해되어도 로봇은 독립적으로 안전 제어를 수행할 수 있어야 한다.

---

#### FR-51. 데이터 업로드 보안

**우선순위: Must**

로봇 측 업로더와 EC2 서버 사이의 데이터 전송은 장치별 Bearer Token과 HTTPS로 인증해야 한다.

인수 조건:

- 업로드 API는 Bearer Token이 없거나 유효하지 않은 요청을 `401 Unauthorized`로 거부해야 한다.
- 토큰은 단일 로봇 업로더에 발급하고 환경 변수 또는 안전한 비밀정보 저장소에서 관리해야 한다.
- 인증 토큰, 비밀번호 및 비밀키를 Git 저장소나 Docker 이미지에 포함하지 않아야 한다.
- 로그에 토큰, 비밀번호 및 전체 `Authorization` 헤더를 출력하지 않아야 한다.
- 서버는 허용된 파일 형식과 설정된 최대 업로드 크기를 검사해야 한다.
- 파일명과 저장 경로를 서버에서 생성하여 경로 조작을 방지해야 한다.
- 카메라 원본 영상, 사용자 이름, 내부 IP 주소 및 운영 비밀정보를 공개 데이터에 포함하지 않아야 한다.

#### FR-52. EC2 배포 및 상태 확인

**우선순위: Must**

EC2 데이터 포털은 반복 가능한 방식으로 배포하고 외부 네트워크에서 실행 상태를 확인할 수 있어야 한다.

인수 조건:

- React 프론트엔드 프로덕션 빌드가 성공해야 한다.
- Django 테스트와 운영 설정 검증이 성공해야 한다.
- Nginx와 Gunicorn을 통해 HTTPS 서비스를 실행해야 한다.
- Django 메타데이터 DB는 EC2 SQLite를 사용해야 한다.
- SQLite DB와 공개 파일은 `EC2_DATA_DIR` 영속 디렉터리 아래에 보관해야 한다.
- GitLab CI 파이프라인 성공 후 운영 배포를 진행해야 한다.
- 운영 배포는 승인된 브랜치와 승인된 사용자만 수동으로 실행할 수 있어야 한다.
- EC2 서버는 애플리케이션 상태 확인용 `GET /health` API를 제공해야 한다.
- 서버 재시작 후 서비스와 데이터가 정상적으로 유지되어야 한다.
- 배포 실패 시 기존 정상 버전을 유지하거나 복구할 수 있어야 한다.
- 운영 비밀정보와 서버 설정은 소스 코드와 분리해야 한다.

### 3.10 배포 및 실행 환경

#### FR-53. 엣지 장치 Docker 실행 환경

**우선순위: Must**

Jetson 및 Raspberry Pi 애플리케이션은 Docker 컨테이너로 실행해야 한다. 각 장치의 기능을 독립된 컨테이너 단위로 배포하고, 동일한 실행 환경을 재현할 수 있도록 Docker 이미지와 실행 설정을 관리해야 한다.

인수 조건:

- Jetson의 비전·AI 처리 및 Web Bridge는 Docker 컨테이너에서 실행되어야 한다.
- Raspberry Pi의 명령 중재·안전 관리 및 DYNAMIXEL 제어는 Docker 컨테이너에서 실행되어야 한다.
- Dockerfile과 장치별 실행 설정은 GitLab 저장소에서 버전 관리해야 한다.
- 컨테이너 이미지에는 애플리케이션과 실행에 필요한 의존성을 포함해야 한다.
- 카메라와 U2D2 장치 파일은 필요한 컨테이너에만 명시적으로 연결해야 한다.
- ROS 2 DDS 통신에 필요한 네트워크 설정을 장치별 실행 설정에서 관리해야 한다.
- rosbag2, 로컬 SQLite, 로그 및 설정은 컨테이너 삭제 후에도 유지되도록 영속 볼륨에 저장해야 한다.
- ROS_DOMAIN_ID, 장치 경로, 저장 경로 및 EC2 주소는 환경 변수 또는 외부 설정 파일로 주입해야 한다.
- 인증 토큰과 비밀번호는 Docker 이미지 또는 Git 저장소에 포함하지 않아야 한다.
- 컨테이너 재시작 후 이전의 일반 제어 명령을 자동으로 재실행하지 않아야 한다.
- 컨테이너 실행 실패가 물리적 비상정지 기능을 방해해서는 안 된다.
- 장치별 전체 서비스를 문서화된 단일 실행 명령 또는 실행 스크립트로 시작할 수 있어야 한다.

## 4. 프로세스 흐름 및 시스템 아키텍처

### 4.1 장치 배치

Jetson과 Raspberry Pi의 애플리케이션은 호스트 운영체제에 직접 설치하는 방식이 아니라 Docker 기반 컨테이너 실행 환경으로 배포한다.

```
[NVIDIA Jetson Orin Nano]
└─ Docker Container
   ├─ camera_node
   ├─ hand_tracking_node
   ├─ hand_target_node
   ├─ landmark_overlay / MJPEG server
   └─ thing_web_bridge
          │ ROS 2 DDS / Wi-Fi
          ▼
[Raspberry Pi 5]
└─ Docker Container
   ├─ command_manager
   ├─ command_guard
   ├─ gesture / sequence executor
   ├─ safety_manager
   ├─ dynamixel_hand_node
   └─ state / diagnostics publisher
          │ U2D2
          ▼
DYNAMIXEL XL-330
          ▼
텐던 로봇 손
```

컨테이너는 장치의 역할에 따라 하나 이상의 서비스로 분리할 수 있다. 다만 컨테이너 구성 방식과 관계없이 카메라·U2D2 접근, ROS 2 네트워크, 영속 데이터 볼륨 및 환경 변수 설정을 명시적으로 관리해야 한다.

### 4.2 모방 명령 흐름

```
RGB 카메라
→ MediaPipe landmark 검출
→ 7논리축 손 목표 생성
→ /thing/command/mimic
→ command_manager
→ /thing/command
→ command_guard
→ /thing/safe_target
→ dynamixel_hand_node
→ U2D2
→ DYNAMIXEL
→ 텐던 로봇 손
```

### 4.3 웹 관제 흐름

```
카메라
→ MediaPipe landmark overlay
→ MJPEG Server
→ 웹 모니터링 화면
```

MJPEG는 관제 전용이며 ROS 2 모터 제어 경로와 분리한다. 카메라는 항상 실행하지만 영상 파일은 저장하지 않는다.

### 4.4 상태 피드백 흐름

```
DYNAMIXEL
→ dynamixel_hand_node
├─ /joint_states
├─ /thing/motor_status
└─ /thing/diagnostics
→ Web Bridge·Logger·개발 도구
```

### 4.5 녹화 흐름

```
웹 녹화 시작
→ Web Bridge
→ /thing/start_recording
→ Logger
├─ Session ID 생성
├─ rosbag2 시작
└─ SQLite 기록

웹 녹화 종료
→ /thing/stop_recording
→ 성공·실패 판정
→ /thing/set_recording_result
→ 다음 녹화 허용
```

### 4.6 안전 우선순위

```
물리적 E-Stop
> FAULT / SAFE 제어
> 소프트웨어 정지
> 현재 활성 모드의 일반 명령
```

MIMIC, MANUAL 및 TELEOP은 동시에 활성화되지 않으며 모드 간 명령 우선순위를 두지 않는다. SafetyState는 현재 활성 모드의 모든 일반 명령보다 우선한다.

### 4.7 실험 데이터 변환 및 EC2 업로드 흐름

```
ROS 2 토픽
├─ /thing/landmarks
├─ /thing/command
├─ /thing/motor_status
├─ /thing/control_state
└─ /thing/safety_state
        │
        ▼
Logger
├─ rosbag2 원본 데이터
└─ SQLite 로컬 세션 정보
        │ 세션 종료 및 판정 완료
        ▼
데이터 변환기·업로더
├─ metadata.json
├─ hand_command.csv
├─ motor_status.csv
├─ 상태·진단 데이터
└─ rosbag2.zip(Could)
        │ 장치별 Bearer Token으로 인증된 HTTPS
        ▼
EC2 Django API
├─ SQLite 세션 메타데이터 DB
├─ EC2_DATA_DIR 영속 파일 저장소
└─ React 조회·다운로드 웹
```

rosbag2는 ROS 2 토픽의 로컬 원본 기록을 담당한다. EC2 서버가 rosbag2 또는 ROS 2 토픽을 직접 구독하지 않으며, 로봇 측 변환기·업로더가 완료된 세션만 장치별 Bearer Token을 사용해 HTTPS로 전송한다. 모든 저장·응답 시간은 UTC를 기준으로 한다.

### 4.8 EC2 데이터 포털 배치

```
내부 로봇 네트워크
├─ Jetson Orin Nano
├─ Raspberry Pi 5
├─ 내부망 관제·제어 웹
├─ Logger
└─ 데이터 변환기·업로더
        │ 장치별 Bearer Token HTTPS Push
        ▼
외부 AWS EC2
└─ Docker Compose
   ├─ Nginx
   ├─ Gunicorn
   ├─ Django REST API
   ├─ React 정적 웹
   ├─ SQLite DB
   └─ EC2_DATA_DIR 영속 파일 저장소
        │ 로그인 없는 HTTPS GET 조회·다운로드
        ▼
외부 데이터 조회 사용자
```

EC2는 ROS 2 DDS 네트워크에 참여하지 않으며, EC2에서 내부 로봇으로 향하는 역방향 제어 경로를 만들지 않는다. SQLite DB와 데이터 파일은 컨테이너가 재시작되어도 유지되는 EC2 영속 디렉터리에 저장한다.

### 4.9 두 웹사이트 역할 구분

| 구분 | 내부망 관제·제어 웹 | EC2 데이터 포털 |
| --- | --- | --- |
| 접근 환경 | 프로젝트 내부 네트워크 | 외부 인터넷 |
| 주요 사용자 | 조작 사용자 및 개발자 | 로그인 없이 저장 데이터를 조회하는 외부 사용자 |
| 접근·인증 | 내부 운용 정책에 따름 | 조회·다운로드는 인증 없는 공개 GET, 업로드는 장치별 Bearer Token |
| 데이터 성격 | 실시간 영상·상태·명령 | 완료되어 업로드된 단일 로봇의 저장 세션 |
| 실시간 영상 | 제공 | 제공하지 않음 |
| 로봇 제어 | 가능 | 불가능 |
| ROS 2 네트워크 참여 | Web Bridge를 통해 연동 | 참여하지 않음 |
| 모드 변경 | 가능 | 불가능 |
| 녹화 시작·종료 | MIMIC 모드에서 가능 | 불가능 |
| 데이터 조회 | 실시간 관제 중심 | UTC 기준 저장 데이터 분석 중심 |
| 다운로드 | 내부 개발 목적 | JSON·CSV 필수, rosbag2 Could |
| 배포 위치 | Jetson 또는 내부 서버 | AWS EC2의 Docker 실행 환경 |

## 5. 비기능 요구사항

### 5.1 성능 요구사항

#### NFR-01. 영상 처리 성능

- 손 landmark 검출은 평균 20FPS 이상을 목표로 한다.
- 손동작 목표값은 초당 20~30회 생성해야 한다.

#### NFR-02. 응답 지연

- 실제 손 움직임부터 로봇 손 동작 시작까지의 전체 지연은 300ms 이하를 목표로 한다.
- 일시적인 프레임 지연이 모터의 급격한 움직임으로 이어지지 않아야 한다.

#### NFR-03. 내구성

- 반복 후 텐던 이탈이나 부품 파손이 발생하지 않아야 한다.
- 최종 시스템은 최소 10분 동안 연속 시연할 수 있어야 한다.

#### NFR-04. 파지 성공률

- 가벼운 물체 2종을 각각 10회 시험한다.
- 각 물체에 대해 7회 이상의 파지 성공을 목표로 한다.

---

### 5.2 신뢰성 및 안전 요구사항

#### NFR-05. 명령 유효성

- 범위를 벗어난 명령은 실행하지 않아야 한다.
- timestamp가 오래된 명령은 무시해야 한다.
- `NaN`, 무한대 및 비정상적인 데이터가 모터에 전달되지 않아야 한다.

#### NFR-06. 고장 격리

- 하나의 모터 통신 오류가 전체 프로그램의 비정상 종료로 이어지지 않아야 한다.
- 오류가 발생한 모터와 오류 원인을 확인할 수 있어야 한다.

#### NFR-07. 기구 안전

- 스프링에는 최대 신장 제한 구조를 적용해야 한다.
- 텐던이 스풀과 가이드에서 쉽게 이탈하지 않아야 한다.
- 손가락이 설계된 가동범위를 물리적으로 초과하지 않아야 한다.
- 모터의 최대 출력 또는 토크를 안전 범위로 제한해야 한다.

---

### 5.3 사용성 요구사항

#### NFR-08. 실행 편의성

- 전체 시스템은 ROS 2 launch 파일을 통해 실행할 수 있어야 한다.
- 실행에 필요한 주요 파라미터는 코드 수정 없이 설정 파일에서 변경할 수 있어야 한다.

설정 대상:

- 카메라 번호
- 모터 ID
- 모터별 최소·최대 위치
- 속도 제한
- timeout 시간
- 안전 자세 및 초기 자세

#### NFR-09. 상태 확인

사용자는 다음 상태를 확인할 수 있어야 한다.

- 손 검출 여부
- 현재 7논리축 목표값
- ROS 2 통신 상태
- 모터 연결 상태
- watchdog 상태
- 오류 코드
- 데이터 기록 여부

손 검출, 7논리축 목표값, 연결, 안전 및 데이터 기록 상태는 내부망 관제·제어 웹에서 확인할 수 있어야 한다. 상세 진단 정보는 로그에서도 확인할 수 있어야 한다.

---

### 5.4 유지보수 및 확장성 요구사항

#### NFR-10. 모듈 분리

다음 기능은 서로 독립적인 ROS 2 노드 또는 모듈로 분리해야 한다.

- 영상 입력
- 손 자세 인식
- 7논리축 명령 생성
- 모터 제어
- 안전 관리
- 데이터 저장

#### NFR-11. 설정 분리

모터 제한값, 캘리브레이션값 및 안전 파라미터는 YAML 등 별도 설정 파일에서 관리해야 한다.

#### NFR-12. 향후 센서 확장

향후 다음 센서를 추가할 수 있도록 상태 메시지와 데이터 저장 구조를 확장 가능하게 설계해야 한다.

- 관절각 센서
- 스프링 변위 센서
- FSR 또는 촉각 센서
- 손끝 힘 센서
- 외부 모션 캡처 시스템

### 5.5 내부망 관제·제어 웹 인터페이스 비기능 요구사항

#### NFR-13. 내부망 관제·제어 웹 화면 응답 성능

내부망 관제·제어 웹은 사용자의 조작과 시스템 상태 변화를 지연 없이 확인할 수 있도록 응답해야 한다.

측정 기준:

- 일반적인 버튼과 메뉴 입력은 200ms 이내에 화면에 반영되어야 한다.
- 손 검출 상태와 7논리축 목표값은 초당 10회 이상 갱신되어야 한다.
- 모터 및 시스템 상태는 초당 5회 이상 갱신되어야 한다.
- 내부망 관제·제어 웹 화면 갱신이 ROS 2의 20~30Hz 명령 발행을 방해해서는 안 된다.
- 영상 표시 지연은 전체 로봇 제어 지연과 별도로 측정할 수 있어야 한다.

---

#### NFR-14. 영상 표시 성능

모방 모드의 카메라 영상은 사용자가 손 인식 상태를 확인할 수 있는 수준으로 제공되어야 한다.

측정 기준:

- 웹 영상은 평균 15FPS 이상 표시를 목표로 한다.
- 영상 지연은 500ms 이하를 목표로 한다.
- 영상 송출 지연이 실제 ROS 2 손 명령 생성에 영향을 주어서는 안 된다.
- 영상이 끊겨도 Raspberry Pi의 안전 기능은 계속 동작해야 한다.

---

#### NFR-15. 내부망 관제·제어 웹 제어 안정성

내부망 관제·제어 웹에서 발생한 오류가 로봇 손의 비정상적인 동작으로 이어져서는 안 된다.

측정 기준:

- 웹에서 생성된 명령은 ROS 2로 전달되기 전에 형식과 범위를 검사해야 한다.
- 동일한 명령이 중복 전송되더라도 로봇 손이 비정상적으로 반복 동작하지 않아야 한다.
- 오래된 명령은 실행되지 않아야 한다.
- 연결이 끊긴 상태에서는 새로운 제어 명령을 생성하지 않아야 한다.
- 내부망 관제·제어 웹을 새로고침하거나 종료하더라도 모터가 임의로 움직이지 않아야 한다.

---

#### NFR-16. 내부망 관제·제어 웹 장애 독립성

내부망 관제·제어 웹 또는 해당 웹 서버의 장애가 로봇 손의 핵심 안전 기능에 영향을 주어서는 안 된다.

측정 기준:

- 내부망 관제·제어 웹 서버가 종료되어도 Raspberry Pi의 위치, 속도 및 전류 제한은 유지되어야 한다.
- 내부망 관제·제어 웹 서버가 종료되어도 통신 timeout과 안전 상태 전환이 동작해야 한다.
- 내부망 관제·제어 웹은 모터에 직접 명령을 전달하지 않아야 한다.
- 실제 모터 제어와 안전 판단은 Raspberry Pi에서 수행해야 한다.
- 웹 연결이 복구되더라도 자동으로 제어를 다시 시작하지 않아야 한다.

---

#### NFR-17. 사용성

처음 사용하는 사용자도 별도의 교육 없이 기본 기능을 구분하고 실행할 수 있어야 한다.

측정 기준:

- 모방 모드와 조작 모드를 명확하게 구분해야 한다.
- 현재 선택된 모드를 항상 화면에서 확인할 수 있어야 한다.
- 손 펴기, 주먹, 파지, 집기, 정지 버튼은 의미를 쉽게 이해할 수 있어야 한다.
- 정상, 대기, 경고, 오류 상태를 시각적으로 구분해야 한다.
- 오류 메시지는 오류 코드뿐만 아니라 사용자가 이해할 수 있는 설명을 포함해야 한다.

---

#### NFR-18. 화면 구성 및 가독성

내부망 관제·제어 웹 화면은 시연 환경에서 주요 상태를 빠르게 확인할 수 있도록 구성해야 한다.

측정 기준:

- 현재 모드, 로봇 연결 상태 및 안전 상태는 화면 상단에 고정하여 표시해야 한다.
- 주요 제어 버튼은 스크롤 없이 접근할 수 있어야 한다.
- 7논리축 값은 숫자와 게이지 또는 그래프 중 하나 이상의 방식으로 표시해야 한다.
- 경고와 오류 상태는 일반 상태보다 눈에 띄게 표시해야 한다.
- 지나치게 많은 원시 로그를 기본 화면에 표시하지 않아야 한다.
- 상세 모터 정보는 별도의 영역에서 확인할 수 있어야 한다.

---

#### NFR-19. 호환성

내부망 관제·제어 웹은 프로젝트에서 사용하는 주요 실행 환경에서 동일한 기능을 제공해야 한다.

측정 기준:

- 데스크톱 환경을 우선 지원해야 한다.
- 일반적인 노트북 해상도에서 화면 요소가 겹치지 않아야 한다.
- 화면 크기가 변경되어도 주요 버튼과 상태 정보가 잘리지 않아야 한다.

---

#### NFR-20. 내부망 관제·제어 웹 보안 및 접근 제한

내부망 관제·제어 웹은 프로젝트 전용 내부 네트워크에서만 로봇 손을 제어할 수 있도록 해야 한다.

측정 기준:

- 외부 인터넷에서 직접 로봇 손 제어 페이지에 접근할 수 없어야 한다.
- 프로젝트 전용 내부 네트워크를 사용해야 한다.
- 웹에서 전달되는 명령은 정의된 명령 형식만 허용해야 한다.
- 임의의 ROS 2 토픽 이름이나 모터 ID를 사용자가 입력할 수 없어야 한다.
- 사용자 입력값은 서버에서 다시 검증해야 한다.
- 웹페이지에 모터 통신 포트, 비밀번호 등 민감한 설정 정보를 노출하지 않아야 한다.

기존 명세서와 동일하게 내부망 관제·제어 웹의 복잡한 회원 인증과 외부 인터넷을 통한 로봇 원격 제어는 MVP에서 제외한다. EC2 데이터 포털의 조회·다운로드 기능과 업로더 인증은 이 제외 범위에 포함되지 않는다.

---

#### NFR-21. 유지보수성

내부망 관제·제어 웹 인터페이스는 화면 표시, ROS 2 연동 및 상태 관리 기능을 분리하여 구현해야 한다.

측정 기준:

- 모방 모드와 조작 모드 기능을 독립적인 화면 또는 컴포넌트로 분리해야 한다.
- ROS 2 메시지 송수신 기능을 화면 코드와 분리해야 한다.
- 명령 프리셋을 별도 설정 파일에서 관리할 수 있어야 한다.
- 오류 처리와 로그 기록 기능을 공통 모듈로 관리해야 한다.
- 기능 변경 시 로봇 모터 제어 코드를 직접 수정하지 않아도 되어야 한다.

---

#### NFR-22. 데이터 무결성 및 로그

웹에서 발생한 주요 제어와 오류 이벤트는 실험 결과를 추적할 수 있도록 기록해야 한다.

기록 대상:

- 모드 변경 시간
- 버튼 명령
- 데이터 기록 시작 및 종료 시간
- ROS 2 연결 및 해제 시간
- 손 검출 실패
- 모터 및 시스템 오류
- 비상정지와 제어 재개
- 파지 성공 또는 실패 결과

측정 기준:

- 모든 이벤트는 timestamp를 포함해야 한다.
- 웹 명령과 ROS 2 명령을 시간 기준으로 비교할 수 있어야 한다.
- 기록 실패가 로봇 제어 프로그램의 종료로 이어져서는 안 된다.
- 로그 파일이 무제한으로 증가하지 않도록 용량 또는 보관 기간을 설정해야 한다.
- 실험 종료 후 로그를 다시 확인할 수 있어야 한다.

---

#### NFR-23. 복구 가능성

일시적인 통신 오류 이후 시스템은 안전한 절차를 통해 복구될 수 있어야 한다.

측정 기준:

- 연결이 끊기면 내부망 관제·제어 웹 화면에 연결 끊김 상태를 표시해야 한다.
- 재연결을 주기적으로 시도하고 재시도 간격은 설정 파일에서 관리해야 한다.
- 연결이 복구되더라도 이전 명령을 다시 실행하지 않아야 한다.
- 사용자가 현재 상태를 확인하고 제어 재개를 선택해야 한다.
- 재연결 실패가 반복되면 명확한 오류 메시지를 제공해야 한다.

---

### 5.6 보안 요구사항

본 시스템의 로봇 제어 기능은 프로젝트 전용 내부 네트워크에서 사용하는 시제품이다. 내부망 관제·제어 웹의 회원 가입·로그인과 인터넷 기반 원격 제어는 MVP에서 제외한다. EC2 데이터 포털의 장치 인증 업로드와 로그인 없는 저장 데이터 조회·다운로드용 HTTPS 기능은 V6 MVP에 포함한다.

다음 기본 조건을 만족해야 한다.

- 외부 인터넷에서 직접 모터 명령을 전달하지 않는다.
- 로봇 제어는 프로젝트 전용 내부 네트워크를 사용한다.
- ROS_DOMAIN_ID를 팀 프로젝트에 맞게 설정한다.
- 모터 제어 노드는 지정된 형식의 명령만 처리한다.
- 외부 인터넷에 로봇 제어용 REST API와 ROS 2 Web Bridge를 제공하지 않는다.
- EC2 데이터 포털은 저장 데이터의 공개 GET 조회·다운로드와 장치 인증 업로드를 위한 HTTPS REST API만 제공해야 한다.
- EC2 REST API는 ROS 2 명령 토픽, 서비스 및 액션을 외부에 노출하지 않아야 한다.
- ROS 2 DDS Security 적용은 향후 확장 항목으로 분류한다.

---

### 5.7 EC2 데이터 포털 비기능 요구사항

#### NFR-24. 조회 응답 성능

- 일반적인 네트워크 환경에서 세션 목록과 상세 페이지는 3초 이내 표시를 목표로 한다.
- 세션 목록은 페이지 단위로 요청하여 전체 데이터를 한 번에 전달하지 않아야 한다.
- 대용량 시계열 데이터는 구간 조회, 샘플링 또는 다운샘플링을 적용할 수 있어야 한다.
- 다운로드 처리로 인해 일반 조회 API와 health API가 중단되지 않아야 한다.

#### NFR-25. 다운로드 무결성

- 다운로드 전에 파일 형식과 파일 크기를 사용자에게 표시해야 한다.
- 다운로드 중 오류가 발생한 부분 파일을 정상 파일로 처리하지 않아야 한다.
- 제공 파일에는 Session ID와 데이터 버전 또는 생성 시각을 포함해야 한다.
- checksum 제공은 Could 범위로 분류한다.
- 동일한 파일을 반복 다운로드해도 서버의 원본 데이터가 변경되지 않아야 한다.

#### NFR-26. 데이터 업로드 신뢰성 및 무결성

- 공개 데이터와 내부 원본 데이터는 동일한 Session ID를 사용해야 한다.
- 데이터 변환 전후의 timestamp 순서와 단위가 유지되어야 하며 저장·응답 시간은 UTC를 기준으로 해야 한다.
- 완료되지 않았거나 불완전한 세션은 기본적으로 업로드하지 않아야 한다.
- 같은 Session ID와 데이터 버전을 재전송해도 중복 세션을 만들지 않아야 한다.
- 데이터 변환 버전과 공개 데이터 스키마 버전을 기록해야 한다.
- 원본 rosbag2와 로컬 SQLite 데이터는 변환·업로드 과정에서 수정하거나 삭제하지 않아야 한다.

#### NFR-27. 인증 정보 및 공개 데이터 보호

- 공개 데이터 포털은 HTTPS를 사용해야 한다.
- 세션 조회·상세·파일 목록·다운로드 GET API는 로그인 없이 공개하고 읽기 전용으로 제공해야 한다.
- 업로드 API는 장치별 Bearer Token으로 인증된 로봇 측 업로더만 사용할 수 있어야 한다.
- 업로드 인증 정보와 운영 비밀정보는 환경 변수 또는 안전한 비밀정보 저장소에서 관리해야 한다.
- 인증 정보를 Git 저장소, 웹 화면 및 애플리케이션 로그에 노출하지 않아야 한다.
- 공개 데이터에는 카메라 원본 영상, 사용자 이름, 내부 IP 주소 및 민감한 서버 설정을 포함하지 않아야 한다.
- 다운로드 경로와 파일명을 사용자가 임의로 조작할 수 없어야 한다.
- EC2 데이터 포털에서는 로봇 제어 API를 제공하지 않아야 한다.

#### NFR-28. 내부 제어 시스템과의 장애 독립성

- EC2 서버가 중단되어도 내부망 관제·제어 웹과 ROS 2 로봇 제어는 정상적으로 동작해야 한다.
- 공개 데이터 업로드 실패가 Logger의 로컬 rosbag2 및 SQLite 저장을 방해해서는 안 된다.
- 데이터 변환기·업로더의 오류가 로봇 제어 프로세스를 종료시키지 않아야 한다.
- 내부 네트워크가 외부 인터넷에 연결되지 않은 경우에도 로봇 제어와 데이터 기록은 가능해야 한다.
- EC2 연결 복구 후 로봇의 이전 제어 모드나 명령을 자동으로 재실행하지 않아야 한다.

#### NFR-29. 저장 공간 및 지속성

- EC2 메타데이터 DB는 SQLite로 구현하고 EC2 영속 디렉터리에 저장해야 한다.
- JSON·CSV와 Could 범위의 rosbag2 파일은 `EC2_DATA_DIR` 아래에 저장해야 한다.
- Docker 컨테이너 또는 애플리케이션을 재시작해도 SQLite DB와 업로드 파일이 유지되어야 한다.
- 다운로드 파일이 무제한으로 누적되지 않도록 저장 용량과 보관 정책을 관리할 수 있어야 한다.
- 데이터 파일 크기, 생성 시각 및 저장 위치를 기록해야 한다.
- 공개 파일을 삭제하거나 숨겨도 로봇에 저장된 로컬 원본 데이터는 별도로 보존할 수 있어야 한다.
- AWS S3 등의 객체 저장소 전환은 데이터 규모가 증가한 이후 검토하며 MVP 범위에는 포함하지 않는다.

### 6.4 통신 인터페이스

- Jetson과 Raspberry Pi는 Wi-Fi 기반 ROS 2 DDS로 통신한다.
- ROS 2 배포판은 Humble로 통일한다.
- `command_manager`만 공식 `/thing/command`를 발행한다.
- `command_guard`를 통과한 `/thing/safe_target`만 모터 노드가 처리한다.
- 명령 콜백은 목표 도달까지 차단되지 않아야 한다.
- ControlMode와 SafetyState를 분리하고 SafetyState를 우선한다.
- 웹과 Web Bridge는 WebSocket JSON으로 통신한다.
- JSON의 세부 필드는 추후 확정한다.
- Jetson은 landmark overlay 영상을 MJPEG로 웹에 제공한다.
- MJPEG와 웹 장애는 로봇 제어 및 안전 기능에 영향을 주지 않아야 한다.
- 카메라는 항상 실행한다.
- 녹화 버튼은 카메라 실행이 아니라 rosbag2 기록만 제어한다.
- 카메라 영상 파일은 저장하지 않는다.
- rosbag2에는 MediaPipe landmark를 반드시 포함한다.
- 그 외 녹화 토픽은 추후 확정한다.
- 연결 복구 후 이전 모드나 명령을 자동으로 재개하지 않는다.
- 데이터 변환기·업로더는 완료된 로컬 세션을 인증된 HTTPS 요청으로 EC2에 전송한다.
- EC2 서버는 ROS 2 DDS 네트워크에 참여하지 않는다.
- EC2에서 내부 ROS 2 네트워크로 향하는 제어 경로를 제공하지 않는다.
- EC2 업로드 실패와 외부 인터넷 단절은 내부 ROS 2 제어 및 로컬 기록에 영향을 주지 않아야 한다.

---

### 6.5 EC2 데이터 포털 인터페이스

#### 사용자 인터페이스

외부 데이터 조회 사용자는 별도 로그인 없이 EC2 데이터 포털에서 다음 기능을 사용할 수 있어야 한다.

- 완료 세션 목록 조회
- 날짜, Session ID 및 성공·실패 결과 검색·필터링
- 세션 상세 메타데이터 확인
- 7논리축 및 모터 상태 데이터의 숫자·표·그래프 확인
- JSON·CSV 파일 형식과 크기 확인
- 세션별 JSON·CSV 다운로드
- rosbag2 기능이 구현된 경우 압축 파일 다운로드

EC2 사용자 인터페이스에는 로봇 제어, 모드 변경, 비상정지 해제 및 녹화 시작·종료 기능을 제공하지 않는다.

#### HTTPS REST API

```
POST /api/v1/uploads/sessions
GET  /api/v1/sessions
GET  /api/v1/sessions/{session_id}
GET  /api/v1/sessions/{session_id}/data
GET  /api/v1/sessions/{session_id}/files
GET  /api/v1/sessions/{session_id}/download/{file_id}
GET  /health
```

- `POST /api/v1/uploads/sessions`는 `Authorization: Bearer <device-token>` 헤더가 있는 로봇 측 업로더만 호출할 수 있다.
- 모든 `GET` API는 별도 로그인 없이 공개하며 읽기 전용으로 제공한다.
- 공개 조회 경로에는 데이터 생성·수정·삭제용 `POST`, `PUT`, `PATCH`, `DELETE`를 제공하지 않는다.
- API 응답 시간과 데이터의 timestamp는 UTC를 기준으로 한다.
- API 응답은 JSON 형식을 사용한다.
- 대용량 파일은 일반 API 응답 본문에 포함하지 않고 별도 다운로드 응답으로 제공한다.
- EC2 API는 ROS 2 토픽·서비스·액션 및 내부 Web Bridge를 외부에 노출하지 않는다.

#### 업로드 요청 계약

업로드 API는 `multipart/form-data`를 사용하며 다음 항목을 전달한다.

- 필수: 세션 메타데이터 JSON
- 필수: HandCommand CSV
- 필수: MotorStatus CSV
- Could: rosbag2 압축 파일
- 필수 메타데이터: Session ID, 단일 Robot ID, 데이터 버전, 스키마 버전, UTC 시작·종료 시각, 성공·실패 결과

처리 결과는 다음 기준을 따른다.

- 신규 세션 저장 성공: `201 Created`
- 같은 Session ID와 데이터 버전 재전송: 중복을 만들지 않고 기존 세션을 반환하는 `200 OK`
- Bearer Token 누락 또는 오류: `401 Unauthorized`
- 파일 크기 제한 초과: `413 Payload Too Large`
- 필수 파일·필드 또는 스키마 오류: `422 Unprocessable Entity`

#### 저장 계약

- EC2 메타데이터 DB는 SQLite를 사용한다.
- 영속 저장소 환경 변수는 `EC2_DATA_DIR`로 정의하고 기본값은 `/var/lib/thing-data`로 한다.
- SQLite 파일은 `/var/lib/thing-data/db.sqlite3`에 저장한다.
- 세션 파일은 `/var/lib/thing-data/sessions/{session_id}/` 아래에 저장한다.
- MVP는 단일 로봇만 지원하며 장치별 Bearer Token은 해당 로봇 업로더 한 대에 발급한다.
- Docker 재배포 또는 컨테이너 재시작 뒤에도 DB와 파일이 유지되어야 한다.

#### 다운로드 파일 인터페이스

필수 제공 파일:

- `session_{session_id}_metadata.json`
- `session_{session_id}_hand_command.csv`
- `session_{session_id}_motor_status.csv`
- 데이터 스키마 또는 `README_schema.md`

Could 제공 파일:

- `session_{session_id}_rosbag2.zip`

파일에는 Session ID, UTC timestamp, 단위, 데이터 타입, 스키마 버전 및 결측값 처리 기준을 포함하거나 별도 스키마 문서로 제공해야 한다. 카메라 영상은 파일 인터페이스에 포함하지 않는다.

## 7. 시스템 제약사항

### 7.1 하드웨어 제약사항

- 각 손가락의 여러 관절은 하나의 모터로 함께 구동된다.
- 모터 엔코더값은 실제 손가락 관절각과 동일하지 않다.
- 물체 접촉 후 모터 이동량 일부는 스프링 신장으로 사용될 수 있다.
- 같은 텐던 힘을 내는 데 필요한 모터 토크와 전류는 스풀 반지름에 따라 달라진다.
- 손가락과 손바닥은 3D 프린팅 공차의 영향을 받는다.
- 텐던의 늘어남, 마찰 및 초기장력 변화가 반복 정확도에 영향을 줄 수 있다.
- 모터 7개의 동시 구동을 고려한 전원 공급 장치가 필요하다.

---

### 7.2 소프트웨어 제약사항

- Jetson에서는 Ubuntu 22.04와 ROS 2 Humble을 사용한다.
- Jetson과 Raspberry Pi의 애플리케이션 실행 환경은 Docker 컨테이너로 구성한다.
- 각 장치의 기능은 독립된 컨테이너 단위로 배포하며, 동일한 실행 환경을 재현할 수 있도록 Docker 이미지와 실행 설정을 버전 관리해야 한다.
- 장치별 컨테이너 실행 설정을 통해 카메라·U2D2 등 하드웨어 인터페이스, ROS 2 네트워크, 데이터 볼륨 및 환경 변수를 관리해야 한다.
- 컨테이너 장애가 호스트 운영체제 전체의 비정상 종료로 이어지지 않도록 구성해야 한다.
- MediaPipe 손 검출 성능은 조명, 손 가림 및 카메라 각도의 영향을 받는다.
- ROBOTIS DYNAMIXEL SDK 기반으로 모터 노드를 구현한다.
- MVP에서는 관절 상태 추정을 위한 학습 모델을 사용하지 않는다.

---

### 7.3 네트워크 제약사항

- Wi-Fi 지연과 패킷 손실이 발생할 수 있다.
- 네트워크 단절과 관계없이 Raspberry Pi가 독립적으로 안전 기능을 수행해야 한다.
- 오래된 명령을 순차적으로 실행하지 않고 가장 최신의 유효한 명령을 사용해야 한다.
- Jetson과 Raspberry Pi는 동일한 ROS_DOMAIN_ID와 호환되는 DDS 설정을 사용해야 한다.

---

### 7.4 설계 및 구현 제약사항

- 전체 개발 기간은 3주이다.
- 첫 번째 주에 손가락 텐던 구동을 우선 검증해야 한다.
- 일반 손가락보다 엄지를 우선적으로 검증해야 한다.
- 하드웨어 제작과 소프트웨어 개발은 병렬로 진행해야 한다.
- 모든 주요 기능은 최종 주 이전에 최소 한 번 이상 통합 시험을 수행해야 한다.

---

### 7.5 전제조건 및 의존성

- 서보와 USB 버스 어댑터가 정상적으로 통신해야 한다.
- 모터의 위치와 상태값을 읽을 수 있어야 한다.
- 3D 프린터를 프로젝트 기간 동안 사용할 수 있어야 한다.
- 모터 전원 공급 장치가 7개 모터의 순간 전류를 감당할 수 있어야 한다.
- 테스트 중 사용자의 손이 카메라 화면에서 크게 가려지지 않아야 한다.
- 한 번에 한 사용자의 오른손만 제어 대상으로 한다.
- 물체는 사전에 지정된 위치와 방향으로 배치한다.

---

### 7.6 EC2 및 데이터 업로드 제약사항

- EC2 데이터 포털은 AWS EC2의 Docker 실행 환경에서 운영한다.
- MVP는 단일 로봇의 완료 세션만 지원한다.
- EC2 서버는 내부 ROS 2 DDS 네트워크에 참여하지 않는다.
- 외부 사용자는 별도 로그인 없이 완료되어 업로드된 데이터만 공개 GET으로 조회·다운로드할 수 있다.
- 로봇 측 데이터 업로더는 장치별 Bearer Token을 사용해 HTTPS로만 업로드한다.
- 로봇 측 데이터 업로더는 일반 Python 애플리케이션 또는 독립 모듈로 구현할 수 있으며 ROS 노드일 필요는 없다.
- 업로더가 ROS 2 상태를 사용해야 하는 경우에도 EC2와는 HTTPS로만 통신한다.
- EC2 메타데이터는 SQLite에 저장하고 JSON·CSV 파일은 EC2 영속 디렉터리에 저장한다.
- 모든 저장·표시·API 응답 시간은 UTC를 기준으로 한다.
- rosbag2 또는 별도 CSV·JSON 기록 데이터가 없으면 EC2에서 상세 시계열 데이터를 제공할 수 없다.
- JSON과 CSV 다운로드는 필수이며 원본 rosbag2 다운로드는 Could 범위다.
- 대용량 rosbag2 파일은 EC2 저장 공간, 업로드 시간 및 네트워크 비용에 영향을 줄 수 있다.
- 외부 인터넷 장애가 내부 로봇 제어와 로컬 데이터 기록에 영향을 주어서는 안 된다.
- 공개 데이터 업로드는 로봇 실시간 제어보다 낮은 우선순위로 처리해야 한다.
- 데이터 업로드 전에 파일 크기, 형식, Session ID, 스키마 및 민감 정보 포함 여부를 검증해야 한다.
- 표시되는 각도는 모터 엔코더 기반 모터축 각도이며 실제 손가락 관절별 측정 각도가 아니다.
- 카메라 영상은 저장·업로드·다운로드하지 않는다.

- 데이터 기록 및 재생 시험
- command manager가 현재 모드의 입력원 하나만 선택하는지 시험
- command guard가 오래된 명령, NaN, 범위 초과 및 잘못된 sequence를 거부하는지 시험
- 이전 목표 도달 전 새로운 목표를 정상적으로 추종하는지 시험
- SafetyState가 ControlMode보다 우선하는지 시험
- owner 충돌과 lease 만료 시 DISABLED 전환 시험
- 웹 재연결 후 이전 명령이 자동 실행되지 않는지 시험
- MJPEG 중단이 로봇 제어에 영향을 주지 않는지 시험
- MIMIC 외 모드에서 녹화 요청이 거부되는지 시험
- 녹화 중 모드 변경이 거부되는지 시험
- rosbag2에 MediaPipe landmark가 기록되는지 시험
- rosbag2 또는 SQLite 초기화 실패 시 녹화 전체가 실패하는지 시험
- 성공·실패 판정 전 다음 녹화가 거부되는지 시험
- 완료 세션의 rosbag2 및 SQLite 데이터를 JSON·CSV로 변환하는지 시험
- 장치별 Bearer Token HTTPS를 통해 EC2에 세션을 업로드하는지 시험
- 동일한 Session ID 재업로드 시 중복 데이터가 생성되지 않는지 시험
- 업로드 실패 시 로컬 원본이 보존되고 재시도 가능한지 시험
- EC2 서버 종료 시 내부 ROS 2 제어와 Logger가 정상 동작하는지 시험
- EC2 서버가 ROS 2 DDS 네트워크에 참여하지 않는지 시험
- EC2 웹에서 ROS 2 제어 토픽·서비스·액션에 접근할 수 없는지 시험
- EC2 데이터에 카메라 영상과 민감 정보가 포함되지 않는지 시험

### 8.3 검수 기준

프로젝트는 다음 조건을 모두 만족했을 때 MVP가 완료된 것으로 판단한다.

- Must 우선순위 기능 요구사항이 모두 구현되었다.
- 실제 손의 편 손과 주먹 자세를 로봇 손이 모방한다.
- 엄지 굽힘과 대립 동작이 구분되어 제어된다.
- 원통형 물체를 파지할 수 있다.
- 가벼운 물체를 집을 수 있다.
- 가벼운 물체 2종을 각각 10회 시험하여 7회 이상 성공한다.
- ROS 2 무선 명령 전달이 정상적으로 동작한다.
- 명령 단절 시 설정된 안전 동작이 수행된다.
- 물리적 비상정지로 모터 전원을 차단할 수 있다.
- 치명적인 기구 파손이나 텐던 이탈 없이 시연을 완료한다.
- 테스트 결과, 성공률 및 주요 제한사항이 문서화되어 있다.
- 완료된 실험 세션을 장치별 Bearer Token이 포함된 HTTPS 요청으로 EC2에 업로드할 수 있다.
- 외부 사용자가 별도 로그인 없이 EC2 데이터 포털의 공개 GET을 통해 세션 목록과 상세 데이터를 조회할 수 있다.
- 세션별 JSON과 CSV 파일을 필수로 다운로드할 수 있고, rosbag2 다운로드는 Could 범위로 구분되어 있다.
- EC2 SQLite DB와 영속 파일 디렉터리가 Docker 재시작 뒤에도 유지된다.
- Docker Compose로 EC2 서비스 전체를 재현 가능하게 배포하고 health를 확인할 수 있다.
- 모든 저장·표시·API 응답 시간이 UTC 기준임이 검증된다.
- 표시되는 모터축 각도와 실제 손가락 관절각의 차이가 명시되어 있다.
- EC2 데이터 포털에서는 로봇 제어, 모드 변경, 녹화 제어 및 비상정지 해제를 수행할 수 없다.
- EC2 서버가 중단되어도 내부 로봇 제어와 로컬 데이터 기록이 정상적으로 동작한다.
- 카메라 영상이 저장·업로드·다운로드되지 않는다.

### 8.4 완료 정의

각 Jira 스토리는 다음 조건을 모두 만족할 때 완료 처리한다.

- 구현 코드 또는 CAD 파일이 GitLab 저장소에 반영되었다.
- 실제 하드웨어 또는 목표 실행 환경에서 테스트되었다.
- 인수 조건을 충족했다.
- 테스트 영상, 사진 또는 로그가 Jira에 첨부되었다.
- 발견된 문제와 제한사항이 기록되었다.
- 팀원 한 명 이상의 검토를 받았다.
- 관련 요구사항 ID와 테스트 결과가 연결되었다.
- EC2 관련 스토리는 업로드 API, 조회 API, 다운로드 파일, 배포 환경 또는 조회 화면 중 담당 결과물이 실제 목표 환경에서 검증되었다.
- 데이터 스키마, 단위, 인증 정보 관리 방식 및 장애 시 동작이 문서화되었다.
