## 1. 프로젝트 개요

### 1.1 프로젝트 배경 및 목적

본 프로젝트는 카메라로 사용자의 오른손 자세를 인식하고, 텐던 방식의 3D 프린팅 로봇 손이 해당 자세를 실시간으로 따라 움직이도록 구현하는 것을 목적으로 한다. 각 손가락의 여러 관절을 하나의 모터로 함께 구동하는 언더액추에이티드 구조를 적용해 가격·무게·제작 난도를 낮추고, 제한된 기간 안에 반복 가능한 파지 성능을 검증한다.

현재 MVP의 핵심 시연 범위는 다음과 같다.

- 편 손·주먹 및 엄지 굽힘·대립·벌림을 포함한 7논리축 실시간 모방
- 원통형 물체 파지와 엄지–검지 집기
    - ROS 2 기반 내부망 명령 전달과 Raspberry Pi의 독립 안전 제어
- MediaPipe landmark, HandCommand, MotorStatus 및 실험 결과의 로컬 rosbag2 기록
- 내부망 관제·제어 웹의 MIMIC·MANUAL 운용
- EC2 데이터 포털의 완료 세션 조회와 metadata JSON·HandCommand CSV·MotorStatus CSV, LandMark JSON 다운로드

EC2 데이터 포털은 저장된 데이터의 공개 읽기 전용 서비스이며 로봇 제어 경로를 제공하지 않는다. 장기적인 학습 데이터·모델 사업화는 현재 MVP 범위에 포함하지 않는다.

프로젝트 전체 계획은 3주이며, 이 문서를 동결하는 시점의 잔여 개발 기간은 2주다. Must 기능의 통합 시연을 우선하고 Should·Could 기능은 Must 검수에 영향을 주지 않는 범위에서만 진행한다.

### 1.2 MVP

1. **로봇 손 구동**
    - 제작 범위
        - 3D 모델링
        - 관절 연결
        - 텐던 연결
        - 모터 연결
    - 검증 동작
        - 손 펴기와 쥐기
        - 원통형 물체 파지
        - 엄지–검지 집기
        - 가벼운 물체 2종을 각각 10회 시험하여 7회 이상 파지
2. **실제 손동작 모방**
    - MediaPipe 기반 손 landmark 검출
    - 손가락 굽힘과 엄지 대립 및 벌림 정도 계산
    - 모터에 전달
    - 7논리축을 7개 물리 모터에 1:1로 연결한다
    - 손동작 모방을 `camera_node → mediapipe_node → hand_target_node`로 구체화
3. **ROS 2 패키지**
    - ROS 2 토픽·노드·서비스·액션 인터페이스 정의 및 구현
    - ROS 2를 통한 무선 명령 전달
    - ROS 2를 이용한 모터 동작
4. **완성형 웹 사용자 인터페이스**
    - 모방 모드에서 실시간 카메라 영상과 손 인식 결과 모니터링
    - 조작 모드에서 웹 버튼으로 로봇 손 제어
    - 모방 모드와 조작 모드는 별도 화면 또는 탭으로 구성
5. **EC2 기반 로봇 데이터 포털**
    - 기존 내부망 관제·제어 웹과 별도의 웹사이트로 구성한다.
    - 완료된 실험 세션 목록을 조회할 수 있다.
    - 세션별 HandCommand와 MotorStatus 데이터를 확인할 수 있다.
    - 세션 메타데이터 JSON과 HandCommand·MotorStatus CSV·LandMark JSON을 모두 다운로드할 수 있다.
    - 원본 rosbag2 업로드·다운로드는 2주 MVP에서 제외하고 Post-MVP Could로 분류한다.
    - EC2 웹에서는 로봇 제어, 녹화 시작·종료 및 모드 변경 기능을 제공하지 않는다.

#### MVP 제외 범위 - 향후 확장 기능

- 관절 각 선형 회귀 AI 모델 - Could
- VLA 기반 자율 조작
- Imitation Learning 모델 학습
- Isaac Sim 및 Isaac Lab 연동
- 손가락 관절별 독립 다축 제어
- 모든 관절의 실제 각도 측정
- 손가락 전체 촉각 센서
- 물체 종류 자동 인식
- 물체 위치 자동 탐색
- 클라우드 또는 외부 인터넷을 통한 로봇 원격 제어
- 산업용 수준의 방수·방진·내구성 확보
- 축–모터 결합·공유 구동은 MVP에서 사용하지 않는다

EC2 기반 데이터 조회 및 다운로드 기능은 MVP에 포함한다. 단, 외부 인터넷에서 로봇으로 명령을 전달하는 기능은 MVP 및 EC2 배포 범위에서 제외한다.

향후 학습 데이터 활용을 위해 MediaPipe landmark, 목표 명령, 모터 엔코더값 및 파지 성공 여부는 MVP에서도 저장한다.

### 1.3 제품 및 시스템 기능 요약

시스템은 손동작 인식, 명령 중재·검증, 모터·안전 제어, 실험 기록·업로드의 네 영역으로 구성한다. 상세 배치는 4장, ROS 2 계약은 6.3절, EC2 계약은 6.5절을 단일 기준으로 사용한다.

1. **내부망 관제·제어 웹**
    - 프로젝트 내부 네트워크에서 MIMIC·MANUAL 모드, MJPEG 영상, 손 검출, 7논리축 목표, 모터·안전·기록 상태를 제공한다.
    - 제어 요청은 Web Bridge와 검증된 ROS 2 인터페이스를 거치며 모터에 직접 접근하지 않는다.
    - 기록 시작·종료와 성공·실패 판정을 요청한다.
2. **EC2 데이터 포털**
    - 외부 인터넷에서 완료·판정된 단일 로봇 세션을 로그인 없이 조회한다.
    - metadata JSON, HandCommand CSV, MotorStatus CSV, LandMark JSON 정확히 네 파일을 표시·다운로드한다.
    - ControlState·SafetyState 변경 이력, 영상과 rosbag2는 MVP 공개 대상에서 제외한다.
    - 로봇 제어, 모드 변경, 기록 제어, Safety Reset 및 ROS 2 DDS 참여를 금지한다.

로봇에는 별도의 애플리케이션 SQLite, `session_state.json` 및 영구 upload spool을 두지 않는다. rosbag2가 로컬 원본이며, 정상 종료와 판정 완료 직후 `thing-logger`의 exporter가 정확히 세 파일을 임시 디렉터리에 생성·검증한다. 격리된 uploader는 rosbag2를 읽지 않고 완료된 세 파일만 받아 Bearer Token HTTPS로 EC2 Django 업로드 API에 즉시 전송한다. EC2 Django가 검증한 세션 정보는 EC2 SQLite에, 다운로드 파일은 `EC2_DATA_DIR`에 저장하며 이 둘이 공개 READY 데이터의 최종 기준이다. Laptop에서 실행하는 내부망 관제·제어 웹은 Web Bridge의 WebSocket과 Jetson MJPEG로 ROS 2 실시간 데이터를 받고, EC2 포털은 Django의 공개 GET API로 저장된 데이터만 조회한다.

MJPEG가 `/thing/image_raw`와 `/thing/landmarks`를 구독해 생성

#### 내부망 웹 기반 운용 흐름

- 카메라와 Vision Node는 기록 여부와 관계없이 계속 동작하며 원본 영상은 저장하지 않는다.
- MIMIC은 검출된 손으로 7논리축 명령을 생성하고 MANUAL은 사전 정의 자세를 실행한다.
- Raspberry Pi는 활성 mode·owner와 안전 상태에 맞는 입력 하나만 선택하고 유효성·범위·속도를 검증한다.
- 기록은 MIMIC에서만 허용하며 기록 중 모드 변경을 거부한다.

#### ROS 2 통합 실행 및 수동 시험

- 운영자는 장치별 실행 절차로 Laptop 내부 제어 웹, Jetson과 Raspberry Pi 스택을 시작한다.
- 필요 시 `teleop_keyboard`로 각 축을 시험한다.
- 편 손·주먹·파지·집기는 Must이며 가위바위보·카운트다운 Sequence는 Could다.

### 1.5 개발 환경

#### 1.5.1 하드웨어 환경

**현재 보유 장비**

- 3D 프린팅 로봇 손, 지름 2mm 철심과 텐던 소재
- U2D2 3개와 U2D2 Power Hub Board 3개
- DYNAMIXEL XL330-M288-T 8개: 활성 구동 7개, 예비 1개

**개발·통합 장비**

- Laptop, RGB 카메라, Jetson Orin Nano, Raspberry Pi 5
- 7개 모터의 순간 전류를 감당하는 별도 전원 공급 장치
- 스프링, 나일론선 및 물리적 E-Stop 주접점·NC 보조접점 회로

#### 1.5.2 소프트웨어 환경

- Jetson: JetPack 6.2·Ubuntu 22.04, Docker Engine. 비전·MJPEG·Web Bridge 이미지를 버전 관리된 `docker run` 스크립트로 실행하며 Docker Compose를 사용하지 않는다.
- Raspberry Pi: Ubuntu 24.04·Docker Engine. `docker compose up -d`를 유일한 표준 시작 방식으로 사용한다.
- Laptop: 내부망 제어 웹의 `web/internal-control/frontend` Vite+React를 native Node.js 환경에서 실행한다. Docker를 사용하지 않으며 브라우저는 Jetson Web Bridge WebSocket과 MJPEG에 내부망으로만 연결한다.
- EC2: Docker와 Compose를 사용하지 않는다. `web/ec2-portal/frontend`의 React 정적 빌드를 Nginx가 제공하고 `web/ec2-portal/backend`의 Django REST API·Gunicorn을 Python 가상환경과 systemd 서비스로 실행한다.
- 공통: ROS 2 Humble, C++·Python·JavaScript, OpenCV, MediaPipe, DYNAMIXEL SDK, rosbag2
- 내부망 웹: Laptop Vite+React, Jetson Django·Web Bridge WebSocket·MJPEG
- EC2 포털: Vite+React, Django REST API, Nginx, Gunicorn, HTTPS
- 로봇 로컬 저장: `ROBOT_DATA_DIR=/var/lib/thing-robot-data` 아래 rosbag2 원본과 업로드 시점에만 생성하는 임시 세 파일. 별도 애플리케이션 SQLite·`session_state.json`·영구 spool은 사용하지 않음
- EC2 저장: SQLite `/var/lib/thing-data/db.sqlite3`와 `EC2_DATA_DIR` 파일 디렉터리
- 데이터 계약: 단일 로봇, UTC, `schema_version=1`, `data_version=1`, 공개 파일 정확히 세 개
- VCS/업무 관리: Git·GitLab, Jira, Notion

## 2. 주요 사용 시나리오

### UC-01-01. 실시간 손동작 모방(MIMIC 모드)

1. 사용자가 카메라 앞에 손을 위치시킨다.
2. 시스템이 손 landmark를 검출한다.
3. 시스템이 손가락별 굽힘값과 엄지 대립 및 벌림값을 계산한다.
4. 7논리축 목표값이 Raspberry Pi로 전달된다.
5. 로봇 손이 사용자의 손 자세를 따라 움직인다.
6. 카메라 프레임→landmark→7축→command manager 순서로 단계 수정

### UC-01-02. 웹 명령 기반 로봇 손 조작(MANUAL 모드)

1. 사용자가 내부망 관제·제어 웹에서 명령을 선택한다.
2. 7논리축 목표값이 Raspberry Pi로 전달된다.
3. 로봇 손이 전달된 목표값에 따라 움직인다.

### UC-02-01. 원통형 물체 파지(MIMIC 모드)

1. 원통형 물체를 로봇 손의 파지 영역에 배치한다.
2. 사용자가 손을 오므린다.
3. 로봇 손가락이 물체와 접촉한다.
4. 직렬 스프링이 추가 모터 이동을 흡수하며 물체를 누른다.
5. 로봇 손이 물체를 최소 3초 이상 유지한다.

### UC-02-02. 원통형 물체 파지(MANUAL 모드)

1. 사용자가 MANUAL 모드에서 원통형 물체 파지 명령을 선택한다.
2. 시스템이 사전에 정의된 7논리축 목표값을 생성한다.
3. Raspberry Pi가 명령의 유효성과 안전 상태를 검사한다.
4. 로봇 손가락이 원통형 물체를 감싸도록 움직인다.
5. 로봇 손이 물체를 최소 3초 이상 유지한다.

### UC-03. 엄지–검지 집기

1. 가벼운 소형 물체를 엄지와 검지의 집기 영역에 배치한다.
2. 사용자가 MIMIC 모드에서 집기 동작을 수행하거나 MANUAL 모드에서 집기 명령을 선택한다.
3. 시스템이 엄지 굽힘·대립축과 검지 굽힘축의 목표값을 생성한다.
4. 엄지 끝과 검지 끝 또는 검지 측면이 물체에 접촉한다.
5. 로봇 손이 물체를 최소 3초 이상 유지한다.

> **사용 사례 번호 변경 기록:** 기존 UC-04(로컬 데이터 기록)는 기록부터 공개 조회까지의 단일 흐름을 만들기 위해 폐기했으며 이력 추적을 위해 번호를 재사용하지 않는다. 기존 UC-07(EC2 업로드)과 UC-08(EC2 조회·다운로드)은 각각 아래 UC-05의 B와 C로 통합했다.

### UC-05. 실험 데이터 기록·직접 업로드·조회 및 다운로드

#### A. 로컬 기록

1. 사용자가 내부망 웹의 MIMIC 모드에서 기록 시작을 요청한다.
2. Logger가 0이 아닌 고유 `uint64` Session ID를 생성하고 rosbag2 기록을 시작한다. 활성 세션 상태는 실행 중 메모리와 RecordingState로만 관리한다.
3. Logger는 landmark, 최종 HandCommand, MotorStatus, ControlState, SafetyState와 기록 상태를 rosbag2에 저장하며 카메라 원본 영상은 저장하지 않는다.
4. 정상 종료 후 rosbag2를 닫고 실행 중 메모리에서 결과 판정을 기다린다. 사용자가 SUCCESS 또는 FAILURE를 판정하기 전에는 다음 정상 기록을 시작할 수 없다.
5. 안전 이벤트나 프로세스 종료로 중단된 rosbag2는 남기지 않는다.

#### B. EC2 직접 업로드

1. 판정 완료 직후 `thing-logger`의 exporter가 rosbag2를 읽어 metadata JSON, HandCommand CSV, MotorStatus CSV, LandMark JSON 를 세션별 임시 디렉터리에 생성한다.
2. exporter는 세 파일을 `.part`로 작성하고 schema·행 수·SHA-256을 검증한 뒤 최종 파일명으로 rename하고, `exported_at`을 제외한 고정 `content_digest`를 계산한다.
3. exporter는 공유 임시 디렉터리의 완료된 세 파일 경로와 `content_digest`만 private Unix socket으로 격리된 uploader에 전달한다. uploader는 rosbag2에 접근하지 않는다.
4. uploader는 완료된 세 파일만 장치 Bearer Token과 HTTPS로 EC2 Django 업로드 API에 즉시 비동기 전송한다.
5. EC2는 STAGING에서 검증한 뒤 파일 디렉터리 이동과 SQLite 상태 전이로 READY만 공개한다.
6. `200`·`201` 응답의 `content_digest`가 요청값과 일치하면 exporter가 로봇의 임시 세 파일을 삭제한다. rosbag2 보존 정책은 별도로 적용한다.
7. 업로드 실패는 제어·안전·기록을 막지 않고 진단 로그에 남긴 뒤 임시 세 파일을 정리한다. 운영자는 `ros2 run thing_logger reupload_session --bag <bag_path> --result SUCCESS|FAILURE`로 보존된 rosbag2에서 세 파일을 다시 생성해 같은 경로로 수동 재업로드한다.
8. 영구 대기열과 인터넷 단절 자동 복구는 MVP 범위에서 제외하며 프로세스 재시작 뒤 실패 작업을 자동 재개하지 않는다.

> 여기서 “바로 업로드”는 기록 중 실시간 HTTP 전송이 아니라 **정상 종료와 판정 직후 시작하는 비동기 업로드**를 뜻한다.
> 

#### C. 공개 조회·다운로드

1. 외부 사용자는 로그인 없이 READY 세션 목록과 상세를 조회한다.
2. 기본 MVP는 Session ID·UTC 시각·결과와 7논리축·모터 데이터를 표 또는 기본 그래프로 확인한다.
3. 사용자는 metadata JSON, HandCommand CSV, MotorStatus CSV, LandMark JSON 정확히 세 파일을 다운로드한다.
4. EC2에서는 로봇 제어, 모드 변경, 기록 제어, Safety Reset과 rosbag2·상태 이력 공개를 제공하지 않는다.

표시 각도는 DYNAMIXEL encoder 기반 모터축 각도이며 실제 손가락 관절각이 아니다.

### UC-06. ROS 2 시스템 실행

1. 사용자가 Laptop의 내부 제어 웹 Vite 실행 명령, Jetson의 `docker run` 스크립트와 Raspberry Pi의 `docker compose up -d`를 실행한다.
2. Laptop은 `web/internal-control/frontend`의 React 화면을 제공하고, Jetson 컨테이너는 카메라·MediaPipe·MJPEG·Web Bridge를, Raspberry Pi 컨테이너는 manager·guard·safety·DYNAMIXEL·Logger·exporter와 격리된 uploader를 시작한다.
3. 모든 제어 노드는 이전 상태를 폐기하고 INIT에서 시작한다.
4. 사용자가 Laptop의 내부망 관제·제어 웹 또는 로컬 프로그램에서 제어 모드를 선택한다.
5. command manager가 현재 제어 모드와 제어권에 맞는 입력원 하나를 선택한다.
6. command guard가 선택된 명령의 timestamp, 범위, 속도 및 안전 상태를 검사한다.
7. 검증된 목표만 DYNAMIXEL 제어 노드에 전달한다.
8. 모터 상태, 제어 모드, 안전 상태 및 진단 정보를 ROS 2 토픽으로 발행하고 Jetson Web Bridge가 6.4절의 WebSocket snapshot으로 Laptop에 전달한다.
9. Jetson vision 실행 노드를 `camera_node`, `mediapipe_node`, `hand_target_node`, `mjpeg_streamer`, `web_bridge_node`

제어 모드는 다음과 같이 구분한다.

- `DISABLED`: 일반 명령 비활성화
- `MIMIC`: MediaPipe 기반 실시간 손동작 모방
- `MANUAL`: 내부망 웹에서 Gesture 서비스와 Sequence 액션 실행
- `TELEOP`: 로컬 키보드 기반 개별축 조작

내부망 관제·제어 웹은 MIMIC과 MANUAL 모드 모두를 관제할 수 있다. 데이터 기록은 MIMIC 모드에서만 허용하며 기록 중에는 제어 모드를 변경할 수 없다.

## 3. 기능 요구사항

우선순위는 다음과 같이 구분한다.

- **Must:** 남은 2주 안에 통합·검수까지 반드시 완료할 기능
- **Should:** Must가 통과한 뒤 구현하며 단순화하거나 다음 스프린트로 이월할 수 있는 기능
- **Could:** 이번 2주 MVP 완료 조건에서 제외하고 시간이 남을 때만 진행할 기능

### 3.1 손 자세 인식

#### FR-01. 손 landmark 검출

**우선순위: Must**

시스템은 RGB 카메라에서 한 사용자의 오른손과 MediaPipe 21개 landmark를 검출해야 한다.

인수 조건:

- `HandLandmarks.detected`, `confidence`, `handedness`를 develop 인터페이스 그대로 발행한다.
- MIMIC 유효 기준은 `detected=true`, 오른손, `confidence>=0.70`이다.
- 손 미검출 또는 낮은 신뢰도가 150ms 연속되면 MIMIC HandCommand 발행을 중단하고 hand-loss latch를 설정한다.
- 명령 중단 뒤 FR-35의 300ms HOLD, 총 1000ms SAFE 정책이 동작해야 하며 미검출값을 새 정상 명령으로 대체하지 않아야 한다.
- 재검출은 위 유효 조건이 300ms 연속 유지되어야 인정한다. 재검출은 복구 조건 확인일 뿐 이전 명령이나 제어를 자동 재개하거나 즉시 latch를 해제하지 않는다.
- 이후 복구는 현재 SafetyState에 따라 FR-35만을 따른다. HOLD에서는 명시적 STOP 후 READY 전환과 MIMIC·owner 재획득이 필요하고, SAFE·FAULT·ESTOP에서는 원인 해소·안정 시간·`/thing/reset_safety`·INIT 재검사·READY 전환 뒤 MIMIC·owner를 새로 획득해야 한다.
- 모든 경로에서 활성화 이후 생성된 새로운 HandCommand만 실행하며 이전 command, Gesture, Sequence 및 recording을 자동 재개하지 않는다.
- 웹은 FR-27에 따라 미검출, latch, 현재 안전 상태와 필요한 복구 경로를 구분해 표시해야 한다.
- landmark overlay 품질 개선과 원시 좌표 상세 표시는 Should다.
- `camera_node`, `mediapipe_node`, `hand_target_node`
- 미검출 landmark 좌표는 유효값으로 사용하지 않음

#### FR-02. 손가락 굽힘값 계산

**우선순위: Must**

시스템은 검지, 중지, 약지, 소지 및 엄지의 landmark를 사용하여 각 손가락의 굽힘 정도를 계산해야 한다.

인수 조건:

- 각 손가락의 굽힘값을 `0.0~1.0` 범위로 표현해야 한다.
- `0.0`은 편 상태, `1.0`은 최대 굽힘 상태로 정의한다.
- 손 크기와 카메라 거리에 따른 영향을 최소화해야 한다.
- 비정상적인 계산 결과는 허용 범위 안으로 제한해야 한다.
- 손가락 굽힘·엄지 대립·벌림 계산 담당을 `hand_target_node`로 명시

#### FR-03. 엄지 대립 및 벌림값 계산

**우선순위: Must**

시스템은 엄지 끝과 검지, 중지 및 손바닥 landmark의 상대 관계를 이용하여 엄지 대립 및 벌림 정도를 계산해야 한다.

인수 조건:

- 엄지 대립 및 벌림값을 `0.0~1.0`으로 표현해야 한다.
- 엄지가 검지 방향으로 접근하는 움직임을 구분할 수 있어야 한다.
- 손의 크기를 기준으로 거리를 정규화해야 한다.
- 손가락 굽힘·엄지 대립·벌림 계산 담당을 `hand_target_node`로 명시

#### FR-04. 사용자 캘리브레이션

**우선순위: Should**

시스템은 사용자마다 다른 손가락 가동범위를 보정할 수 있어야 한다.

인수 조건:

- 사용자의 편 손 자세를 최소값으로 저장할 수 있어야 한다.
- 사용자의 주먹 자세를 최대값으로 저장할 수 있어야 한다.
- 저장된 값은 손가락별 정규화에 적용되어야 한다.
- 캘리브레이션은 내부망 관제·제어 웹에서 편 손과 주먹 자세를 수집·확인한 후 적용해야 한다.
- 사용자 캘리브레이션 적용 위치를 `hand_target_node`로 명시

### 3.2 명령 생성 및 전달

#### FR-05. 명령값 필터링

**우선순위: Must**

시스템은 손 떨림과 landmark 오차가 모터의 급격한 움직임으로 전달되지 않도록 목표값을 필터링해야 한다.

인수 조건:

- 작은 변화는 deadband를 통해 무시할 수 있어야 한다.
- 이동 평균 또는 저역 통과 필터를 적용해야 한다.
- 한 프레임에서 목표값이 급격하게 변경되지 않도록 제한해야 한다.
- deadband·저역 통과 필터·변화율 제한 담당을 `hand_target_node`로 명시

#### FR-06. ROS 2 손 명령 발행

**우선순위: Must**

`thing_vision/hand_target_node`는 7논리축 목표를 GitLab `develop`의 `HandCommand.msg`와 동일하게 `/thing/command/mimic`에 발행해야 한다.

기준:

- 브랜치: [develop/thing_interfaces](https://lab.ssafy.com/s15-webmobile3-sub1/S15P11C103/-/tree/develop/thing_ws/src/thing_interfaces?ref_type=heads)
- 동결 커밋: `70dfdab8d555dfbfdd471c5acca4f30a8a8fc3ec`
- 경로: `/thing/command/mimic → command_manager → /thing/command/selected → command_guard → /thing/command`

인수 조건:

- `stamp`, source별 `sequence`, `source`, 7개 고정 축, `speed_limit`, `confidence`를 develop 정의 그대로 사용한다.
- `HandCommand`에는 mode·owner·enable 필드를 추가하지 않는다. mode·owner는 `SetControlMode`와 `ControlState`로만 관리한다.
- MIMIC 유효 명령은 20Hz 이상 발행하고, hand-loss latch 상태에서는 발행하지 않는다.
- 축 값과 confidence는 `0.0~1.0`의 유한값이어야 한다.
- 운영 `stamp`는 UTC와 동기화한 ROS system time을 사용한다.
- `speed_limit`은 MVP 프로젝트 규칙으로 `0.0 < value <= 1.0`만 허용하고 `0`은 invalid로 거부한다. 실제 축 속도는 YAML의 최대속도에 이 비율을 곱한다.

### 3.3 모터 제어

#### FR-07. 7채널 서보 제어

**우선순위: Must**

Raspberry Pi는 7개의 서보에 개별 목표 위치를 전달해야 한다.

인수 조건:

- 각 모터는 서로 다른 ID를 사용해야 한다.
- 손가락마다 최소 및 최대 모터 위치를 설정할 수 있어야 한다.
- 7개 모터에 서로 다른 목표값을 전달할 수 있어야 한다.
- 잘못된 목표값은 모터에 전달되기 전에 제한되어야 한다.

#### FR-08. 명령 보간 및 속도 제한

**우선순위: Must**

Raspberry Pi는 Jetson에서 전달된 목표값을 모터 제어 주기에 맞춰 부드럽게 보간해야 한다.

인수 조건:

- 목표 위치가 갑자기 변경되어도 모터가 즉시 최대 속도로 이동하지 않아야 한다.
- 손가락별 최대 속도를 설정할 수 있어야 한다.
- 엄지 대립 및 벌림축은 일반 손가락과 별도의 속도 제한값을 사용할 수 있어야 한다.

#### FR-09. 모터 상태 수집

**우선순위: Must**

시스템은 서보에서 제공하는 상태값을 수집해야 한다.

수집 대상:

- 실제 위치
- 목표 위치
- 속도
- 전류 또는 부하 추정값
- 온도
- 통신 상태

권장 토픽:

```
/thing/motor_status, /thing/diagnostics
```

`/joint_states`는 develop 인터페이스에 없으므로 2주 Must 경로에서 제외한다. 위치·속도·전류·온도·통신은 Must이며, 전압·hardware_error의 상세 UI 활용은 Should다.

#### FR-10. 초기화·명시적 정지 및 토크 정책

**우선순위: Must**

시작·재시작·모드 전환은 이전 명령을 재생하지 않아야 하며 토크 상태를 안전 상태 머신이 단일하게 결정해야 한다.

인수 조건:

- `INIT`: 캐시·sequence·실행 큐를 폐기하고 토크 OFF로 설정·E-Stop·7개 모터 통신을 검사한다.
- `READY`: 토크 OFF 상태로 새 mode·owner와 새 명령을 기다린다.
- `RUN`: 유효 mode·owner를 획득한 뒤 활성화 이후 첫 유효 명령에서만 토크 ON한다.
- `HOLD`: 현재 보간 setpoint에서 추가 이동을 멈추고 제한 토크를 유지한다.
- `SAFE`: 모터 통신·전류·온도가 정상일 때만 YAML 안전 자세로 저속 이동하고 도달 뒤 토크 OFF한다.
- `FAULT`: 일반 명령을 차단하고 토크 OFF한다.
- `ESTOP`: 물리 회로로 구동 전원을 차단한다.
- 명시적 STOP은 `SetControlMode(MODE_DISABLED, OWNER_NONE)`로 처리하며 READY·RUN·HOLD에서만 READY 복귀 경로로 허용한다. READY에서는 토크 OFF·mode=`DISABLED`·owner=`NONE`인 READY를 유지하고, RUN·HOLD에서는 즉시 큐·Gesture·Action을 취소한 뒤 현재 setpoint에서 HOLD한다.
- RUN·HOLD에서 STOP이 수락되면 command timeout에 의한 SAFE 상승 타이머를 취소하고 `stop_settle_ms=500` 동안 안정한 뒤 토크 OFF·READY로 전환한다. STOP은 안전 자세 이동 명령이 아니다.
- STOP 안정화 중 새 FAULT·ESTOP이 발생하면 해당 안전 상태가 우선한다. SAFE·FAULT·ESTOP에서 STOP은 mode=`DISABLED`, owner=`NONE`, `owner_alive=false`와 기존 큐만 원자적으로 해제하고 현재 안전 상태는 유지한다. 이 상태에서 READY 복귀는 원인 해소와 Safety Reset·INIT 재검사를 통해서만 허용한다.
- 시작, 컨테이너 재시작, 네트워크 복구와 E-Stop 물리 해제만으로 토크·mode·owner·명령·녹화를 자동 재개하지 않는다.

### 3.4 안전 기능

#### FR-11. 명령 timeout 및 owner lease

**우선순위: Must**

Raspberry Pi는 monotonic clock으로 마지막 유효 명령과 owner lease를 서로 독립적으로 판정해야 한다.

```yaml
command_hold_timeout_ms: 300
command_safe_timeout_ms: 1000
control_renew_period_ms: 1000
owner_lease_timeout_ms: 3000
hand_confidence_min: 0.70
hand_loss_debounce_ms: 150
hand_reacquire_stable_ms: 300
stop_settle_ms: 500
fault_clear_stable_ms: 1000
estop_release_stable_ms: 500
safe_motion_timeout_ms: 3000
```

- develop에는 전용 heartbeat/lease 메시지·서비스와 lease ID가 없다.
- 2주 MVP에서는 현재 owner가 동일한 mode·owner로 `/thing/set_control_mode`를 1000ms마다 재호출하면 lease를 갱신한다. 이 호출은 명령 timeout을 갱신하지 않는다.
- 3000ms 동안 갱신이 없으면 하나의 임계구역에서 owner=`NONE`, mode=`DISABLED`, `owner_alive=false`로 바꾸고 Gesture·Action·명령 큐를 취소하며 활성 기록을 `INTERRUPTED`로 요청한다.
- lease 만료는 계획되지 않은 단절이므로 즉시 HOLD하고 마지막 유효 명령 기준 총 1000ms에 SAFE로 전환한다.
- 마지막 유효 명령 후 300ms에 HOLD, 총 1000ms에 SAFE로 전환하며 연결 복구만으로 RUN에 돌아가지 않는다.
- MIMIC·TELEOP은 활성 동작 동안 신선한 stamp·증가 sequence의 HandCommand를 20Hz로 발행해야 한다. Gesture executor는 동작·초기 유지시간이 끝난 뒤에도 다음 유효 MANUAL 명령 또는 STOP까지 마지막 자세를 동일한 조건으로 20Hz 발행한다. Sequence는 구현하는 경우 동일 규칙을 따른다.

#### FR-12. 안전 우선순위와 복구 원칙

**우선순위: Must**

안전 우선순위는 `ESTOP > FAULT > SAFE > HOLD > 일반 제어`로 고정하고 손 미검출을 포함한 모든 세부 전이와 복구 절차의 단일 기준은 FR-35로 한다.

- 안전 전이는 mode 변경, Logger 응답, 웹과 일반 명령보다 먼저 처리한다.
- HOLD·SAFE·FAULT·ESTOP에서 이전 큐와 stale command를 재실행하지 않는다.
- HOLD의 명시적 STOP 복구와 SAFE·FAULT·ESTOP의 원인 해소·안정 시간·Safety Reset·`INIT` 재검사·READY 전환은 FR-35의 절차만 따른다.
- `/thing/reset_safety`는 V6 MVP의 ROS 2 런타임 인터페이스 계약으로 확정한다. Raspberry Pi의 `thing_control` 패키지에 속한 `safety_manager`가 표준 `std_srvs/srv/Trigger` 서버를 제공하며 내부망에서만 사용하고 EC2·외부망에는 노출하지 않는다.
- 이 서비스는 커스텀 `thing_interfaces` 타입이 아니다. `thing_interfaces/srv/ResetSafety.srv`와 인터페이스 생성 항목을 추가하지 않으며 기존 7 msg·5 srv·1 action 구성을 유지한다.
- 현재 확정 범위는 서비스 이름·타입·담당 노드·동작 원칙이며 실제 서버와 전체 안전 상태 머신 구현은 `thing_control` 후속 작업이다.
- Reset 요청이 수락되면 INIT 재검사를 시작한다. 검사를 통과해 READY가 된 뒤에도 토크 OFF, mode=`DISABLED`, owner=`NONE`을 유지하며 새 활성화와 새 명령이 있어야 RUN으로 전환한다.

#### FR-13. 물리적 비상정지와 상태 감지

**우선순위: Must**

ROS 2·CPU와 무관하게 모터 구동 전원을 차단하는 물리적 E-Stop을 제공해야 한다.

- 전원 차단 주접점과 별도 NC 보조접점을 사용하고 보조접점은 절연 GPIO로 읽는다.
- 보조접점 단선·읽기 불가는 E-Stop active로 처리한다.
- CPU가 동작 중이면 작동 후 100ms 안에 `SafetyState.estop_active=true`와 ESTOP을 발행한다.
- 물리 해제는 복구 요청이 아니며 `estop_release_stable_ms=500`의 연속 안정과 Safety Reset·INIT 재검사가 필요하다.

#### FR-14. 모터 fault 판정

**우선순위: Must**

과전류·과온·지속 통신 오류와 SAFE 동작 실패를 latch FAULT로 처리해야 한다.

- 단일 읽기 실패는 경고로 기록한다.
- 필수 모터의 `communication_ok=false`가 3회 연속이거나 `bus_communication_ok=false`가 300ms 연속이면 지속 통신 오류로 판정한다.
- DYNAMIXEL 자체 shutdown 보호를 비활성화하지 않는다.
- 전류·온도 trip 값은 XL330-M288-T 제조사 범위 이하에서 실물 부하 시험으로 확정해 YAML에 저장한다. 검증값이 없거나 범위를 벗어나면 INIT을 실패 처리한다.
- fault 원인이 1000ms 이상 해소되기 전 Reset을 거부하며, FAULT에서 자율 자세 이동을 시도하지 않는다.

### 3.6 데이터 저장

#### FR-18. 실험 데이터 기록 및 세션 수명주기

**우선순위: Must**

Logger는 rosbag2를 로봇의 유일한 로컬 시계열 원본으로 사용하며 별도의 애플리케이션 SQLite, `session_state.json` 및 영구 upload outbox를 만들지 않는다.

필수 rosbag2:

- `/thing/landmarks`, 최종 `/thing/command`, `/thing/motor_status`
- `/thing/control_state`, `/thing/safety_state` , _

```jsx
/thing/start_recording
/thing/stop_recording 
# 시작 및 종료 시간은 rosbag에 기록되지 않음.
# web bridge에서 시작/종료 시간 호출할 떄 
```

실행 중 상태 관리:

- 활성 Session ID, bag path, UTC 시작·종료, 기록·판정 대기 상태는 Logger 메모리와 RecordingState로 관리한다.
- 업로드 성공·실패는 uploader 진단 로그에 기록하고 최종 공개 상태는 EC2 GET API에서 확인한다.

세션 규칙:

- Session ID는 CSPRNG로 만든 0이 아닌 63-bit 양의 정수로 생성해 ROS `uint64`에 담고 기존 rosbag2 경로 충돌을 검사한다. JSON·API·EC2에서는 10진 문자열로 표현한다.
- 기록은 MIMIC에서 동시에 하나만 허용한다. StartRecording은 고유 경로 확보와 rosbag2 시작이 모두 성공해야 수락한다.
- 정상 Stop은 rosbag2를 flush·종료하고 실행 중 메모리에서 결과 판정을 기다린다. 결과 수락 직후 exporter를 시작하며 판정 전 다음 정상 기록을 거부한다.
- 카메라 원본 영상은 저장하지 않는다.
- SAFE·FAULT·ESTOP·lease 만료·프로세스 종료 시 안전 전이를 먼저 수행하고 가능한 즉시 rosbag2를 flush한다.
- 프로세스 재시작 뒤 이전 recording·판정 대기·upload를 자동 복원하거나 재개하지 않는다. 남은 rosbag2는 수동 확인·재업로드의 원본으로만 사용한다.
- rosbag2·exporter·uploader I/O는 제어 callback과 분리한다. 기록 디스크가 불가하면 새 recording만 거부하고 제어·안전은 계속한다.
- `/thing/landmarks`는 기록하지만 `/thing/image_raw`와 MJPEG 영상은 저장하지 않는다.

### 3.7 내부망 관제·제어 웹 기능

#### FR-19. 웹 모드 선택

**우선순위: Must**

웹은 MIMIC과 MANUAL을 선택하고 현재 mode·owner를 `/thing/control_state`로 확인해야 한다.

- mode·owner는 `HandCommand`에 포함하지 않고 `/thing/set_control_mode`로만 요청한다.
- MIMIC↔MANUAL 직접 전환은 금지한다. 먼저 `MODE_DISABLED, OWNER_NONE`으로 STOP한 뒤 READY에서 새 mode·owner를 획득한다.
- 기록·Gesture·Action 중 새 일반 mode 요청은 거부하되 STOP과 안전 전이는 항상 선점한다.
- 동시에 온 요청은 command manager의 단일 mutex에서 직렬화하며 첫 유효 요청 하나만 수락한다. 다른 owner, stale owner, 안전 비정상 요청은 거부하고 현재 ControlState를 유지한다.
- hand-loss latch 뒤 MIMIC 재개도 DISABLED→MIMIC의 명시적 두 단계로 수행한다.

#### FR-20. 모방 모드 영상 표시

**우선순위: Must**

웹은 저장하지 않는 MJPEG 영상, 손 검출 여부와 hand-loss·재개 필요 상태를 표시해야 한다. landmark overlay의 정교한 표현은 Should다.

`mjpeg_streamer`가 image와 landmark를 합성해 HTTP MJPEG를 제공.

#### FR-21. 모방 모드 손동작 정보 표시

**우선순위: Should**

5개 손가락 굽힘, 엄지 대립·벌림, 7논리축 목표와 confidence를 숫자 또는 게이지로 표시한다. 원시 landmark 좌표 표시는 Could다.

구조화된 landmark·7축 정보는 `web_bridge_node`가 WebSocket으로 제공

#### FR-22. 조작 모드 명령 입력

**우선순위: Must**

MANUAL에서 편 손, 주먹, 원통 파지, 집기, STOP을 사전 정의 7축 값으로 실행해야 한다.

- 같은 시점에 Gesture 하나만 실행하고 새 일반 동작은 큐에 쌓지 않고 거부한다.
- Gesture executor는 동작·초기 유지 중 20Hz의 새 HandCommand를 발행한다. 기본 동작·초기 유지시간은 open·fist 1000ms, cylindrical_grasp·pinch 3000ms이며 YAML에서 변경한다.
- 초기 유지시간이 끝난 뒤에도 active mode=`MANUAL`, 유효 owner lease, `SafetyState=RUN` 조건을 매 주기 확인하면서 다음 유효 MANUAL 명령 또는 STOP까지 마지막 자세를 신선한 stamp·증가 sequence로 20Hz 계속 발행한다.
- 새 Gesture는 기존 마지막 자세 발행을 교체한다. STOP·owner lease 만료·HOLD·SAFE·FAULT·ESTOP은 마지막 자세 발행을 즉시 취소하며 안전 전이가 항상 우선한다.
- STOP은 FR-10의 DISABLED 전환이며 다른 일반 동작을 선점한다.
- 가위바위보·카운트다운 Sequence와 별도 초기 자세 버튼은 Could다.

#### FR-23. 웹 명령 범위 제한

**우선순위: Must**

웹은 허용된 gesture·mode enum만 전송하고 임의 축·모터 ID·ROS 이름을 입력받지 않아야 한다. 서버와 command_guard가 유한값, 범위, speed_limit, timestamp, sequence를 다시 검증한다.

#### FR-24. 로봇 및 시스템 상태 모니터링

**우선순위: Must**

웹은 Jetson·Raspberry Pi·ROS 2·카메라·모터 연결, active mode·owner, SafetyState와 RecordingState를 구분해 표시해야 한다. 모터별 watchdog·원시 진단 상세 화면은 Should다.

camera·MediaPipe·hand_target·MJPEG 연결 상태를 각각 구분해 표시

#### FR-25. 모터 상태 표시

**우선순위: Should**

7개 모터의 목표·현재 위치, 속도, 전류, 온도와 통신 상태를 구분하고 stale 값은 연결 끊김과 구별해야 한다. 이 화면은 Raspberry Pi의 안전 판단을 대신하지 않는다.

#### FR-26. 데이터 기록 UI 및 상태 표시

**우선순위: Must**

웹은 develop의 StartRecording·StopRecording·SetMimicResult 서비스만 호출하고 RecordingState로 Session ID·상태·판정 대기를 표시해야 한다.

- 웹은 rosbag2·임시 업로드 파일·EC2 SQLite를 직접 생성·수정·삭제하지 않는다.
- 내부망 웹의 실시간 영상·상태는 MJPEG와 Web Bridge WebSocket을 통해 ROS 2에서 받고 rosbag2나 DB를 조회하지 않는다.
- `bag_path`는 로컬 rosbag2가 활성화된 정상 세션 경로이며 EC2 upload 상태를 뜻하지 않는다.
- develop RecordingState에는 upload 필드가 없으므로 업로드 진행률은 ROS 계약에 추가하지 않고 uploader 진단 로그로만 확인한다. 완료된 공개 세션은 EC2 포털의 GET API에서 조회한다.
- 영상은 MJPEG HTTP, 상태 데이터는 WebSocket이라는 경로 분리

#### FR-27. 웹 오류 및 안전 안내

**우선순위: Must**

웹은 손 미검출, 연결 단절, timeout, 모터 통신, 과전류·과온, E-Stop과 reset 가능 여부를 설명하고 위험 상태에서 일반 조작을 비활성화해야 한다.

- 손 미검출과 유효 재검출 300ms를 표시하되 재검출이나 연결 복구만으로 제어가 재개된 것처럼 표시하지 않는다.
- 현재 SafetyState가 HOLD이면 `SetControlMode(MODE_DISABLED, OWNER_NONE)` 명시적 STOP, READY 전환, MIMIC·owner 재획득이 필요함을 안내한다.
- 현재 SafetyState가 SAFE·FAULT·ESTOP이면 원인 해소와 설정된 안정 시간 뒤 `/thing/reset_safety`가 필요함을 안내하고, INIT 재검사와 READY 전환 전에는 MIMIC 재활성화를 허용하지 않는다.
- reset 가능 여부와 거부 사유를 구분하고, 복구 완료 뒤에도 새 MIMIC·owner 획득과 새 HandCommand가 필요함을 표시한다.
- hand-loss latch는 develop ROS 2 메시지에 필드를 추가하지 않고 HandLandmarks·SafetyState·ControlState를 바탕으로 Web Bridge가 파생한 WebSocket 표시 상태로만 제공한다.
    - 상세 복구 순서의 단일 기준은 FR-35이며 이전 command, Gesture, Sequence 및 recording을 자동 재개하지 않는다.
- Web Bridge가 `/thing/landmarks`를 직접 구독해 hand-loss 상태를 계산

#### FR-28. 내부망 관제·제어 웹 실행 환경 제한

**우선순위: Must**

#### FR-30. 사용자 정의 ROS 2 인터페이스 동결

**우선순위: Must**

ROS 2 스키마의 단일 기준은 [GitLab develop의 thing_interfaces](https://lab.ssafy.com/s15-webmobile3-sub1/S15P11C103/-/tree/develop/thing_ws/src/thing_interfaces?ref_type=heads)이며 이 문서 검증 커밋은 `70dfdab8d555dfbfdd471c5acca4f30a8a8fc3ec`이다.

- 메시지 7종: `HandCommand`, `HandLandmarks`, `MotorState`, `MotorStatus`, `ControlState`, `SafetyState`, `RecordingState`
- 서비스 5종: `SetControlMode`, `ExecuteGesture`, `StartRecording`, `StopRecording`, `SetMimicResult`

이 문서에는 필드 원문을 복제하지 않는다. 이름·타입·상수·필드 순서는 위 커밋의 `.msg/.srv/.action` 파일을 그대로 사용하며 6.3절은 런타임 이름만 정의한다.

`/thing/reset_safety`는 프로젝트의 ROS 2 런타임 서비스 계약에는 포함되지만 커스텀 `thing_interfaces` 구성에는 포함되지 않는다. ROS 2 표준 `std_srvs/srv/Trigger`를 사용하므로 `thing_interfaces/srv/ResetSafety.srv`를 만들거나 `thing_interfaces/CMakeLists.txt`의 인터페이스 생성 목록을 변경하지 않는다.

프로젝트 의미 규칙:

- `HandCommand`는 7개 고정 축·source·sequence·speed_limit·confidence이며 mode·owner·enable이 없다.
- `ControlState`만 active mode·owner·owner_alive·sequence_running을 나타낸다.
- `RecordingState.bag_path`는 로컬 rosbag2 경로이며 EC2 상태가 아니다.
- `SafetyState.fault_code` 코드표, speed_limit 의미와 reason 문자열은 develop 스키마에 없으므로 FR-41 프로젝트 설정·문서로 고정한다.
- `/thing/image_raw`가 표준 `sensor_msgs/msg/Image`임

#### FR-31. 명령 중재와 충돌 처리

**우선순위: Must**

`command_manager`만 MIMIC·TELEOP·MANUAL 중 active mode·owner에 맞는 하나를 `/thing/command/selected`로 발행한다.

- mode·owner 획득·갱신·해제는 하나의 mutex/atomic transaction에서 처리한다.
- owner=`NONE`에서 첫 유효 획득 요청 하나만 수락한다. 같은 owner·mode 재요청은 lease 갱신, 다른 owner 요청은 거부다.
- mode 전환은 반드시 DISABLED를 거친다. 기록·Gesture·Action 실행 중 새 일반 요청은 거부한다.
- Gesture와 Action은 동시에 실행하지 않으며 새 일반 동작은 큐에 쌓지 않는다.
- STOP, lease 만료와 SafetyState 전이는 일반 동작을 선점하고 선택·최종 큐를 함께 폐기한다.
- 안전 전이와 일반 요청이 동시에 발생하면 안전 전이가 이긴다. STOP과 새 동작이 동시에 발생하면 STOP이 이긴다.
- `command_manager`가 `/thing/command/mimic`을 구독

#### FR-32. 명령 검증 및 최종 모터 명령

**우선순위: Must**

`command_guard`만 `/thing/command/selected`를 검증해 `/thing/command`로 발행한다.

검증:

- 유한값, 축·confidence `0.0~1.0`, speed_limit `0.0 초과 1.0 이하`
- source와 active mode 일치
- ROS stamp가 미래 100ms를 넘지 않고 수신 시점 기준 300ms보다 오래되지 않음
- source별 sequence가 새 값임
- 축별 위치·속도·변화율과 SafetyState

sequence는 active source별로 관리한다. 새 mode 획득 때 해당 source 기준을 초기화하고, active 동안에는 uint32 serial-number 비교로 전진만 허용해 wrap을 처리한다. 단순 프로세스 재연결은 초기화 조건이 아니며 DISABLED 재획득이 필요하다.

STOP·Safety Reset은 HandCommand가 아니므로 이 토픽에 가짜 명령으로 넣지 않는다.

#### FR-33. 최신 목표 추종과 하드웨어 watchdog

**우선순위: Must**

DYNAMIXEL 노드는 콜백에서 `latest_target`만 원자적으로 갱신하고 제어 타이머가 최신 목표를 보간한다.

- 이전 목표 완료 전 새 목표를 처리하고 stale 목표를 큐에 쌓지 않는다.
- Raspberry Pi 내부 `hardware_command_watchdog_ms=500`에서 새 최종 명령이 없으면 추가 이동을 중단한다.
- ROS executor가 지연되어도 watchdog과 E-Stop 판정이 독립적으로 동작해야 한다.
- DYNAMIXEL Bus Watchdog 레지스터 적용은 실물 모델·제어주기 검증 후 Should로 진행한다.

#### FR-34. 제어 모드 및 owner lease

**우선순위: Must**

develop의 `MODE_DISABLED|MIMIC|MANUAL|TELEOP`와 `OWNER_NONE|WEB|LOCAL` 상수를 사용한다.

- MIMIC은 mimic, MANUAL은 Gesture·Sequence의 manual, TELEOP은 teleop 입력만 허용한다.
- 획득: READY에서 `SetControlMode(활성 mode, WEB|LOCAL)`.
- 갱신: 현재 owner가 같은 mode·owner 요청을 1000ms마다 보낸다.
- 정지·해제: `SetControlMode(MODE_DISABLED, OWNER_NONE)`. 누구나 내부망에서 안전 정지를 요청할 수 있으나 활성 mode 획득은 owner 충돌 검사를 거친다. STOP의 상태별 처리와 READY 복귀 조건은 FR-35를 따른다.
- 3000ms lease 만료 시 FR-11의 원자적 해제와 안전 전이를 적용한다.
- `ControlState.owner_alive`는 유효 lease일 때만 true다.

#### FR-35. 안전 상태 관리와 복구 절차

**우선순위: Must**

develop `SafetyState`의 `INIT, READY, RUN, HOLD, SAFE, FAULT, ESTOP`을 사용하며 이 절을 안전 전이와 복구 절차의 단일 기준으로 한다.

- 시작·재시작 → INIT: 토크 OFF, 캐시·큐 폐기, 설정·E-Stop·7모터 검사
- INIT 정상 → READY: 토크 OFF, 새 획득 대기
- READY + 유효 mode·owner 획득 뒤 새 명령 → RUN
- RUN + 명령 300ms 단절 → HOLD: 현재 보간 setpoint 고정
- RUN/HOLD + 마지막 유효 명령 기준 총 1000ms 단절 → SAFE: 건강한 모터만 저속 안전 자세, 성공 뒤 토크 OFF
- READY의 명시적 STOP → 토크 OFF·mode=`DISABLED`·owner=`NONE`인 READY 유지
- RUN·HOLD의 명시적 STOP → 기존 큐를 폐기하고 HOLD, command timeout 기반 SAFE 상승 타이머 취소, `stop_settle_ms=500` 안정 뒤 토크 OFF·READY
- SAFE·FAULT·ESTOP의 명시적 STOP → mode·owner·큐만 해제하고 현재 안전 상태 유지, READY 복귀는 Safety Reset만 허용
- 과전류·과온·지속 통신 오류·SAFE 3000ms 실패 → FAULT
- E-Stop active/입력 불명 → ESTOP

손 미검출 복구의 공통 조건:

- 손 미검출 또는 낮은 신뢰도가 150ms 연속되면 MIMIC HandCommand 발행을 중단하고 hand-loss latch를 설정한다.
- 유효한 손 검출 조건이 300ms 연속 유지되어야 재검출로 인정한다. 재검출만으로 latch, mode, owner 또는 RUN을 자동 복원하지 않는다.
- hand-loss가 SAFE 원인인 경우 300ms 재검출을 원인 해소로 인정한 뒤 `fault_clear_stable_ms=1000` 안정 타이머를 시작한다.

현재 안전 상태가 HOLD인 경우:

1. 사용자가 `SetControlMode(MODE_DISABLED, OWNER_NONE)`으로 명시적 STOP을 요청한다.
2. STOP을 수락하는 순간 mode=`DISABLED`, owner=`NONE`, `owner_alive=false`로 바꾸고 기존 command·Gesture·Sequence 큐를 폐기하며 command timeout 기반 SAFE 상승 타이머를 취소한다.
3. 시스템이 HOLD에서 `stop_settle_ms=500` 동안 안정화한다. 이 동안 새 FAULT·ESTOP이 발생하면 READY 전이를 취소하고 해당 안전 상태가 우선한다.
4. 상위 안전 원인이 없으면 토크 OFF인 READY로 전환한다.
5. 사용자가 MIMIC mode와 owner를 새로 획득한다.
6. 시스템은 이 새 활성화 이후 생성된 신선한 HandCommand부터 실행한다.

현재 안전 상태가 SAFE, FAULT 또는 ESTOP인 경우:

- 이 상태에서 명시적 STOP은 mode=`DISABLED`, owner=`NONE`, `owner_alive=false`와 기존 command·Gesture·Sequence 큐만 원자적으로 해제하고 현재 안전 상태를 변경하지 않는다. READY 복귀는 아래 Safety Reset 절차로만 허용한다.
1. 손 미검출, 통신 오류, 과전류·과온, E-Stop 등 안전 진입 원인을 해소한다.
2. SAFE·FAULT 원인은 해소 뒤 `fault_clear_stable_ms=1000`, E-Stop은 물리 해제 뒤 `estop_release_stable_ms=500`을 연속으로 만족해야 한다. 원인이 여러 개면 적용되는 조건을 모두 만족해야 한다.
3. 조건을 만족한 뒤 내부망에서 `/thing/reset_safety`를 호출한다. HOLD에서는 이 서비스를 사용하지 않고 FR-35의 명시적 STOP 절차를 사용한다.
4. `safety_manager`는 현재 상태와 원인·안정시간을 다시 검사한다. 조건이 충족되지 않으면 `success=false`와 거부 이유를 반환하고 현재 안전 상태를 유지한다.
5. 요청을 수락하면 `success=true`와 수락 메시지를 반환하고 INIT 전체 재검사를 시작한다. 이 `success`는 Reset 요청의 수락을 뜻하며 INIT 검사 통과나 READY 도달을 뜻하지 않는다.
6. 시스템이 INIT에서 설정, E-Stop 입력과 7개 모터 상태를 다시 검사한다.
7. 검사를 통과하면 토크 OFF·mode=`DISABLED`·owner=`NONE`인 READY로 전환한다.
8. 사용자가 MIMIC mode와 owner를 새로 획득한다.
9. 시스템은 이 새 활성화 이후 생성된 신선한 HandCommand부터 실행한다.

복구 공통 규칙:

- 새 MIMIC·owner 획득이 수락될 때 hand-loss latch를 해제한다.
- HOLD에서는 명시적 STOP 요청 시, SAFE·FAULT·ESTOP에서는 해당 상태 진입 시 기존 command·Gesture·Sequence 큐를 폐기하고 활성 recording을 `RecordingState.state=INTERRUPTED`로 종료한다.
- 이전 command, Gesture, Sequence 및 recording은 어떤 경로에서도 자동 재개하지 않는다.

안전 자세와 토크 override는 Raspberry Pi의 safety manager와 hardware node 내부 경로로 적용한다. develop에 없는 `/thing/command/safety`를 임의 생성하지 않으며 `SOURCE_SAFETY`는 향후 확장을 위해 예약한다.

**우선순위: Must**

#### develop에 없는 항목과 MVP 처리

아래 항목은 기준 커밋에 **없다**.

- 전용 STOP 인터페이스 → 기존 SetControlMode의 DISABLED/NONE으로 처리
- heartbeat/lease·lease ID → 같은 mode·owner SetControlMode 주기 재호출로 처리
- 커스텀 Safety Reset 타입 → 추가하지 않음. 프로젝트 런타임 서비스 `/thing/reset_safety`는 표준 `std_srvs/srv/Trigger`로 계약 확정, `thing_control`의 실제 서버 구현은 후속 작업
- SAFE 전용 command 토픽 → Raspberry Pi 내부 safety/hardware override로 처리
- fault code 표·speed_limit 의미·reason 표준·통신 오류 임계값 → FR-41 YAML과 `docs/interfaces.md`에 프로젝트 규칙으로 추가
- command_manager·safety_manager·thing_hardware·Logger 사이 내부 상태 전파 → 개발 중 구체 reason 값·호출 순서·구독 책임을 확정한다. 기존 공개 ROS 2 스키마와 Safety Reset 계약은 유지하고 안전 통합 시험 전에 `docs/interfaces.md`에 동결한다.
- EC2 upload 상태 필드 → ROS 메시지에 추가하지 않고 uploader 진단으로 처리

### 3.9 EC2 기반 데이터 포털

#### 확정된 MVP 데이터 계약

- 공개 접근: 로그인 없는 READY 데이터 GET
- 업로드: 단일 로봇 Bearer Token + HTTPS
- 로봇 로컬 저장: rosbag2 원본 + 업로드 시점의 임시 세 파일. 별도 애플리케이션 DB·영구 spool 없음
- EC2 저장: SQLite와 `EC2_DATA_DIR=/var/lib/thing-data`
- 공개 파일: metadata JSON, HandCommand CSV, MotorStatus CSV 정확히 세 개
- 제외: landmark, ControlState·SafetyState 이력, 영상, rosbag2
- 시간: UTC, `schema_version=1`, `data_version=1`
- 다중 data version, 파일 교체, S3는 이번 2주 범위 밖

#### FR-46. 완료 세션 직접 EC2 전송

**우선순위: Must**

SUCCESS·FAILURE 판정 직후 `thing-control`의 Logger 측 exporter와 격리된 uploader는 6.5절에 따라 세 파일을 생성·검증·비동기 업로드해야 한다.

- 임시 경로: `/var/lib/thing-robot-data/tmp-upload/{session_id}/`
- exporter가 rosbag2를 읽고 세 파일을 `.part`로 작성한 뒤 fsync·schema·행 수·SHA-256을 검증하여 같은 임시 디렉터리 안에서 최종 파일명으로 원자적 rename한다.
- uploader는 rosbag2 mount를 갖지 않는다. exporter는 완료된 세 파일 경로와 `content_digest`만 `/run/thing-uploader/uploader.sock`의 private Unix socket으로 전달하고, uploader는 임시 디렉터리를 읽기 전용으로 사용한다.
- 실행 중 상태는 메모리에서 `EXPORTING→UPLOADING→UPLOADED|FAILED`로 관리하고 uploader 진단 로그에 결과를 남긴다. 이를 위한 로컬 DB나 영구 queue는 만들지 않는다.
- 신규 `(robot_id, session_id)`와 `content_digest`는 201, 기존 key의 같은 `content_digest` 재전송은 200, 같은 key의 다른 `content_digest`는 409이며 덮어쓰지 않는다.
- `200`·`201` 응답의 `content_digest`가 요청값과 일치하면 exporter가 임시 세 파일을 즉시 삭제한다.
- 업로드 실패 시 임시 세 파일을 정리하고 오류를 기록한다. 운영자는 `ros2 run thing_logger reupload_session --bag <bag_path> --result SUCCESS|FAILURE`로 보존된 rosbag2를 수동 재업로드한다. `--result`를 생략하거나 SUCCESS·FAILURE 외 값을 주면 실행을 거부한다.
- 인터넷 단절 장기 보관, 지수 backoff, 재부팅 후 자동 upload 복구는 2주 MVP 범위에서 제외한다. 업로드 실패가 로봇 제어·안전을 중단시키지 않아야 한다.

#### FR-47. 공개 세션 목록 및 상세 조회

**우선순위: Must**

READY 세션의 Session ID, UTC 시작·종료·업로드 시각, 결과, 기간, 행 수와 파일 크기를 로그인 없이 조회해야 한다.

- 기본 정렬은 `started_at DESC, session_id DESC`, 기본 20개·최대 100개다.
- 존재하지 않는 세션은 404, STAGING·FAILED는 공개하지 않는다.
- 정확한 Session ID 검색은 Must다. 날짜·결과 필터와 cursor pagination은 Should다.

#### FR-48. 로봇 데이터 표시

**우선순위: Must**

상세 화면은 7논리축 HandCommand와 모터별 목표·현재 위치, motor-axis rad, 속도, 전류, 전압, 온도와 통신 여부를 기본 표 또는 그래프로 표시해야 한다.

- 단위·UTC·결측·통신 실패를 구분하고 모터축 각도가 실제 관절각이 아님을 표시한다.
- 한 개의 기본 시계열 차트와 표는 Must다. 다축 고급 차트·구간 조회·서버 다운샘플링은 Should다.

#### FR-49. 데이터 다운로드

**우선순위: Must**

세션마다 canonical 이름의 metadata JSON 1개, HandCommand CSV 1개, MotorStatus CSV 1개를 로그인 없는 GET으로 다운로드해야 한다. 파일 누락·hash 불일치는 정상 다운로드로 제공하지 않는다. 크기 사전표시와 공개 checksum 표시는 Should·Could다.

#### FR-50. 조회 전용 보안 경계

**우선순위: Must**

EC2에는 조회·다운로드 GET과 장치 인증 upload POST만 둔다. 로봇 명령, mode·기록·Safety Reset, callback·socket, ROS 2·rclpy·DDS와 내부 Web Bridge를 설치·노출하지 않는다.

#### FR-51. 업로드 인증과 입력 검증

**우선순위: Must**

- `Authorization: Bearer <device-token>`과 TLS 인증서 검증을 강제하고 누락·오류는 401이다.
- 원문 token은 Raspberry Pi `/etc/thing/uploader.env`의 0600 파일에만 두고, EC2에는 비교용 token hash를 0600 systemd EnvironmentFile로 주입한다. 어느 값도 Git·이미지·Compose·로그에 넣지 않는다.
- 서버가 파일명·경로를 생성하고 part, content type, schema, header, 행 수, 유한값, 크기, hash와 robot ID를 검증한다.
- part 상한은 metadata 256KiB, HandCommand 20MiB, MotorStatus 60MiB, 세 파일 합계 80.25MiB다. Django request 85MiB, Nginx body 90MiB로 고정한다.
- 기록 상한은 기본 60분이며 초과 전에 정상 종료·판정 절차로 넘어간다.

#### FR-52. EC2 네이티브 배포와 상태 확인

**우선순위: Must**

EC2에는 Docker·Compose를 사용하지 않는다.

- Nginx: `web/ec2-portal/frontend` React 정적 파일·HTTPS·reverse proxy
- Gunicorn+Django: `web/ec2-portal/backend`, Python venv와 systemd
- SQLite·파일: `/var/lib/thing-data`, 서비스 재시작·EC2 재부팅 후 유지
- 공개 인바운드: 443만. 관리용 22는 팀 고정 IP로 제한하며 DDS port는 열지 않는다.
- `/health`는 Django, SQLite 접근과 데이터 디렉터리 쓰기 가능 시 200을 반환하되 경로·비밀정보를 노출하지 않는다.
- React build, Django test·deploy check, native 배포 절차와 재부팅 복구 시험은 Must다. GitLab CI 수동 운영 배포와 자동 rollback은 Should다.

### 3.10 배포 및 실행 환경

#### FR-53. Jetson·Raspberry Pi Docker 실행

**우선순위: Must**

Docker 적용 대상은 Jetson과 Raspberry Pi로 제한하고 Compose는 Raspberry Pi에서만 사용한다.

- Laptop: Docker 없이 `web/internal-control/frontend`의 Vite+React를 native로 실행하고 Jetson의 Web Bridge·MJPEG에 내부망으로 연결한다.
- Jetson: 버전 관리된 Dockerfile과 `docker run` 스크립트로 vision·MJPEG·Web Bridge 컨테이너를 실행한다. Compose 금지.
- Raspberry Pi: 버전 관리된 Docker Compose로 `thing-control`과 격리된 `thing-data-uploader`를 `docker compose up -d` 한 번에 시작한다.
- `thing-control`은 manager·guard·safety·DYNAMIXEL·Logger와 Logger 측 exporter를 포함한다. rosbag2 원본은 이 서비스만 읽는다.
- `thing-data-uploader`는 `/run/thing-uploader/uploader.sock`의 private Unix socket으로 전달된 완료 job만 받고 임시 세 파일 디렉터리를 읽기 전용으로 mount한다. rosbag2·모터 장치·제어 publish 권한을 갖지 않고 외부 HTTPS만 사용한다.
- 카메라는 Jetson 컨테이너에만, U2D2는 Raspberry Pi control 서비스에만 연결한다.
- rosbag2·로그는 Raspberry Pi의 제한된 영속 bind mount로 관리하고 임시 업로드 디렉터리는 용량을 제한한다. 별도 SQLite·`session_state.json`·영구 spool 볼륨은 만들지 않는다.
- ROS_DOMAIN_ID, 장치·저장 경로와 EC2 URL은 외부 설정으로, 토큰은 0600 env 파일로 주입한다.
- restart 정책 뒤 항상 INIT에서 시작하며 이전 명령·mode·owner·녹화·upload job을 재생하지 않는다.
- 기능별 추가 컨테이너 분리와 CI 이미지 자동 태그는 Should다.
- Jetson 컨테이너의 노드 목록, 카메라 장치 mount, MJPEG HTTP port 명시

EC2와 개발 Laptop은 FR-53 Docker 범위에 포함하지 않는다. 구현 일정과 Jira 작업 분해는 요구사항 명세가 아니라 Jira/WBS에서 관리한다.

```
물리 ESTOP > FAULT > SAFE > HOLD
> STOP·lease 만료 > active mode의 일반 명령
```

안전 전이와 STOP은 Gesture·Action·일반 명령을 취소한다. 동시에 온 mode 획득은 한 요청만 수락하며 다른 owner는 거부한다.

### 4.7 직접 EC2 업로드 흐름

```
판정 완료 rosbag2
→ thing-logger exporter: metadata.json + hand_command.csv + motor_status.csv 임시 생성
→ schema·행 수·SHA-256·content_digest 검증
→ private Unix socket으로 완료된 세 파일 job 전달
→ 격리된 uploader가 Bearer Token HTTPS POST
→ EC2 STAGING 검증
→ 파일 atomic rename + EC2 SQLite READY transaction
→ 로그인 없는 GET 조회·다운로드
→ 응답 content_digest 일치 확인 후 로봇 임시 세 파일 삭제
```

영구 로컬 spool과 자동 장애 복구는 사용하지 않는다. 업로드 실패는 진단 로그에 남기고 임시 세 파일을 정리한다. 필요하면 운영자가 `ros2 run thing_logger reupload_session --bag <bag_path> --result SUCCESS|FAILURE`로 rosbag2에서 세 파일을 재생성해 수동 재업로드하며 제어와 안전 executor를 기다리게 하지 않는다.

### 4.8 EC2 네이티브 배치

Nginx는 `web/ec2-portal/frontend`의 React 정적 파일과 HTTPS를 제공하고 `web/ec2-portal/backend`의 Gunicorn·Django는 systemd로 실행한다. SQLite와 세 파일은 `/var/lib/thing-data`에 영속한다. 공개 443 외의 DDS·제어 포트는 열지 않고, 관리 SSH는 팀 고정 IP만 허용한다.

### 4.9 두 웹사이트 역할 및 저장소 경계

```
web/
├─ internal-control/
│  └─ frontend/        # Laptop native Vite + React
└─ ec2-portal/
   ├─ frontend/        # EC2 Nginx가 제공하는 React build
   └─ backend/         # EC2 Django REST API

thing_ws/src/thing_web_bridge/  # Jetson ROS 2 ↔ WebSocket Bridge
```

- 내부망 웹: Laptop 브라우저가 Jetson MJPEG와 `/ws/robot-state` WebSocket을 통해 ROS 2의 실시간 영상·상태를 받고 MIMIC·MANUAL·기록 요청을 보낸다. rosbag2와 DB는 실시간 통신 경로가 아니다.
- 로봇 uploader: 판정 완료 세 파일을 Bearer Token HTTPS POST로 EC2 Django API에 전송한다.
- EC2 포털: 브라우저가 HTTPS 공개 GET으로 Django API를 호출하고 EC2 SQLite·파일 디렉터리에 저장된 READY 세션을 조회·다운로드한다.

- `thing_vision`과 `thing_web_bridge`의 노드별 책임

## 5. 비기능 요구사항

### 5.1 성능·기구 품질

#### NFR-01. 영상 처리 성능

**우선순위: Must**

검출은 평균 20FPS 이상, 유효 MIMIC HandCommand는 20Hz 이상이어야 한다.

camera 30FPS, MediaPipe 평균 20FPS, HandCommand 20Hz를 분리 측정

#### NFR-02. 응답 지연

**우선순위: Must**

카메라 frame 시각부터 최초 MotorStatus 반응까지 30회 P95 300ms 이하여야 한다.

카메라 `header.stamp`부터 MotorStatus까지 P95 300ms 측정

#### NFR-03. 내구성

**우선순위: Must**

텐던 이탈·부품 파손 없이 10분 연속 시연해야 한다.

#### NFR-04. 파지 성공률

**우선순위: Must**

원통과 집기 물체를 각각 10회 시험해 7회 이상 3초 유지해야 한다.

### 5.2 신뢰성·안전

#### NFR-05. 명령 유효성

**우선순위: Must**

FR-32의 source·stamp·sequence·유한값·범위 검사를 통과하지 못한 명령은 모터에 전달하지 않는다.

#### NFR-06. 고장 격리

**우선순위: Must**

모터·Logger·uploader·웹 하나의 장애가 전체 프로세스와 물리 E-Stop을 무력화하지 않아야 하며 원인을 식별할 수 있어야 한다.

MJPEG/Web 장애가 MediaPipe·MIMIC 명령을 막지 않아야 함

#### NFR-07. 기구 안전

**우선순위: Must**

스프링 과신장, 텐던 이탈, 손가락 물리 범위 초과와 검증되지 않은 토크를 구조·설정으로 제한한다.

### 5.3 사용성·운영

#### NFR-08. 실행 편의성

**우선순위: Must**

Laptop 내부 제어 웹은 문서화된 Vite 실행 명령, Jetson은 `docker run` 스크립트, Raspberry Pi는 `docker compose up -d`, EC2는 systemd 절차로 시작·상태 확인·중지할 수 있어야 한다.

#### NFR-09. 상태 확인

**우선순위: Must**

Laptop 내부망 웹에서 손 검출, mode·owner, 연결, SafetyState, RecordingState를 확인하고 상세 원인은 diagnostics·로그에서 확인한다.

각 Vision 노드의 실행·연결 상태 확인

### 5.4 유지보수·확장

#### NFR-10. 모듈 분리

**우선순위: Should**

vision, 제어·안전, hardware, Logger, uploader, 웹과 EC2를 책임별로 분리한다. Must 통합을 지연시키는 추가 package 리팩터링은 이월한다.

캡처·검출·7축 계산·영상 송출 책임 분리

#### NFR-11. 설정 분리

**우선순위: Must**

FR-41의 motor·gesture·timeout·fault 설정은 코드와 분리하고 유효성 검사·기본값·단위를 문서화한다.

#### NFR-12. 향후 센서 확장

**우선순위: Could — 2주 범위 밖**

관절각·스프링·촉각·힘 센서 확장은 기존 MVP 스키마를 임의 변경하지 않고 별도 버전에서 검토한다.

### 5.5 내부망 웹

#### NFR-13. 화면 응답

**우선순위: Should**

버튼 반영 200ms, 손·7축 10Hz, 모터·상태 5Hz를 목표로 하며 UI 갱신이 ROS 20Hz 명령을 막지 않는다.

#### NFR-14. 영상 표시

**우선순위: Should**

MJPEG 평균 15FPS·지연 500ms 이하를 목표로 하고 영상 지연은 제어 경로와 분리한다.
서로 다른 프레임의 image와 landmark를 합성하지 않도록 규칙 

#### NFR-15. 제어 안정성

**우선순위: Must**

중복·stale 요청을 실행하지 않고 새로고침·종료·연결 단절 시 lease가 만료되어 안전 전이한다. 재연결은 이전 명령을 재생하지 않는다.

#### NFR-16. 웹 장애 독립성

**우선순위: Must**

웹·MJPEG·Web Bridge 장애 중에도 Raspberry Pi의 범위·속도·timeout·E-Stop 판단은 계속 동작한다.

#### NFR-17. 사용성

**우선순위: Should**

MIMIC·MANUAL, 현재 mode, STOP, 편 손·주먹·파지·집기와 정상·경고·오류를 구분해 표시한다.

#### NFR-18. 화면 구성

**우선순위: Could**

고정 상태 바, 게이지·그래프, 반응형 상세 패널과 장식성 개선은 Must 화면 뒤 진행한다.

#### NFR-19. 호환성

**우선순위: Could**

데스크톱 Chrome 최신 버전을 Must 검수 기준으로 삼고 추가 브라우저·반응형 범위는 후순위다.

#### NFR-20. 내부망 제어 보안

**우선순위: Must**

제어 웹과 Web Bridge는 내부망에만 두고 임의 ROS topic·motor ID 입력과 외부 인터넷 제어 API를 금지한다.

#### NFR-21. 유지보수성

**우선순위: Should**

UI, WebSocket adapter, 상태 store와 preset을 분리해 웹 변경이 hardware 코드를 직접 바꾸지 않게 한다.

#### NFR-22. 이벤트 로그

**우선순위: Should**

mode, 명령, 기록, 연결, 손 미검출, fault·E-Stop과 결과를 timestamp와 함께 회전 로그로 남긴다. 실패가 제어를 중단시키지 않는다.

#### NFR-23. 복구 가능성

**우선순위: Must**

손 재검출이나 연결 복구 뒤 시스템과 웹은 현재 SafetyState·mode·owner·원인을 다시 조회하고 FR-35의 현재 상태별 절차를 따라야 한다.

- HOLD에서는 사용자가 `SetControlMode(MODE_DISABLED, OWNER_NONE)`으로 명시적 STOP을 요청하고 READY 전환 뒤 MIMIC mode와 owner를 새로 획득해야 한다.
- SAFE·FAULT·ESTOP에서는 원인 해소와 안정 시간, `/thing/reset_safety`, INIT 재검사와 READY 전환을 완료한 뒤 MIMIC mode와 owner를 새로 획득해야 한다.
- 어느 경로에서도 이전 command, Gesture, Sequence(Action) 및 recording을 자동 재개하지 않고 새 활성화 이후의 신선한 HandCommand만 실행해야 한다.

### 5.6 공통 보안 경계

내부망 제어와 EC2 공개 데이터 포털을 분리한다. 외부 인터넷에는 HTTPS 443의 저장 데이터 GET과 장치 upload POST만 공개하고 로봇 제어 REST·WebSocket·DDS를 제공하지 않는다. 이 절은 FR-28·50·51의 공통 원칙이며 세부 API는 6.5절을 따른다.

### 5.7 EC2 데이터 포털

#### NFR-24. 부하 성능

**우선순위: Could**

READY 100세션 목록·상세 P95 3초와 고급 downsampling 부하 시험은 2주 최소 검수 밖이다. 대표 세션 정상 조회·다운로드는 Must다.

#### NFR-25. 다운로드 무결성

**우선순위: Must**

서버가 저장한 세 파일의 SHA-256과 실제 파일이 일치하고, metadata에 기록된 두 CSV의 행 수·크기·SHA-256이 실제 CSV와 일치하는 READY만 제공해야 한다. 반복 GET은 원본을 바꾸지 않아야 한다.

#### NFR-26. 업로드 신뢰성

**우선순위: Must**

동일 `(robot_id, session_id)`와 동일 `content_digest`는 중복 없이 200, 같은 key의 다른 `content_digest`는 409다. STAGING 부분 파일은 공개하지 않고 crash 뒤 재조정할 수 있어야 한다.

#### NFR-27. 인증·공개 데이터 보호

**우선순위: Must**

업로드만 Bearer Token으로 인증하고 공개 GET은 로그인 없이 읽기 전용으로 제공한다. 토큰·내부 경로·IP·영상·landmark·상태 이력을 공개 데이터와 로그에서 제외한다.

#### NFR-28. 제어와 업로드 장애 독립성

**우선순위: Must**

exporter·uploader·EC2 업로드 실패가 ROS 제어·SafetyState·rosbag2를 중단하거나 지연시키지 않아야 하며 실패 원인을 진단 로그에 남겨야 한다. 인터넷 단절 중 영구 보관과 자동 재시도는 2주 MVP 범위에서 제외한다.

#### NFR-29. 저장 공간과 지속성

**우선순위: Must**

로봇은 rosbag2 원본과 용량이 제한된 임시 업로드 디렉터리만 사용하며 별도의 애플리케이션 SQLite·상태 파일·영구 spool을 만들지 않는다. 업로드 성공 후 임시 세 파일을 삭제하고 rosbag2는 별도 보존 정책을 따른다. EC2 SQLite와 세 파일은 systemd 재시작·EC2 재부팅 뒤 유지한다. S3·자동 공개 삭제는 2주 범위 밖이다.

- 실행 위치: Raspberry Pi의 `thing-control` 실행 환경과 프로젝트 내부망
- 외부 노출: EC2·외부망·공개 REST API·공개 WebSocket에 노출하지 않음

`/thing/reset_safety`는 프로젝트의 ROS 2 인터페이스 계약이지만 커스텀 `thing_interfaces` 타입은 아니다. 표준 Trigger 타입을 사용하므로 `thing_interfaces/srv/ResetSafety.srv`를 추가하지 않고 `thing_interfaces/CMakeLists.txt`의 인터페이스 생성 목록도 변경하지 않는다. `thing_interfaces`는 메시지 7종·서비스 5종·액션 1종을 그대로 유지한다.

실제 서비스 서버는 `thing_control` 패키지의 `safety_manager`가 담당한다. `thing_control/package.xml`은 표준 Trigger 타입을 사용하기 위한 `std_srvs` 실행 의존성을 가져야 한다. 이 절은 인터페이스 계약과 구현 책임을 확정하는 것이며 safety_manager의 전체 상태 머신, 하드웨어 검사, E-Stop GPIO, 모터 통신 검사 또는 통합 시험이 이미 구현됐다는 뜻이 아니다.

Trigger 의미:

- 요청 필드는 없다.
- 응답 `success`는 Reset 요청의 수락 여부다.
- 응답 `message`는 수락 또는 거부 이유다.
- 호출 의미는 현재 SAFE·FAULT·ESTOP 원인과 안정시간을 다시 검사하고, 조건을 만족하면 INIT 전체 재검사를 시작해 달라는 요청이다.
- `success=true`는 INIT 검사 통과나 READY 도달을 보장하지 않는다. 최종 진행 상태는 `/thing/safety_state`로 확인한다.

허용 상태와 안정시간:

- SAFE·FAULT·ESTOP에서만 복구 요청으로 사용한다.
- HOLD에서는 Safety Reset을 사용하지 않고 `SetControlMode(MODE_DISABLED, OWNER_NONE)`의 명시적 STOP 절차를 사용한다.
- SAFE·FAULT 원인은 해소 뒤 `fault_clear_stable_ms=1000`을 만족해야 한다.
- E-Stop은 물리 해제 뒤 `estop_release_stable_ms=500`을 만족해야 한다.
- 원인이나 안정시간 조건을 만족하지 않으면 `success=false`와 거부 이유를 반환하고 현재 안전 상태를 유지한다.

Reset이 수행하지 않는 동작:

- 물리적 E-Stop 해제
- 모터 토크 즉시 활성화
- 이전 mode 또는 owner 복원
- 이전 명령·Gesture·Sequence·queue 재실행
- 이전 녹화 자동 재개
- 즉시 READY 또는 RUN 전환

Reset 요청이 수락되면 INIT 전체 재검사를 시작한다. 검사를 통과하면 토크 OFF·mode=`DISABLED`·owner=`NONE`인 READY까지만 전환한다. RUN으로 전환하려면 새로운 mode·owner 획득과 활성화 이후의 새로운 유효 명령이 필요하다.

현재 구현 상태:

- 서비스 이름·타입 결정: 완료
- 담당 패키지·노드 결정: 완료
- 커스텀 `ResetSafety.srv`를 만들지 않는 결정: 완료
- 요구사항 명세서 V6.2 반영: 완료
- GitLab `docs/interfaces.md`와 `thing_control` dependency 반영: 진행 중
- `safety_manager` 서비스 서버 구현: 후속 작업
- 안정시간 및 상태 전이 구현: 후속 작업
- E-Stop GPIO와 모터 상태 연동: 후속 작업
- 통합 테스트: 후속 작업

따라서 MVP에서 사용할 Safety Reset 인터페이스 계약은 확정됐지만 실제 `/thing/reset_safety` 서버와 전체 안전 기능은 아직 구현 완료 상태가 아니다.

- MVP 기본값: 나머지 command Reliable depth 1, MotorStatus Reliable depth 5, ControlState Reliable Transient Local
- 미확정 QoS 튜닝값은 GitLab 확정값으로 오인하지 않도록 `docs/interfaces.md`에 프로젝트 결정으로 기록한다.

#### 내부망 WebSocket

요청은 `request_id`, `type`, `timestamp`, `payload`, 응답은 같은 `request_id`, `accepted`, `reason`을 포함한다. type별 payload는 ROS 2 필드명·상수를 재사용하고 별도 인터페이스 문서에서 동결한다. WebSocket은 임의 topic·motor ID를 받지 않는다.

### 6.4 통신 인터페이스

- Jetson–Raspberry Pi: 내부 Wi-Fi의 ROS 2 Humble DDS, 같은 ROS_DOMAIN_ID
- 내부망 웹: Laptop 브라우저 ↔ Jetson MJPEG·Web Bridge WebSocket ↔ ROS 2. 실시간 영상·상태·제어 요청 경로이며 rosbag2나 DB를 조회하지 않음
- 제어: manager가 입력 하나를 선택하고 guard만 최종 command 발행
- 기록: 로봇 로컬 rosbag2만 사용하고 웹은 기록 서비스를 호출함
- 업로드: Raspberry Pi uploader가 완료된 세 파일만 Bearer Token outbound HTTPS POST로 Django API에 전송함
- EC2 포털: 사용자 브라우저가 HTTPS 공개 GET으로 Django API를 호출하고 EC2 SQLite와 파일 디렉터리의 READY 데이터만 조회·다운로드함
- EC2: ROS 2 DDS에 참여하지 않고 로봇으로 향하는 연결을 만들지 않음
- 로봇은 EC2 SQLite 파일에 직접 접속하지 않고 HTTPS upload API만 호출하며, Django가 검증 후 EC2 SQLite와 파일 디렉터리를 갱신함

#### 내부망 WebSocket 상태 snapshot v1

Jetson Web Bridge의 서버→클라이언트 endpoint는 `/ws/robot-state`로 고정한다. Laptop frontend는 `WS_URL` 설정으로 내부망 주소를 주입한다. 메시지는 UTF-8 JSON object이며 top-level 형식은 다음과 같다.

```json
{
  "timestamp": "2026-07-23T12:00:00Z",
  "mode": "MIMIC",
  "recording_state": "RECORDING",
  "landmarks": {},
  "motor_state": {},
  "safety_state": {}
}
```

- `timestamp`: Web Bridge가 snapshot을 생성한 RFC 3339 UTC `Z` 시각
- `mode`: `DISABLED|MIMIC|MANUAL|TELEOP`
- `recording_state`: 현재 RecordingState의 symbolic state
- `landmarks`: 최신 HandLandmarks 기반 표시 객체
- `motor_state`: 최신 7개 모터 상태의 표시 객체
- `safety_state`: 현재 SafetyState·원인·reset 가능 여부의 표시 객체
- 아직 유효 데이터를 받지 못한 객체는 `null` 대신 `{}`를 사용한다. 새 snapshot은 같은 연결의 이전 snapshot을 대체한다.
- 이 top-level 여섯 필드는 MVP 계약으로 고정한다. 세 객체의 세부 field와 클라이언트→서버 mode·gesture·recording 요청 JSON은 개발 중 확정하되 기존 ROS 2 서비스·액션에만 매핑하고 통합 시험 전에 `docs/interfaces.md`에 동결한다.
- `landmarks`의 출처가 `web_bridge_node`의 `/thing/landmarks` 구독

### 6.5 데이터 저장·EC2 REST 인터페이스

#### 로봇 로컬 저장과 실행 중 상태

로봇에는 별도의 애플리케이션 SQLite, `session_state.json`, 영구 upload outbox 및 spool을 두지 않는다.

- 경로: `ROBOT_DATA_DIR=/var/lib/thing-robot-data`
- 영구 저장 대상: rosbag2 원본과 회전 로그
- 임시 저장 대상: `/var/lib/thing-robot-data/tmp-upload/{session_id}/`의 metadata JSON·HandCommand CSV·MotorStatus CSV
- ROS 2 Humble의 rosbag2가 내부 기록 파일로 `.db3`를 생성할 수 있으나 이는 rosbag2 저장 포맷이며 세션·조회·업로드 상태를 관리하는 애플리케이션 DB가 아니다.
- 활성 Session ID, bag path, 기록 상태와 판정 대기는 Logger 실행 중 메모리와 RecordingState로 관리한다. 정상 Stop 후에는 `RecordingState.state=COMPLETED`, `result_pending=true`로 판정을 기다린다.
- StartRecording은 고유 Session ID·경로 확보와 rosbag2 시작이 모두 성공할 때만 수락한다.
- SetMimicResult 수락 후 `thing-control`의 Logger 측 exporter가 rosbag2를 읽어 임시 세 파일을 생성·검증한다. export와 HTTPS POST는 제어·안전 callback을 차단하지 않는다.
- exporter는 세 파일을 최종 파일명으로 rename한 뒤 완료 파일 경로와 `content_digest`를 `/run/thing-uploader/uploader.sock`의 private Unix socket으로 전달한다.
- `thing-data-uploader`는 rosbag2를 mount하지 않고 임시 세 파일 디렉터리를 읽기 전용으로 mount한다. uploader는 전달받은 완료 세 파일만 HTTPS POST한다.
- `200`·`201` 응답의 `content_digest`가 요청값과 일치하면 exporter가 임시 세 파일을 삭제한다.
- 실패 시 임시 세 파일을 정리하고 진단 로그를 남긴다. 프로세스 재시작 전 상태와 실패 upload를 자동 복원하지 않는다.
- 수동 재업로드는 `ros2 run thing_logger reupload_session --bag <bag_path> --result SUCCESS|FAILURE`를 사용한다. CLI는 rosbag2의 RecordingState에서 Session ID를 확인하고 `--result`가 없거나 허용값이 아니면 실패한다.

#### HTTPS REST API

```
POST /api/v1/uploads/sessions
GET  /api/v1/sessions
GET  /api/v1/sessions/{session_id}
GET  /api/v1/sessions/{session_id}/data?dataset=hand_command|motor_status&cursor=&limit=
GET  /api/v1/sessions/{session_id}/download/{file_kind}
GET  /health
```

- POST만 `Authorization: Bearer <device-token>`과 `Idempotency-Key: <robot_id>:<session_id>:<data_version>:<content_digest>`를 요구한다.
- public GET은 IP당 분당 120회, upload POST는 token당 분당 10회를 기본으로 제한하고 초과 시 `429`와 `Retry-After`를 반환한다.
- GET은 로그인 없이 READY만 읽기 전용으로 제공한다.
- `file_kind`는 `metadata|hand_command|motor_status` enum이며 경로 입력을 받지 않는다.
- 목록 기본 20개·최대 100개, `started_at DESC, session_id DESC`
- exact Session ID 검색은 Must; 날짜·결과 필터와 cursor pagination은 Should
- data 기본 1000행·최대 5000행, timestamp 오름차순; 결측 숫자는 JSON `null`

#### metadata JSON schema v1

```json
{
  "schema_version": 1,
  "data_version": 1,
  "robot_id": "THING-001",
  "session_id": "123456789012345678",
  "started_at": "2026-07-29T00:00:00.000Z",
  "ended_at": "2026-07-29T00:01:00.000Z",
  "exported_at": "2026-07-29T00:01:05.000Z",
  "result": "SUCCESS",
  "interface_commit": "70dfdab8d555dfbfdd471c5acca4f30a8a8fc3ec",
  "time_sync": true,
  "content_digest": "sha256:hex-64",
  "files": {
    "hand_command": {
      "filename": "session_123456789012345678_hand_command.csv",
      "size_bytes": 1234,
      "row_count": 1200,
      "sha256": "hex-64"
    },
    "motor_status": {
      "filename": "session_123456789012345678_motor_status.csv",
      "size_bytes": 5678,
      "row_count": 4200,
      "sha256": "hex-64"
    }
  }
}
```

- Session ID는 ROS `uint64`지만 JSON·API·EC2 SQLite에서는 문자열이다.
- 시간은 RFC 3339 UTC `Z`, `ended_at>started_at`; result는 SUCCESS 또는 FAILURE다.
- `schema_version`과 `data_version`은 이번 MVP에서 1로 고정한다.
- `content_digest`는 `exported_at`과 `content_digest` 자신을 제외한 metadata의 의미 필드 전체를 key 오름차순·공백 없는 UTF-8 canonical JSON으로 직렬화한 뒤 SHA-256으로 계산한다. 두 CSV의 filename·size_bytes·row_count·sha256은 계산 대상에 포함한다.
- 따라서 같은 rosbag2와 같은 SUCCESS·FAILURE 판정은 수동 재생성 시 `exported_at`이 달라져도 같은 `content_digest`를 가져야 한다.
- 서버는 metadata와 실제 두 CSV를 검증해 `content_digest`를 다시 계산한다. token의 robot과 `robot_id`가 일치해야 한다.
- 장치 token은 최소 32바이트 CSPRNG로 생성하고 EC2에는 hash만 비교 가능한 형태로 보관한다. 유출 시 교체한다.

#### CSV 규칙

UTF-8 without BOM, RFC 4180 quoting, comma, header 1행, LF, 소수점 `.`, bool `true|false`를 사용한다. NaN·Infinity를 금지하고 읽기 실패 숫자는 빈 칸으로 둔다. 각 행은 Session ID, UTC Unix stamp와 `elapsed_ms`를 포함하며 timestamp는 비감소여야 한다.

HandCommand CSV:

```
session_id,stamp_sec,stamp_nanosec,elapsed_ms,sequence,source,thumb_flex,thumb_opp,thumb_abd,index_flex,middle_flex,ring_flex,little_flex,speed_limit,confidence
```

MotorStatus CSV:

```
session_id,stamp_sec,stamp_nanosec,elapsed_ms,frame_id,motor_id,actuator_name,goal_position_raw,present_position_raw,goal_position_rad,present_position_rad,velocity_rad_s,current_ampere,voltage_volt,temperature_celsius,hardware_error,communication_result,communication_ok,bus_communication_ok,failed_read_count
```

MotorStatus 한 수신 시각의 motor 하나를 한 행으로 평탄화한다. 자유 문자열 `MotorStatus.message`, landmark와 상태 이력은 EC2 CSV에 넣지 않는다.

#### EC2 저장·원자성

- unique key: `(robot_id, session_id)`, data version은 1 고정
- SQLite: `/var/lib/thing-data/db.sqlite3`
- 파일: `/var/lib/thing-data/sessions/{robot_id}/{session_id}/`
- staging에 streaming 저장하며 크기·content type·schema·header·행 수·SHA-256과 `content_digest`를 검증한다.
- 검증 후 같은 파일시스템의 final 경로로 원자적 rename하고 SQLite를 READY로 변경한다. 공개 API는 READY만 읽는다.
- crash 후 final 파일과 STAGING row를 대조해 READY 또는 정리 상태로 복구한다.
- 신규 key는 201, 같은 key·같은 `content_digest`는 기존 READY를 유지하고 200, 같은 key·다른 `content_digest`는 409다. 같은 digest의 200 응답에서는 기존 저장 파일을 덮어쓰지 않는다.

#### 성공·오류 응답

성공:

```json
{
  "session_id": "123456789012345678",
  "data_version": 1,
  "status": "READY",
  "content_digest": "sha256:hex-64",
  "files": {
    "metadata": {"sha256": "hex-64", "size_bytes": 980},
    "hand_command": {"sha256": "hex-64", "size_bytes": 1234},
    "motor_status": {"sha256": "hex-64", "size_bytes": 5678}
  },
  "uploaded_at": "2026-07-29T00:01:06.000Z"
}
```

uploader는 HTTP 상태만으로 성공 처리하지 않고 응답의 `session_id`, `data_version`, `status=READY`, `content_digest`가 요청과 일치하는지 확인한다. raw metadata SHA-256은 `exported_at` 때문에 수동 재생성 시 달라질 수 있으므로 로봇 임시 파일 삭제의 동일성 기준은 `content_digest`다.

오류:

```json
{"error":{"code":"SESSION_CONTENT_CONFLICT","message":"The session already exists with different content.","details":[]},"request_id":"request-uuid"}
```

`400` malformed, `401` 인증, `404` 없음, `405` 공개 쓰기, `409` 충돌, `413` 크기, `415` media type, `422` schema·값, `429` rate limit, `500` 내부, `503` DB·디스크 불가를 사용한다. 경로·토큰·stack trace를 응답에 넣지 않는다.

#### 다운로드 파일

정확히 다음 세 개만 공개한다.

- `session_{session_id}_metadata.json`
- `session_{session_id}_hand_command.csv`
- `session_{session_id}_motor_status.csv`

OpenAPI·스키마 문서는 세션의 네 번째 파일로 세지 않는다.

## 7. 시스템 제약사항

### 7.1 하드웨어 제약사항

- 손가락별 여러 관절을 하나의 모터로 구동하므로 encoder 기반 motor-axis angle은 실제 관절각이 아니다.
- 텐던 마찰·늘어남·초기장력, 스풀 반지름, 스프링과 3D 프린팅 공차가 반복성에 영향을 준다.
- 7개 모터의 순간 전류를 감당하는 별도 전원과 CPU 독립 E-Stop이 필요하다.

### 7.2 소프트웨어·배포 제약사항

- ROS 2 Humble과 develop 기준 인터페이스를 사용한다.
- Docker는 Jetson·Raspberry Pi에만 사용하고 Docker Compose는 Raspberry Pi에서만 사용한다.
- EC2는 native Nginx·Gunicorn·Django·React·SQLite를 systemd로 운영한다.
- 로봇에는 별도의 애플리케이션 SQLite·`session_state.json`·영구 upload spool을 사용하지 않는다. rosbag2의 내부 `.db3` 기록 파일은 이 제한의 대상인 애플리케이션 DB가 아니다.
- MediaPipe는 조명·가림·카메라 각도의 영향을 받으며 MVP는 학습 기반 관절 추론을 사용하지 않는다.

### 7.3 네트워크 제약사항

- 내부 Wi-Fi 지연·손실은 제어 안전 조건으로 취급한다. 인터넷 단절 중 업로드 보존·자동 복구는 2주 MVP 범위에서 제외한다.
- Raspberry Pi 안전 판단은 Jetson·웹·EC2 연결에 의존하지 않는다.
- ROS 2 입력은 최신 유효 명령만 사용하고 재연결 뒤 stale 명령을 실행하지 않는다.
- uploader는 outbound HTTPS만 사용하고 EC2는 DDS에 참여하지 않는다.

### 7.4 일정·범위 제약사항

- 잔여 개발 기간은 2주다.
- Must는 통합·실물 검수까지 완료하고 Should는 Must 통과 후 진행한다.
- FR-39·44·45, 고급 차트·필터·부하 시험·다중 data version·rosbag 공개·S3는 최소 검수에서 제외한다.
- 하드웨어·ROS 2·웹·EC2는 병렬 개발하되 최종 주 이전에 최소 한 번 통합한다.

### 7.5 전제조건과 의존성

- U2D2·7모터·전원·카메라·E-Stop 회로가 준비되어야 한다.
- 한 번에 한 사용자의 오른손과 사전 지정 위치의 시험 물체만 지원한다.
- UTC NTP 동기화, EC2 domain·TLS 인증서, 장치 Token과 팀 고정 관리 IP가 필요하다.
- rosbag2·임시 업로드 파일·EC2 저장 파일을 위한 디스크 용량을 사전에 확보한다.

### 7.6 EC2·업로드 제약사항

- 단일 로봇의 판정 완료 세션과 schema/data version 1만 지원한다.
- 공개 파일은 정확히 세 개이고 landmark·상태 이력·영상·rosbag2는 제외한다.
- EC2 업로드 실패가 로봇 제어·안전을 중단하지 않아야 한다. 로봇에는 영구 미전송 queue를 두지 않으며 필요하면 보존된 rosbag2에서 세 파일을 수동 재생성·재업로드한다.
- 성공한 임시 세 파일은 삭제하고 실패 후 남은 임시 파일은 정리할 수 있다. rosbag2 원본은 별도 보존 정책을 따른다.
- EC2 공개 데이터의 최종 기준은 READY SQLite row와 final 파일 디렉터리다.
- 공개 443, 제한된 관리 22 외 포트를 열지 않는다.

## 8. 품질 속성 및 검증 기준

### 8.1 Must 품질 지표

- 손 검출: 300~700lux, 40~80cm, 오른손 60초 시험에서 평균 20FPS·유효 검출 90% 이상
- 명령: 60초 MIMIC에서 유효 HandCommand 20Hz 이상, stamp 역행·sequence 중복 실행 0건
- 종단 지연: 카메라 frame부터 최초 MotorStatus 반응 30회 P95 300ms 이하
- 파지: 지정 원통과 집기 물체 각각 10회 중 7회 이상 3초 유지
- 손 미검출: confidence 0.70 미만 또는 미검출 150ms 뒤 발행 중단, 자동 재개 0건
- 명령 단절: 20회에서 HOLD 300ms±100ms, SAFE 1000ms±100ms, stale 재실행 0건
- lease: 갱신 중단 뒤 3000ms±200ms에 owner NONE·mode DISABLED·큐 취소
- Safety Reset: HOLD와 원인 유지 중 수락 0건, SAFE·FAULT 원인 해소 1000ms 또는 E-Stop 물리 해제 500ms 뒤 요청 수락·INIT 재검사·READY, 토크·mode·owner·RUN 자동 복원 0건
- E-Stop: INIT·READY·RUN·SAFE에서 CPU와 무관한 전원 차단, 물리 해제만으로 재동작 0건
- 로봇 로컬 저장: 별도 애플리케이션 SQLite·`session_state.json`·영구 spool 생성 0건, rosbag2 원본과 임시 세 파일만 생성
- 직접 업로드: 정상 네트워크에서 판정 수락 후 5초 안에 upload 시도 시작
- 실패 처리: upload 실패가 제어·rosbag2를 중단하지 않고 진단 로그에 남으며 `reupload_session --bag <bag_path> --result SUCCESS|FAILURE`로 같은 rosbag2를 수동 재생성·재업로드 가능
- 세 파일: 대표 60초 세션의 schema·Session ID·UTC·row count·SHA-256과 재계산한 `content_digest` 일치
- 멱등성: 같은 key·같은 `content_digest` 재업로드 200·중복 0, 같은 key·다른 `content_digest` 409, 부분 공개 0
- 공개 포털: 대표 세션 목록·상세·기본 표/차트와 정확히 세 파일 다운로드 성공
- 지속성: Raspberry Pi container 재시작 뒤 이전 recording·판정·upload 자동 재개 0건, EC2 service 재시작과 EC2 재부팅 뒤 READY 데이터 유지
- fan-out, timestamp, overlay 동기화, MJPEG 장애 독립성, 영상 미저장 시험

### 8.3 최소 검수 조건

다음은 모두 pass여야 MVP 완료다.

1. 모든 Must FR과 Must NFR이 구현되고 develop 커밋 기준 `colcon build`·인터페이스·관련 package test가 통과한다.
2. `/thing/reset_safety` 계약과 SetControlMode lease·STOP 의미가 `docs/interfaces.md`에 반영되고, `thing_control`의 `std_srvs` dependency·`safety_manager` 서비스 서버 구현 및 관련 package test가 후속 MR에서 통과한다.
3. 7논리축 20Hz·P95 300ms와 원통·집기 7/10, 3초 기준을 통과한다.
4. hand loss·명령 단절·lease·FAULT·E-Stop 시험에서 이전 명령·토크·녹화 자동 재개가 0건이다.
5. 로봇에 별도 애플리케이션 SQLite·`session_state.json`·영구 spool이 없고, 활성 세션은 메모리·RecordingState로만 관리되며 재시작 뒤 이전 작업을 자동 재개하지 않는다.
6. 대표 세션 판정 뒤 즉시 업로드되고 metadata JSON·HandCommand CSV·MotorStatus CSV 정확히 세 개만 READY로 공개된다.
7. 세 파일의 Session ID·UTC·schema·row count·SHA-256과 `content_digest`가 일치하고 제외 데이터·민감정보가 없다.
8. 인증 401, 공개 쓰기 405, 크기 413, schema 422, 같은 key의 다른 `content_digest` 409와 EC2 STAGING crash 복구가 계약대로 동작한다.
9. Laptop 내부망 웹은 Jetson `/ws/robot-state` WebSocket·MJPEG로 ROS 2 실시간 데이터를 받고, EC2 포털은 HTTPS 공개 GET으로 EC2 READY 데이터만 조회하며 두 웹 모두 DB나 ROS 2 DDS 경계를 우회하지 않는다.
10. Laptop Vite, Jetson Docker, Raspberry Pi Compose, EC2 native systemd가 문서화한 명령으로 기동하고 EC2 재시작 뒤 READY 데이터가 유지된다.
11. 10분 연속 동작에서 치명적 fault·기구 파손·텐던 이탈이 없고 시험 로그·설정·결과를 GitLab 또는 Jira에 남긴다.

Should·Could 미완료는 위 Must 검수를 막지 않는다.
