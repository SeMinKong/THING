## 1. 프로젝트 개요

### 1.1 프로젝트 배경 및 목적

본 프로젝트는 카메라로 사용자의 실제 손 자세를 인식하고, 텐던 방식으로 구동되는 3D 프린팅 로봇 손이 해당 동작을 실시간으로 따라 움직이도록 구현하는 것을 목적으로 한다.

기존의 정교한 로봇 손은 손가락 관절마다 별도의 모터와 센서를 사용하기 때문에 가격, 무게, 제작 난도가 높다. 본 프로젝트에서는 각 손가락의 여러 관절을 하나의 모터로 함께 구동하는 underactuated 구조를 적용하여 제한된 기간과 자원 안에서 사람 손의 주요 동작을 재현한다.

B2C로 손가락의 움직임 데이터를 확보한 뒤 B2B로 foundation 모델을 제공한다.

최종적으로 다음 기능을 시연하는 것을 목표로 한다.

- 실제 손의 펴기와 쥐기, 카판지 엄지 대립 검사 동작 모방
- 원통형 물체 파지
- ROS 2 기반 무선 제어
    - - MediaPipe landmark, 6채널 목표 명령 및 모터 상태 기록
- 웹을 통해 로봇손 조작모드와 모방모드를 시연할 수 있다.
- 추후 손 동작 테스트 해보고 추가
- 엄지와 검지를 이용한 집기
- 통신 단절 시 안전 동작

프로젝트 개발 기간은 총 3주이며, vision을 통한 손가락 동작 모방과 반복 가능한 파지 성능 확보를 우선한다.

### 1.3 제품 및 시스템 기능 요약

시스템은 크게 손동작 인식부, 명령 생성부, 로봇 손 제어부, 기구 구동부로 구성된다.

- 카메라와 Vision Node는 시스템 실행 중 항상 동작한다. 웹의 녹화 버튼은 카메라 실행 여부를 제어하지 않고 rosbag2 데이터 기록만 시작하거나 종료한다.

웹사이트는 MIMIC 모드와 MANUAL 모드 모두에서 영상, landmark, 6채널 목표값, 모터 상태 및 안전 상태를 관제할 수 있어야 한다.

- MIMIC 모드: 사용자의 손동작을 실시간으로 모방한다.
- MANUAL 모드: 웹 버튼으로 사전 정의 자세 또는 연속 동작을 실행한다.
- 데이터 녹화는 MIMIC 모드에서만 사용할 수 있다.
- 녹화 중에는 제어 모드를 변경할 수 없다.
1. 사용자가 웹사이트에 접속한다.
2. 모방모드에서 실시간으로 MediaPipe를 이용해 인식과 동작확인이 가능하다.
    1. RGB 카메라가 사용자의 손 영상을 입력받는다.
    2. Jetson에서 MediaPipe를 이용해 손 landmark를 검출한다.
    3. landmark를 이용해 5개 손가락 굽힘값과 엄지 대립값을 계산한다.
    4. 계산된 6채널 목표값을 ROS 2 토픽으로 발행한다.
3. 조작모드에서 실시간으로  로봇손의 조작이 가능하다.
    1. 사용자가 특정 명령(버튼, 키보드 등)을 내린다.
    2. 해당 명령에 맞는 6채널 목표값을 ROS 2 토픽으로 발행한다.
4. Raspberry Pi가 명령을 수신하고 값의 범위와 유효성을 검사한다.
5. Raspberry Pi가 목표값을 보간하고 모터 속도와 위치를 제한한다.
6. 서보가 스풀과 텐던을 당겨 로봇 손가락을 움직인다.
7. 모터 상태 및 시스템 상태를 ROS 2 토픽으로 발행하고 저장한다.

### UC-06. ROS 2 시스템 실행

1. 사용자가 장치별 launch파일을 실행한다.
2. Jetson은 `vision.launch.py` 를 실행하여 카메라, MediaPipe, 손 목표 생성, MJPEG 및 Web Bridge 노드를 실행한다.
3. Raspberry Pi는 `thing_bringup.launch.py` command manager, command guard, safety manager 및 DYNAMIXEL 제어 노드를 실행한다.
4. 사용자가 웹 또는 로컬 프로그램에서 제어 모드를 선택한다.
5. command manager가 현재 제어 모드와 제어권에 맞는 입력원 하나를 선택한다.
6. command guard가 선택된 명령의 timestamp, 범위, 속도 및 안전 상태를 검사한다.
7. 검증된 목표만 DYNAMIXEL 제어 노드에 전달한다.
8. 모터 상태, 제어 모드, 안전 상태 및 진단 정보를 ROS 2 토픽으로 발행한다.

제어 모드는 다음과 같이 구분한다.

- `DISABLED`: 일반 명령 비활성화
- `MIMIC`: MediaPipe 기반 실시간 손동작 모방
- `MANUAL`: 웹에서 Gesture 서비스와 Sequence 액션 실행
- `TELEOP`: 로컬 키보드 기반 개별축 조작

웹은 MIMIC과 MANUAL 모드 모두를 관제할 수 있다. 데이터 녹화는 MIMIC 모드에서만 허용하며 녹화 중에는 제어 모드를 변경할 수 없다.

## 3. 기능 요구사항

우선순위는 다음과 같이 구분한다.

- **Must:** MVP 완료를 위해 반드시 필요한 기능
- **Should:** 가능하면 구현해야 하지만 단순화할 수 있는 기능
- **Could:** 시간이 남을 경우 구현하는 기능

### 3.1 손 자세 인식

#### FR-01. 손 landmark 검출

**우선순위: Must**

시스템은 RGB 카메라 영상에서 사용자의 한쪽 손을 검출하고 MediaPipe 기반 21개 landmark 좌표를 생성해야 한다.

인수 조건:

- 한 번에 한 손을 검출할 수 있어야 한다.
- landmark를 카메라 영상 위에 표시할 수 있어야 한다.
- 손이 검출되지 않은 상태를 구분할 수 있어야 한다.
- 손 검출 여부와 정확도 정보를 제공해야 한다.

#### FR-02. 손가락 굽힘값 계산

**우선순위: Must**

시스템은 검지, 중지, 약지, 소지 및 엄지의 landmark를 사용하여 각 손가락의 굽힘 정도를 계산해야 한다.

인수 조건:

- 각 손가락의 굽힘값을 `0.0~1.0` 범위로 표현해야 한다.
- `0.0`은 편 상태, `1.0`은 최대 굽힘 상태로 정의한다.
- 손 크기와 카메라 거리에 따른 영향을 최소화해야 한다.
- 비정상적인 계산 결과는 허용 범위 안으로 제한해야 한다.

#### FR-03. 엄지 대립값 계산

**우선순위: Must**

시스템은 엄지 끝과 검지, 중지 및 손바닥 landmark의 상대 관계를 이용하여 엄지 대립 정도를 계산해야 한다.

인수 조건:

- 엄지 대립값을 `0.0~1.0`으로 표현해야 한다.
- 엄지가 검지 방향으로 접근하는 움직임을 구분할 수 있어야 한다.
- 손의 크기를 기준으로 거리를 정규화해야 한다.

#### FR-04. 사용자 캘리브레이션

**우선순위: Should**

시스템은 사용자마다 다른 손가락 가동범위를 보정할 수 있어야 한다.

인수 조건:

- 사용자의 편 손 자세를 최소값으로 저장할 수 있어야 한다.
- 사용자의 주먹 자세를 최대값으로 저장할 수 있어야 한다.
- 저장된 값은 손가락별 정규화에 적용되어야 한다.

- 비고
    
    사용자별 손의 값을 웹사이트 상에서 인식한 뒤 분석하고 시작함

### 3.2 명령 생성 및 전달

#### FR-05. 명령값 필터링

**우선순위: Must**

시스템은 손떨림과 landmark 오차가 모터의 급격한 움직임으로 전달되지 않도록 목표값을 필터링해야 한다.

인수 조건:

- 작은 변화는 deadband를 통해 무시할 수 있어야 한다.
- 이동평균 또는 저역통과필터를 적용해야 한다.
- 한 프레임에서 목표값이 급격하게 변경되지 않도록 제한해야 한다.

#### FR-06. ROS 2 손 명령 발행

**우선순위: Must**

Jetson은 계산된 6채널 목표값을 ROS 2 토픽으로 발행해야 한다.

권장 토픽:

```
/hand/command/mimic → command_manager → /hand/command
```

명령 데이터에는 다음 정보가 포함되어야 한다.

- 메시지 생성 시간
- 메시지 순서 번호
- 손가락별 목표값 6개
- 제어 활성화 여부
- 제어 모드
- 최대 속도 또는 속도 제한값

인수 조건:

- 명령을 초당 20회 이상 발행해야 한다.
- 오래된 명령과 최신 명령을 구분할 수 있어야 한다.
- 목표값은 사전에 정의된 범위를 벗어나지 않아야 한다.
- 제어 모드는 `ControlState.msg`로 분리함

### 3.3 모터 제어

#### FR-07. 6채널 서보 제어

**우선순위: Must**

Raspberry Pi는 6개의 서보에 개별 목표 위치를 전달해야 한다.

인수 조건:

- 각 모터는 서로 다른 ID를 사용해야 한다.
- 손가락마다 최소 및 최대 모터 위치를 설정할 수 있어야 한다.
- 6개 모터에 서로 다른 목표값을 전달할 수 있어야 한다.
- 잘못된 목표값은 모터에 전달되기 전에 제한되어야 한다.

#### FR-08. 명령 보간 및 속도 제한

**우선순위: Must**

Raspberry Pi는 Jetson에서 전달된 목표값을 모터 제어 주기에 맞춰 부드럽게 보간해야 한다.

인수 조건:

- 목표 위치가 갑자기 변경되어도 모터가 즉시 최대 속도로 이동하지 않아야 한다.
- 손가락별 최대 속도를 설정할 수 있어야 한다.
- 엄지 대립축은 일반 손가락과 별도의 속도 제한값을 사용할 수 있어야 한다.

#### FR-09. 모터 상태 수집

**우선순위: Should**

시스템은 서보에서 제공하는 상태값을 수집해야 한다.

수집 대상:

- 실제 위치
- 목표 위치
- 속도
- 전류 또는 부하 추정값
- 온도
- 통신 상태

권장 토픽:

```
/joint_states, /hand/motor_status, /hand/diagnostics
```

#### FR-10. 초기 자세 설정

**우선순위: Must**

시스템 시작 시 로봇 손이 안전하게 정의된 초기 자세로 이동해야 한다.

인수 조건:

- 시스템 시작 직후 급격한 모터 움직임이 발생하지 않아야 한다.
- 초기 자세는 편 손 또는 중립 자세로 설정할 수 있어야 한다.
- 초기 자세 이동 시 낮은 속도 제한을 적용해야 한다.

### 3.4 안전 기능

#### FR-11. 통신 timeout 감지

**우선순위: Should**

Raspberry Pi는 마지막 정상 명령을 수신한 이후 경과 시간을 지속적으로 확인해야 한다.

인수 조건:

- 200~500ms 범위에서 timeout 기준값을 설정할 수 있어야 한다.
- timeout이 발생하면 새로운 일반 명령 실행을 중단해야 한다.
- timeout 발생 여부를 시스템 상태로 발행해야 한다.

#### FR-12. 안전 상태 전환

**우선순위: Should**

통신 단절 또는 시스템 오류 발생 시 시스템은 사전에 정의된 안전 상태로 전환해야 한다.

상태는 다음과 같이 구분한다.

```
INIT
→ READY
→ RUN
→ HOLD
→ SAFE 또는 FAULT
```

- `INIT`: 시스템과 모터 초기화
- `READY`: 제어 명령 대기
- `RUN`: 정상 손동작 추종
- `HOLD`: 짧은 통신 단절 시 현재 자세 유지
- `SAFE`: 장시간 통신 단절 시 안전 자세 수행
- `FAULT`: 과전류, 과온 또는 모터 통신 오류 상태

#### FR-13. 물리적 비상정지

**우선순위: Must**

ROS 2 및 소프트웨어 상태와 관계없이 모터 전원을 차단할 수 있는 물리적 비상정지 기능을 제공해야 한다.

인수 조건:

- 비상정지 작동 시 모터 구동 전원이 차단되어야 한다.
- Jetson 또는 Raspberry Pi가 멈춘 상태에서도 작동해야 한다.
- 비상정지 해제 후 자동으로 모터가 재동작하지 않아야 한다.

#### FR-14. 과전류 및 과온 보호

**우선순위: Should**

모터가 설정된 전류 또는 온도 기준값을 초과하면 시스템은 해당 모터의 동작을 제한하거나 중단해야 한다.

### 3.5 파지 기능

#### FR-15. 편 손과 주먹 동작

**우선순위: Must**

로봇 손은 사용자의 손동작 또는 사전 정의된 명령을 통해 편 손과 주먹 자세를 수행해야 한다.

인수 조건:

- 모든 손가락이 시각적으로 구분 가능한 편 손 자세를 만든다.
- 모든 손가락이 주먹 방향으로 굽혀진다.
- 편 손에서 주먹, 주먹에서 편 손으로 반복 전환할 수 있다.

#### FR-16. 원통형 물체 파지

**우선순위: Must**

로봇 손은 손바닥과 여러 손가락을 이용해 가벼운 원통형 물체를 파지해야 한다.

인수 조건:

- 지정된 위치에 놓인 원통형 물체를 감쌀 수 있어야 한다.
- 물체를 최소 3초 이상 유지해야 한다.
- 동일 물체를 10회 시험하여 7회 이상 성공해야 한다.

#### FR-17. 집기

**우선순위: Must**

- 로봇 손은 엄지 굽힘 및 대립축과 검지를 이용해 가벼운 소형 물체를 집어야 한다.
    
    인수 조건:
    
    - 엄지 끝과 검지 끝 또는 검지 측면이 접촉해야 한다.
    - 물체를 최소 3초 이상 유지해야 한다.
    - 지정된 물체를 10회 시험하여 7회 이상 성공해야 한다.

### 3.7 웹 기능

#### FR-19. 웹 모드 선택

**우선순위: Must**

시스템은 사용자가 웹사이트에서 로봇 손의 제어 방식을 선택할 수 있도록 해야 한다.

제공 모드:

- MIMIC: 실제 손동작 모방 모드
- MANUAL: 웹 버튼 기반 조작 모드

인수 조건:

- 사용자가 현재 선택된 제어 모드를 확인할 수 있어야 한다.
- 모방 모드와 조작 모드가 동시에 활성화되지 않아야 한다.
- 현재 제어 모드가 ROS 2 명령 메시지에 포함되어야 한다.
- 로봇 손이 동작 중이면서 안전한 상태(초기 자세)가 아닐 때에는 모드 변경이 불가능해야 한다.
→ 정지 버튼을 눌러서 안전한 상태(초기 자세)가 되어야만 모드를 변경할 수 있다.
- 두 모드 모두 웹에서 영상, landmark, 6채널 목표값, 모터 상태 및 안전 상태를 확인할 수 있어야 한다.
- 녹화 중에는 MIMIC 모드에서 MANUAL 모드로 변경할 수 없어야 한다.
- 녹화 중인 상태에서는 모든 일반 모드 변경 요청을 거부해야 한다.

#### FR-20. 모방 모드 영상 표시

**우선순위: Must**

웹사이트는 모방 모드에서 사용자의 손을 촬영하는 카메라 영상을 실시간으로 표시해야 한다.

인수 조건:

- RGB 카메라 영상을 웹 화면에서 확인할 수 있어야 한다.
- 영상 위에 MediaPipe 손 landmark를 표시해야 한다.
- 손 검출 성공 여부를 표시해야 한다.
- 손이 검출되지 않으면 사용자에게 안내 메시지를 출력해야 한다.
- 카메라 연결이 끊어진 상태를 구분할 수 있어야 한다.
- 카메라와 Vision Node는 시스템 실행 중 항상 동작해야 한다.
- MJPEG 영상 스트리밍은 데이터 녹화 여부와 독립적으로 동작해야 한다.
- MJPEG 영상은 웹 관제 목적으로만 사용하며 파일로 저장하지 않아야 한다.

#### FR-21. 모방 모드 손동작 정보 표시

**우선순위: Must**

웹사이트는 MediaPipe를 통해 계산된 손동작 정보를 실시간으로 표시해야 한다.

표시 대상:

- 5개 손가락 굽힘값
- 엄지 대립값
- 총 6채널 목표값
- 손 검출 신뢰도
- 현재 명령 발행 상태

인수 조건:

- 각 채널의 값을 `0.0~1.0` 범위로 표시해야 한다.
- 값의 변화를 숫자 또는 게이지 형태로 확인할 수 있어야 한다.
- 비정상적인 값은 화면에 표시하지 않고 오류 상태를 안내해야 한다.
- 기본 화면에는 직관적 데이터만 출력, 세부 데이터는 노출하지 않는다.
- 현재 통신 상태를 확인할 수 있어야 한다.

#### FR-22. 조작 모드 명령 입력

**우선순위: Must**

웹사이트는 조작 모드에서 버튼 입력을 통해 로봇 손에 명령을 전달할 수 있어야 한다.

기본 명령:

- 손 펴기
- 주먹 쥐기
- 원통형 물체 파지 자세
- 집기 자세
- 동작 정지
- 초기 자세 이동

추가 명령:

- 가위바위보
- 카운트다운

인수 조건:

- 사용자가 버튼을 통해 각 동작을 실행할 수 있어야 한다.
- 사용자 입력을 사전에 정의된 6채널 목표값으로 변환해야 한다.
- 현재 명령이 실행 중인 경우, 다음 명령은 실행하지 않는다(queueing).
- 모방 모드에서는 조작 모드 명령이 실행되지 않아야 한다.
- 각 버튼은 직관적인 아이콘을 사용한다.

---

#### FR-23. 웹 명령 범위 제한

**우선순위: Must**

웹사이트에서 생성하는 명령은 사전에 정의된 안전 범위를 벗어나지 않아야 한다.

인수 조건:

- 6채널 목표값은 각각 허용된 범위 안에서 생성되어야 한다.
- `NaN`, 무한대, 문자열 등 잘못된 값은 전달하지 않아야 한다.
- 한 번의 입력으로 목표값이 급격하게 변경되지 않아야 한다.
- 동작 정지 명령은 다른 일반 명령보다 우선하여 처리되어야 한다.
- 웹사이트는 모터에 직접 명령하지 않고 ROS 2 명령 인터페이스를 통해 전달해야 한다.

#### FR-24. 로봇 및 시스템 상태 모니터링

**우선순위: Must**

웹사이트는 로봇 손과 제어 시스템의 현재 상태를 표시해야 한다.

표시 대상:

- Jetson 연결 상태
- Raspberry Pi 연결 상태
- ROS 2 통신 상태
- 카메라 연결 상태
- 모터 연결 상태
- 현재 제어 모드
- watchdog 상태
- 안전 상태

인수 조건:

- 정상, 대기, 연결 끊김 및 오류 상태를 시각적으로 구분해야 한다.
- 모터 통신 오류가 발생한 경우 해당 모터를 식별할 수 있어야 한다.
- 통신이 끊기면 사용자에게 즉시 상태를 안내해야 한다.
- 상태 정보는 주기적으로 갱신되어야 한다.

#### FR-25. 모터 상태 표시

**우선순위: Should**

웹사이트는 Raspberry Pi가 발행한 모터 상태를 확인할 수 있도록 해야 한다.

표시 대상:

- 모터별 목표 위치
- 모터별 실제 위치
- 모터별 속도
- 모터별 전류
- 모터별 온도
- 모터 통신 상태

인수 조건:

- 6개 모터의 상태를 구분하여 표시해야 한다.
- 전류 또는 온도가 기준값을 초과하면 경고를 표시해야 한다.
- 상태값을 수신하지 못한 경우 마지막 값과 연결 끊김 상태를 구분해야 한다.
- 웹 화면의 상태 표시가 실제 모터 안전 제어를 대신해서는 안 된다.

#### FR-26. 데이터 기록 제어

**우선순위: Must**

웹사이트는 MIMIC 모드에서 실험 데이터 기록을 시작하고 종료할 수 있어야 한다.

인수 조건:

- 녹화 버튼은 MIMIC 모드에서만 활성화되어야 한다.
- 녹화 시작 요청 시 Logger가 Session ID를 생성해야 한다.
- 현재 녹화 상태와 Session ID를 웹에서 확인할 수 있어야 한다.
- 녹화 중에는 모드 변경 요청을 거부해야 한다.
- 웹에서 녹화 종료를 요청할 수 있어야 한다.
- 녹화 종료 후 사용자가 성공 또는 실패를 판정할 수 있어야 한다.
- 판정이 완료되기 전에는 다음 녹화를 시작할 수 없어야 한다.
- 카메라 영상은 저장하지 않아야 한다.
- rosbag2에는 MediaPipe landmark가 반드시 저장되어야 한다.
- WebSocket 메시지는 JSON 형식을 사용하며 세부 필드는 추후 확정한다.

#### FR-27. 웹 오류 및 안전 안내

**우선순위: Must**

웹사이트는 시스템 오류와 안전 상태를 사용자가 이해할 수 있도록 안내해야 한다.

안내 대상:

- 손 검출 실패
- 카메라 연결 실패
- ROS 2 통신 단절
- Raspberry Pi 연결 실패
- 모터 통신 오류
- timeout 발생
- 과전류 및 과온
- 비상정지 작동

인수 조건:

- 오류 발생 위치와 원인을 화면에 표시해야 한다.
- 위험 상태에서는 새로운 일반 조작 명령을 비활성화해야 한다.
- 비상정지가 작동한 경우 해제 전까지 조작 기능을 사용할 수 없어야 한다.
- 통신이 복구되더라도 사용자의 명시적인 제어 재개 입력 없이 자동으로 로봇 손을 움직이지 않아야 한다.

---

#### FR-28. 웹 실행 환경 제한

**우선순위: Must**

웹사이트는 프로젝트 전용 내부 네트워크에서 사용하는 것을 기본으로 해야 한다.

인수 조건:

- 외부 인터넷에서 직접 로봇 손을 제어할 수 없어야 한다.
- 웹 명령은 지정된 ROS 2 시스템에만 전달되어야 한다.
- 웹 서버가 중단되어도 Raspberry Pi의 모터 제한과 안전 기능은 독립적으로 동작해야 한다.

#### FR-31. 명령 중재 노드

**우선순위: Must**

`command_manager`는 여러 명령 입력 중 현재 제어 모드와 제어권에 맞는 입력원 하나만 선택해야 한다.

입력:

```
/hand/command/mimic
/hand/command/teleop
Gesture 실행 목표
Sequence 실행 목표
```

출력:

```
/hand/command
```

인수 조건:

- `command_manager`만 공식 `/hand/command`를 발행해야 한다.
- 현재 ControlMode와 owner에 맞는 입력원만 선택해야 한다.
- 모드 변경 시 이전 입력원의 명령을 폐기해야 한다.
- 물리적 범위 제한과 모터 보간은 수행하지 않아야 한다.
- 연결 복구 후 이전 모드와 명령을 자동으로 재개하지 않아야 한다.

#### FR-32. 명령 검증 및 안전 목표 생성

**우선순위: Must**

`command_guard`는 공식 명령을 검증하고 안전 제한을 적용해야 한다.

```
/hand/command
    ↓
command_guard
    ↓
/hand/safe_target
```

검증 항목:

- timestamp와 timeout
- sequence 중복 및 역전
- `NaN`과 무한대
- 논리축 `0.0~1.0` 범위
- 축별 위치·속도·변화율 제한
- 현재 SafetyState

인수 조건:

- 검증을 통과한 명령만 `/hand/safe_target`으로 발행해야 한다.
- 입력원 선택과 제어권 중재는 수행하지 않아야 한다.
- 안전 상태에서 허용되지 않는 일반 명령을 차단해야 한다.
- `command_guard`가 중단되면 마지막 일반 명령을 계속 실행하지 않아야 한다.

---

#### FR-33. 최신 목표 추종형 모터 제어

**우선순위: Must**

DYNAMIXEL 제어 노드는 목표 도달까지 콜백을 차단하지 않고 최신 안전 목표를 계속 추종해야 한다.

인수 조건:

- 명령 콜백은 `latest_target`만 갱신하고 즉시 반환해야 한다.
- 별도 제어 타이머가 최신 목표를 향해 보간해야 한다.
- 이전 목표에 도달하기 전에 새로운 목표를 처리할 수 있어야 한다.
- hardware-side timeout 시 마지막 일반 목표를 계속 실행하지 않아야 한다.
- 상태를 `/joint_states`와 `/hand/motor_status`로 발행해야 한다.

#### FR-34. 제어 모드 및 제어권 관리

**우선순위: Must**

ControlMode와 SafetyState는 독립적으로 관리하며 SafetyState가 항상 우선해야 한다.

ControlMode:

```
DISABLED
MIMIC
MANUAL
TELEOP
```

Owner:

```
NONE
WEB
LOCAL
```

모드별 허용 명령:

| 모드 | 허용 명령 |
| --- | --- |
| `MIMIC` | MediaPipe 손 목표 |
| `MANUAL` | 웹 Gesture 서비스·Sequence 액션 |
| `TELEOP` | 로컬 키보드 명령 |
| `DISABLED` | 일반 명령 없음 |

인수 조건:

- 모드 변경은 `/hand/set_control_mode` 서비스를 통해 수행해야 한다.
- 다른 owner의 모드 변경 요청은 거부해야 한다.
- Gesture 또는 Sequence 종료 후에도 MANUAL 모드를 유지해야 한다.
- 녹화 중에는 MIMIC 모드를 유지하고 모드 변경을 거부해야 한다.
- owner lease 만료 시 owner를 `NONE`, 모드를 `DISABLED`로 전환해야 한다.
- heartbeat와 lease timeout 수치는 추후 확정한다.

#### FR-35. 안전 상태 관리

**우선순위: Must**

안전 상태:

```
INIT
READY
RUN
HOLD
SAFE
FAULT
ESTOP
```

| 현재 상태 | 조건 | 다음 상태 | 동작 |
| --- | --- | --- | --- |
| 시작 전 | Bringup 실행 | `INIT` | 설정·모터 통신 검사 |
| `INIT` | 초기화 성공 | `READY` | 명령 대기 |
| `INIT` | 초기화 실패 | `FAULT` | 모터 구동 금지 |
| `READY` | 유효한 명령 | `RUN` | 최신 목표 추종 |
| `RUN` | 짧은 timeout | `HOLD` | 현재 목표 유지 |
| `RUN/HOLD` | timeout 장기화 | `SAFE` | 안전 동작 수행 |
| `RUN/HOLD` | 과전류·과온·통신 오류 | `FAULT` | 일반 명령 중단 |
| 모든 상태 | 물리적 비상정지 | `ESTOP` | 모터 전원 차단 |
| `SAFE` | 원인 해소·사용자 확인 | `READY` | 이전 명령 폐기 |
| `FAULT` | 원인 해소·reset 성공 | `READY` | 전체 조건 재검증 |

인수 조건:

- `SAFE`, `FAULT`, `ESTOP`은 일반 명령보다 우선해야 한다.
- HOLD 진입 후 자동으로 RUN에 복귀하지 않아야 한다.
- 통신 복구 후 사용자의 재활성화를 요구해야 한다.
- 실제 timeout·전류·온도 제한값은 하드웨어 시험 후 확정한다.

#### FR-40. 녹화 세션 및 결과 관리

**우선순위: Must**

Logger는 rosbag2 녹화와 SQLite 세션 정보를 전담해야 한다.

필수 서비스:

```

/hand/stop_recording
/hand/set_recording_result
```

인수 조건:

- 녹화는 MIMIC 모드에서만 허용해야 한다.
- 녹화 중에는 모드 변경을 거부해야 한다.
- Logger가 Session ID를 생성해야 한다.
- Logger만 SQLite를 수정할 수 있어야 한다.
- 웹은 SQLite를 직접 조회하거나 수정하지 않아야 한다.
- 동시에 하나의 녹화 세션만 허용해야 한다.
- 카메라 영상은 파일로 저장하지 않아야 한다.
- rosbag2에는 MediaPipe landmark가 반드시 포함되어야 한다.
- 나머지 녹화 토픽은 추후 확정한다.
- rosbag2 시작 또는 SQLite 초기화 실패 시 전체 녹화를 실패 처리해야 한다.
- 녹화 종료 후 성공·실패 판정 전에는 다음 녹화를 허용하지 않아야 한다.
- 녹화의 기술적 성공과 미믹 동작의 성공·실패를 분리해야 한다.

#### FR-44. Nominal 관절 자세 시각화

모터축에서 계산한 nominal 관절 자세를 RViz에 표시할 수 있다.

- 실제 측정값이 아님을 명시해야 한다.
- offset, ratio 및 dead-zone은 YAML로 관리한다.
- 실제 디지털 트윈 또는 정밀 관절 상태로 표현하지 않는다.

---

#### FR-45. 자세 추론 연구

**우선순위: Could**

- 사람 손 landmark에서 로봇 6축 목표를 추론할 수 있다.
- 첫 기준선은 정적 선형 회귀로 한다.
- 기하학 기반 retargeting을 fallback으로 유지한다.
- 모터 위치만으로 실제 접촉 상태의 관절각을 유일하게 복원할 수 없음을 명시한다.
- 본 기능은 MVP 필수 범위에서 제외한다.

## 5. 비기능 요구사항

### 5.1 성능 요구사항

#### NFR-01. 영상 처리 성능

- 손 landmark 검출은 평균 20FPS 이상을 목표로 한다.
- 손동작 목표값은 초당 20~30회 생성해야 한다.

#### NFR-02. 응답 지연

- 실제 손 움직임부터 로봇 손 동작 시작까지의 전체 지연은 300ms 이하를 목표로 한다.
- 일시적인 프레임 지연이 모터의 급격한 움직임으로 이어지지 않아야 한다.

#### NFR-03. 내구성

- 반복 후 텐던 이탈이나 부품 파손이 발생하지 않아야 한다.
- 최종 시스템은 최소 10분 동안 연속 시연할 수 있어야 한다.

#### NFR-04. 파지 성공률

- 가벼운 물체 2종을 각각 10회 시험한다.
- 각 물체에 대해 7회 이상의 파지 성공을 목표로 한다.

---

### 5.2 신뢰성 및 안전 요구사항

#### NFR-05. 명령 유효성

- 범위를 벗어난 명령은 실행하지 않아야 한다.
- timestamp가 오래된 명령은 무시해야 한다.
- `NaN`, 무한대 및 비정상적인 데이터가 모터에 전달되지 않아야 한다.

#### NFR-06. 고장 격리

- 하나의 모터 통신 오류가 전체 프로그램의 비정상 종료로 이어지지 않아야 한다.
- 오류가 발생한 모터와 오류 원인을 확인할 수 있어야 한다.

#### NFR-07. 기구 안전

- 스프링에는 최대 신장 제한 구조를 적용해야 한다.
- 텐던이 스풀과 가이드에서 쉽게 이탈하지 않아야 한다.
- 손가락이 설계된 가동범위를 물리적으로 초과하지 않아야 한다.
- 모터의 최대 힘의 크기를 제한해야함

---

### 5.3 사용성 요구사항

#### NFR-08. 실행 편의성

- 전체 시스템은 ROS 2 launch 파일을 통해 실행할 수 있어야 한다.
- 실행에 필요한 주요 파라미터는 코드 수정 없이 설정 파일에서 변경할 수 있어야 한다.

설정 대상:

- 카메라 번호
- 모터 ID
- 모터별 최소·최대 위치
- 속도 제한
- timeout 시간
- 안전 자세 - 초기 자세

#### NFR-09. 상태 확인

사용자는 다음 상태를 확인할 수 있어야 한다.

- 손 검출 여부
- 현재 6채널 목표값
- ROS 2 통신 상태
- 모터 연결 상태
- watchdog 상태
- 오류 코드
- 데이터 기록 여부

카메라 영상 오버레이와 터미널 로그 또는 간단한 모니터링 화면으로 구현할 수 있다.

---

### 5.4 유지보수 및 확장성 요구사항

#### NFR-10. 모듈 분리

다음 기능은 서로 독립적인 ROS 2 노드 또는 모듈로 분리해야 한다.

- 영상 입력
- 손 자세 인식
- 6채널 명령 생성
- 모터 제어
- 안전 관리
- 데이터 저장

#### NFR-11. 설정 분리

모터 제한값, 캘리브레이션값 및 안전 파라미터는 YAML 등 별도 설정 파일에서 관리해야 한다.

#### NFR-12. 향후 센서 확장

향후 다음 센서를 추가할 수 있도록 상태 메시지와 데이터 저장 구조를 확장 가능하게 설계해야 한다.

- 관절각 센서
- 스프링 변위 센서
- FSR 또는 촉각 센서
- 손끝 힘 센서
- 외부 모션 캡처 시스템

### 5.5 웹 인터페이스 비기능 요구사항

#### NFR-13. 웹 화면 응답 성능

웹사이트는 사용자의 조작과 시스템 상태 변화를 지연 없이 확인할 수 있도록 응답해야 한다.

측정 기준:

- 일반적인 버튼과 메뉴 입력은 200ms 이내에 화면에 반영되어야 한다.
- 손 검출 상태와 6채널 목표값은 초당 10회 이상 갱신되어야 한다.
- 모터 및 시스템 상태는 초당 5회 이상 갱신되어야 한다.
- 웹 화면 갱신이 ROS 2의 20~30Hz 명령 발행을 방해해서는 안 된다.
- 영상 표시 지연은 전체 로봇 제어 지연과 별도로 측정할 수 있어야 한다.

---

#### NFR-14. 영상 표시 성능

모방 모드의 카메라 영상은 사용자가 손 인식 상태를 확인할 수 있는 수준으로 제공되어야 한다.

측정 기준:

- 웹 영상은 평균 15FPS 이상 표시를 목표로 한다.
- 영상 지연은 500ms 이하를 목표로 한다.
- 영상 송출 지연이 실제 ROS 2 손 명령 생성에 영향을 주어서는 안 된다.
- 영상이 끊겨도 Raspberry Pi의 안전 기능은 계속 동작해야 한다.

---

#### NFR-15. 웹 제어 안정성

웹사이트에서 발생한 오류가 로봇 손의 비정상적인 동작으로 이어져서는 안 된다.

측정 기준:

- 웹에서 생성된 명령은 ROS 2로 전달되기 전에 형식과 범위를 검사해야 한다.
- 동일한 명령이 중복 전송되더라도 로봇 손이 비정상적으로 반복 동작하지 않아야 한다.
- 오래된 명령은 실행되지 않아야 한다.
- 연결이 끊긴 상태에서는 새로운 제어 명령을 생성하지 않아야 한다.
- 웹사이트를 새로고침하거나 종료하더라도 모터가 임의로 움직이지 않아야 한다.

---

#### NFR-16. 장애 독립성

웹사이트 또는 웹 서버의 장애가 로봇 손의 핵심 안전 기능에 영향을 주어서는 안 된다.

측정 기준:

- 웹 서버가 종료되어도 Raspberry Pi의 위치, 속도 및 전류 제한은 유지되어야 한다.
- 웹 서버가 종료되어도 통신 timeout과 안전 상태 전환이 동작해야 한다.
- 웹사이트는 모터에 직접 명령을 전달하지 않아야 한다.
- 실제 모터 제어와 안전 판단은 Raspberry Pi에서 수행해야 한다.
- 웹 연결이 복구되더라도 자동으로 제어를 다시 시작하지 않아야 한다.

---

#### NFR-17. 사용성

처음 사용하는 사용자도 별도의 교육 없이 기본 기능을 구분하고 실행할 수 있어야 한다.

측정 기준:

- 모방 모드와 조작 모드를 명확하게 구분해야 한다.
- 현재 선택된 모드를 항상 화면에서 확인할 수 있어야 한다.
- 손 펴기, 주먹, 파지, 집기, 정지 버튼은 의미를 쉽게 이해할 수 있어야 한다.
- 정상, 대기, 경고, 오류 상태를 시각적으로 구분해야 한다.
- 오류 메시지는 오류 코드뿐만 아니라 사용자가 이해할 수 있는 설명을 포함해야 한다.

---

#### NFR-18. 화면 구성 및 가독성

웹 화면은 시연 환경에서 주요 상태를 빠르게 확인할 수 있도록 구성해야 한다.

측정 기준:

- 현재 모드, 로봇 연결 상태 및 안전 상태는 화면 상단에 고정하여 표시해야 한다.
- 주요 제어 버튼은 스크롤 없이 접근할 수 있어야 한다.
- 6채널 값은 숫자와 게이지 또는 그래프 중 하나 이상의 방식으로 표시해야 한다.
- 경고와 오류 상태는 일반 상태보다 눈에 띄게 표시해야 한다.
- 지나치게 많은 원시 로그를 기본 화면에 표시하지 않아야 한다.
- 상세 모터 정보는 별도의 영역에서 확인할 수 있어야 한다.

---

#### NFR-19. 호환성

웹사이트는 프로젝트에서 사용하는 주요 실행 환경에서 동일한 기능을 제공해야 한다.

측정 기준:

- 데스크톱 환경을 우선 지원해야 한다.
- 일반적인 노트북 해상도에서 화면 요소가 겹치지 않아야 한다.
- 화면 크기가 변경되어도 주요 버튼과 상태 정보가 잘리지 않아야 한다.

---

#### NFR-20. 보안 및 접근 제한 -AI는 이 내용을 빼고 진행할 것

웹사이트는 프로젝트 전용 내부 네트워크에서만 로봇 손을 제어할 수 있도록 해야 한다.

측정 기준:

- 외부 인터넷에서 직접 로봇 손 제어 페이지에 접근할 수 없어야 한다.
- 프로젝트 전용 또는 신뢰할 수 있는 내부 네트워크를 사용해야 한다.
- 웹에서 전달되는 명령은 정의된 명령 형식만 허용해야 한다.
- 임의의 ROS 2 토픽 이름이나 모터 ID를 사용자가 입력할 수 없어야 한다.
- 사용자 입력값은 서버에서 다시 검증해야 한다.
- 웹페이지에 모터 통신 포트, 비밀번호 등 민감한 설정 정보를 노출하지 않아야 한다.

기존 명세서와 동일하게 복잡한 회원 인증, 외부 클라우드 제어 및 인터넷 원격 제어는 MVP에서 제외한다.

---

#### NFR-21. 유지보수성

웹 인터페이스는 화면 표시, ROS 2 연동 및 상태 관리 기능을 분리하여 구현해야 한다.

측정 기준:

- 모방 모드와 조작 모드 기능을 독립적인 화면 또는 컴포넌트로 분리해야 한다.
- ROS 2 메시지 송수신 기능을 화면 코드와 분리해야 한다.
- 명령 프리셋을 별도 설정 파일에서 관리할 수 있어야 한다.
- 오류 처리와 로그 기록 기능을 공통 모듈로 관리해야 한다.
- 기능 변경 시 로봇 모터 제어 코드를 직접 수정하지 않아도 되어야 한다.

---

#### NFR-22. 데이터 무결성 및 로그

웹에서 발생한 주요 제어와 오류 이벤트는 실험 결과를 추적할 수 있도록 기록해야 한다.

기록 대상:

- 모드 변경 시간
- 버튼  명령
- 데이터 기록 시작 및 종료 시간
- ROS 2 연결 및 해제 시간
- 손 검출 실패
- 모터 및 시스템 오류
- 비상정지와 제어 재개
- 파지 성공 또는 실패 결과

측정 기준:

- 모든 이벤트는 timestamp를 포함해야 한다.
- 웹 명령과 ROS 2 명령을 시간 기준으로 비교할 수 있어야 한다.
- 기록 실패가 로봇 제어 프로그램의 종료로 이어져서는 안 된다.
- 로그 파일이 무제한으로 증가하지 않도록 용량 또는 보관 기간을 설정해야 한다.
- 실험 종료 후 로그를 다시 확인할 수 있어야 한다.

---

#### NFR-23. 복구 가능성

일시적인 통신 오류 이후 시스템은 안전한 절차를 통해 복구될 수 있어야 한다.

측정 기준:

- 연결이 끊기면 웹 화면에 연결 끊김 상태를 표시해야 한다.
- 연결 복구를 일정 주기로 시도할 수 있어야 한다.
- 연결이 복구되더라도 이전 명령을 다시 실행하지 않아야 한다.
- 사용자가 현재 상태를 확인하고 제어 재개를 선택해야 한다.
- 재연결 실패가 반복되면 명확한 오류 메시지를 제공해야 한다.

---

### 5.6 보안 요구사항

본 시스템은 폐쇄된 실험실 또는 내부 Wi-Fi 환경에서 사용하는 시제품이므로 복잡한 인증 시스템과 인터넷 기반 보안 기능은 MVP에서 제외한다.

다만 다음 기본 조건은 만족해야 한다.

- 외부 인터넷에서 직접 모터 명령을 전달하지 않는다.
- 프로젝트 전용 또는 신뢰할 수 있는 내부 네트워크를 사용한다.
- ROS_DOMAIN_ID를 팀 프로젝트에 맞게 설정한다.
- 모터 제어 노드는 지정된 형식의 명령만 처리한다.
- 외부 REST API와 클라우드 제어 기능은 제공하지 않는다.
- ROS 2 DDS Security 적용은 향후 확장 항목으로 분류한다.

### 6.4 통신 인터페이스

- Jetson과 Raspberry Pi는 Wi-Fi 기반 ROS 2 DDS로 통신한다.
- ROS 2 배포판은 Humble로 통일한다.
- `command_manager`만 공식 `/hand/command`를 발행한다.
- `command_guard`를 통과한 `/hand/safe_target`만 모터 노드가 처리한다.
- 명령 콜백은 목표 도달까지 차단되지 않아야 한다.
- ControlMode와 SafetyState를 분리하고 SafetyState를 우선한다.
- 웹과 Web Bridge는 WebSocket JSON으로 통신한다.
- JSON의 세부 필드는 추후 확정한다.
- Jetson은 landmark overlay 영상을 MJPEG로 웹에 제공한다.
- MJPEG와 웹 장애는 로봇 제어 및 안전 기능에 영향을 주지 않아야 한다.
- 카메라는 항상 실행한다.
- 녹화 버튼은 카메라 실행이 아니라 rosbag2 기록만 제어한다.
- 카메라 영상 파일은 저장하지 않는다.
- rosbag2에는 MediaPipe landmark를 반드시 포함한다.
- 그 외 녹화 토픽은 추후 확정한다.
- 연결 복구 후 이전 모드나 명령을 자동으로 재개하지 않는다.

## 7. 시스템 제약사항

### 7.1 하드웨어 제약사항

- 각 손가락의 여러 관절은 하나의 모터로 함께 구동된다.
- 모터 엔코더값은 실제 손가락 관절각과 동일하지 않다.
- 물체 접촉 후 모터 이동량 일부는 스프링 신장으로 사용될 수 있다.
- 모터 토크와 전류는 스풀 반지름에 영향을 받는다.
- 손가락과 손바닥은 3D 프린팅 공차의 영향을 받는다.
- 텐던의 늘어남, 마찰 및 초기장력 변화가 반복 정확도에 영향을 줄 수 있다.
- 모터 6개의 동시 구동을 고려한 전원 공급 장치가 필요하다.

---

### 7.2 소프트웨어 제약사항

- Jetson에서는 Ubuntu 22.04와 ROS 2 Humble을 사용한다.
- Raspberry Pi에서는 ROS 2 Humble 실행을 위해 Ubuntu 22.04 기반 Docker를 사용한다.
- MediaPipe 손 검출 성능은 조명, 손 가림 및 카메라 각도의 영향을 받는다.
- 로보티즈 SDK 기반으로 모터 노드를 구현한다.
- MVP에서는 관절 상태 추정을 위한 학습 모델을 사용하지 않는다.

---

### 7.3 네트워크 제약사항

- Wi-Fi 지연과 패킷 손실이 발생할 수 있다.
- 네트워크 단절과 관계없이 Raspberry Pi가 독립적으로 안전 기능을 수행해야 한다.
- 오래된 명령을 순차적으로 실행하지 않고 가장 최신의 유효한 명령을 사용해야 한다.
- Jetson과 Raspberry Pi는 동일한 ROS_DOMAIN_ID와 호환되는 DDS 설정을 사용해야 한다.

---

### 7.4 설계 및 구현 제약사항

- 전체 개발 기간은 3주이다.
- 첫 번째 주에 손가락 텐던 구동을 우선 검증해야 한다.
- 일반 손가락보다 엄지를 우선적으로 검증해야 한다.
- 하드웨어 제작과 소프트웨어 개발은 병렬로 진행해야 한다.
- 모든 주요 기능은 최종 주 이전에 최소 한 번 이상 통합 시험을 수행해야 한다.

---

### 7.5 전제조건 및 의존성

- 서보와 USB 버스 어댑터가 정상적으로 통신해야 한다.
- 모터의 위치와 상태값을 읽을 수 있어야 한다.
- 3D 프린터를 프로젝트 기간 동안 사용할 수 있어야 한다.
- 모터 전원 공급 장치가 6개 모터의 순간 전류를 감당할 수 있어야 한다.
- 테스트 중 사용자의 손이 카메라 화면에서 크게 가려지지 않아야 한다.
- 한 번에 한 사용자의 오른손만 제어 대상으로 한다.
- 물체는 사전에 지정된 위치와 방향으로 배치한다.

### 8.2 테스트 요구사항

#### 단위 테스트

- 손가락 관절각 계산 테스트
- `0.0~1.0` 정규화 테스트
- 필터 및 deadband 테스트
- 잘못된 명령값 제한 테스트
- timeout 계산 테스트
- 모터 명령 변환 테스트

#### 기구 테스트

- 텐던 소재별 늘어남 비교
- 스풀 반지름별 이동량 비교
- 스프링 강성 및 초기장력 비교
- 한 손가락 10회 반복 시험
- 반복 후 텐던 이탈과 영점 변화 확인
- 모터 온도와 전류 확인
- 엄지 가동범위 및 검지 접촉 여부 확인

#### 통합 테스트

- Jetson에서 Raspberry Pi로 ROS 2 명령 전달
- 6개 모터 동시 제어
- 실제 손동작과 로봇 손동작 연결
- 손 landmark 검출 실패 시험
- 모터 통신 오류 시험
- 데이터 기록 및 재생 시험
- command manager가 현재 모드의 입력원 하나만 선택하는지 시험
- command guard가 오래된 명령, NaN, 범위 초과 및 잘못된 sequence를 거부하는지 시험
- 이전 목표 도달 전 새로운 목표를 정상적으로 추종하는지 시험
- SafetyState가 ControlMode보다 우선하는지 시험
- owner 충돌과 lease 만료 시 DISABLED 전환 시험
- 웹 재연결 후 이전 명령이 자동 실행되지 않는지 시험
- MJPEG 중단이 로봇 제어에 영향을 주지 않는지 시험
- MIMIC 외 모드에서 녹화 요청이 거부되는지 시험
- 녹화 중 모드 변경이 거부되는지 시험
- rosbag2에 MediaPipe landmark가 기록되는지 시험
- rosbag2 또는 SQLite 초기화 실패 시 녹화 전체가 실패하는지 시험
- 성공·실패 판정 전 다음 녹화가 거부되는지 시험
- 실제 모터 없이 Dry-run 명령 경로 시험

#### 시스템 테스트

- 편 손과 주먹 시연
- 원통형 물체 파지
- 집기
- 물체별 10회 반복 시험
- 10분 연속 동작 시험
- 비상정지 시험

### 8.3 검수 기준

프로젝트는 다음 조건을 모두 만족했을 때 MVP가 완료된 것으로 판단한다.

- Must 우선순위 기능 요구사항이 모두 구현되었다.
- 실제 손의 편 손과 주먹 자세를 로봇 손이 모방한다.
- 엄지 굽힘과 대립 동작이 구분되어 제어된다.
- 원통형 물체를 파지할 수 있다.
- 가벼운 물체를 집을 수 있다.
- 가벼운 물체 2종을 각각 10회 시험하여 7회 이상 성공한다.
- ROS 2 무선 명령 전달이 정상적으로 동작한다.
- 명령 단절 시 설정된 안전 동작이 수행된다.
- 물리적 비상정지로 모터 전원을 차단할 수 있다.
- 치명적인 기구 파손이나 텐던 이탈 없이 시연을 완료한다.
- 테스트 결과, 성공률 및 주요 제한사항이 문서화되어 있다.
